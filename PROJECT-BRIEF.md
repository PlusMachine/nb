# NB — презентация проекта (полный контекст)

> Самодостаточный обзор проекта: что это, для кого, что уже реализовано с
> **продуктовой** и **технической** точек зрения, что в работе и что дальше.
> Актуально на 2026-07-02 (сверено с кодом и историей коммитов; канонический
> внутренний контекст — `CONTEXT.md`, порядок работ — `docs/roadmap.md`).

---

## 1. Что это

**NB** (рабочие кандидаты названия — «NB» / «hmelo») — **web-first платформа для
домашних пивоваров** (homebrewing). Не форум и не магазин: центр гравитации —
**рецепт** и путь от идеи до готового пива.

**Продуктовый workflow:**

```
Каталог ингредиентов → Мой склад → Рецепт → Match «что можно сварить» →
Варка (виртуальный гид ИЛИ автоматика на своём контроллере) → Журнал замеров → Дашборд
```

Поверх этого — публичная витрина: рецепты сообщества, справочник стилей BJCP,
калькуляторы пивовара, редакторские гайды.

### Две продуктовые петли

- **Мастерская** (рабочая зона, требует логина) — рецепт из склада → Match → варка
  → журнал замеров → дашборд. Отвечает за **удержание** (retention). Приоритетна.
- **Витрина** (публичная, без логина) — контент/гайды, рецепты сообщества, BJCP,
  калькуляторы. Отвечает за **привлечение** (acquisition, SEO). Идёт вторым эшелоном.

Принцип: между этапами всегда держим «следующий логичный шаг»; retention раньше
acquisition; интерфейс самоочевиден из структуры/иконок/порядка, без поясняющих
подзаголовков.

## 2. Что пользователь уже может сделать (продуктовое состояние)

Всё перечисленное — **реализовано и работает**, не макеты.

### Каталог ингредиентов (публичный)
- Просмотр каталога солодов, хмеля, дрожжей, сахаров, добавок, финингов и пр. по
  адресу `/catalog` — **без логина**.
- Технические поля по каждому типу (для солода — экстракт/цвет, для хмеля — альфа/форма,
  для дрожжей — тип/форма/аттенюация и т.д.), алиасы, источники, варианты фасовки.
- Единый поиск и единый `IngredientPicker` для каталога/склада/рецептов.
- Залогиненный пользователь может завести **кастомный ингредиент**, отметить избранное,
  предложить ингредиент в модерацию.

### Мой склад / инвентарь
- Учёт того, что реально есть дома: количество во **введённых и нормализованных**
  единицах (ввёл «500 г» / «1 кг» — сервер нормализует к канонической единице).
- Фильтры, сортировка, инлайн-редактирование количества, архивирование.
- **Цены и валюты** (RUB/USD/EUR, хранение в минорных единицах), дата покупки,
  свежесть, стоимость позиции.
- Автокомплит-подсказки по складу.

### Рецепты (авторская сторона)
- Полноценный **редактор рецепта**: ингредиенты по стадиям (затор/кипячение/хмелестояние/
  брожение), тайминги, вода, оборудование.
- **Живой расчёт статистики**: OG, FG, ABV, IBU, цвет (SRM/EBC) — production-grade
  движок (`@nb/brewing-core`).
- **Водоподготовка**: профили воды (исходный/целевой), солвер солей/кислот, оценка pH затора.
- **Импорт/экспорт**: BeerXML и JSON.
- **Версионирование** рецептов (семейство + номер версии, стабильные ключи ингредиентов).
- **Клон чужого** публичного рецепта себе + **пересчёт под свой объём** (scaling).
- **Фото** рецепта: загрузка, 4 варианта размеров + blur-заглушка, обложка.
- Публикация: draft / private / published, серверный gating.

### Витрина рецептов сообщества (публичная)
- Список публичных рецептов с **discovery**: фильтры (sidebar/выезжающий sheet на мобиле),
  range-слайдеры (OG/FG/ABV/IBU/SRM), выбор стиля, цветовая шкала, пагинация,
  состояние в URL.
- Страница рецепта по slug: полная инфа, **рейтинг (звёзды 1–5)**, **сохранение в избранное**,
  богатые SEO-метаданные.
- **Адаптивная вёрстка** витрины (недавний редизайн: колонки, скелетоны, sticky-панель,
  список на мобиле).

### Match Engine — «что можно сварить прямо сейчас»
- На карточках рецептов (в discovery, «Мои», «Сохранённые») — **бейдж «можно сварить / почти»**:
  движок построчно матчит рецепт против твоего склада.
- Дрожжи матчатся **по наличию штамма** (а не по количеству), бренд-каскад для
  обобщённых сортов солода.
- Порог: покрыто ≥70% типов ингредиентов и не больше 2 недостающих → «почти»;
  есть все типы → «можно сварить».
- Из панели рецепта — **«добавить недостающее на склад»** (не «докупить» — магазина нет),
  с предзаполненной нехваткой в человеческих единицах.

### Варка (Brew Session) — жизненный цикл
- Раздел **«Варки»** (`/app/brew-batches`): активные (planned/brewing/fermenting) + история.
- Деталь варки — **«центр управления»**: гибкий статус-степпер (любой переход + отмена),
  **журнал замеров OG/FG** (SG, вычисление ABV и степени сбраживания против целей рецепта), заметки.
- **Иммутабельный снапшот** рецепта/оборудования/воды в момент старта варки — источник истины
  (рецепт можно потом менять, варка не «поедет»).
- **Списание склада на варку**: авто-подбор и consume ингредиентов с привязкой к варке,
  компенсирующий откат при отмене, защита от двойного списания.
- **Два режима исполнения** (см. §3).

### Дашборд / командный центр (`/app`)
- **«Активные варки»** — карточки, отсортированные по срочности подсказки «следующего шага»
  («пора начинать» / «запишите OG» / «N дней без замера — проверьте FG»).
- **«Можно сварить сейчас»** — свои рецепты, под которые на складе есть все типы ингредиентов.
- Статы (рецепты / в наличии / всего позиций), быстрые входы, discover-полоска.
- Секции **count-conditional**: новый пользователь видит чистый онбординг, активный — рабочую петлю сверху.

### Справочник BJCP и калькуляторы (публичные)
- Каталог стилей BJCP и страницы стилей (file-backed данные, SEO, related).
- **Каталог калькуляторов** пивовара: конвертеры gravity/ABV/аттенюация/разбавление/
  выкипание, рефрактометр↔ареометр, прайминг, карбонизация, дрожжевой стартер, объёмы
  воды, свежесть хмеля, конвертер единиц.

### Контент-CMS / гайды (публичные + админка)
- Публичный хаб **`/guides`** и страницы статей (безопасный рендер Tiptap JSON → React,
  SEO + JSON-LD).
- **Админ-CRUD** `/admin/articles` с Tiptap-редактором; публикация/вывод на главную/
  удаление — по ролям.
- Главная переделана в **хаб гайдов** (featured из CMS + BJCP + точки входа).

### Устройства BrewForge (см. §3, автоматический режим варки)
- Раздел **`/app/devices`**: пайринг устройства по коду, статус online/offline, настройки,
  отзыв доступа.

### Аутентификация
- Мультиметодный вход `/login`: **пароль, OTP (6 цифр), magic-link, OAuth** (Google/VK/Yandex).
- Роли: user / editor / moderator / admin. Серверные гейты доступа и ownership.
- **App-first навигация** с гейтом логина, «помнящим» цель (`?next=`): действия вроде
  сохранения/оценки ведут на логин и возвращают обратно.

## 3. Ключевая фича — два режима варки

Свой рецепт можно варить в **двух режимах**. Оба создают одну сущность `brew_batch`
и идут по одному жизненному циклу; различие — «контур исполнения».

### Режим 1 — Виртуальный (ручной)
Без устройства (`device_id = NULL`). Человек сам управляет оборудованием, портал — **гид и контроль**:
- **Пошаговый «варочный день» на экране** — живой чек-лист из снапшота плана варки:
  группы затор / кипячение / хмелестояние (вирпул) / брожение, **таймеры пауз и кипячения**
  (переживают перезагрузку страницы), отметки «шаг выполнен».
- Плюс журнал замеров и списание склада.

### Режим 2 — Автоматический (BrewForge)
Через **собственный контроллер BrewForge** (железо на ESP32-S3; прошивка — в соседнем
репозитории `../brewforge`). Варка запускается **прямо с сайта**:
- Точка входа «Варить на устройстве» → открыть сессию → push рецепта → START_BREW.
- Деталь варки показывает **live-дашборд и график телеметрии**.
- **Два транспорта:**
  - **LAN** — прямой REST на устройство в локальной сети (с SSRF-гардом).
  - **Облако** — «варка откуда угодно» через мост `apps/bridge` (MQTT↔WebSocket↔Postgres):
    телеметрия читается из БД, команды/рецепт публикуются в брокер, ack коррелируется по id команды.
    Верифицировано end-to-end на связке mosquitto + мост + симулятор.
- Замороженный zod-контракт протокола `@nb/brewforge-protocol` (прошивка зеркалит его в cJSON),
  симулятор устройства `@nb/device-sim`, safety нагрева живёт **на устройстве** (портал её не ослабляет).

**Статус:** базовая интеграция построена и подключена (оба транспорта, пайринг, телеметрия,
команды Пауза/Продолжить/Пропустить, cloud start-brew). Идёт **редизайн «пульта» варочного
центра (L2)** — новые компоненты, device-mode, запуск варки из каталога; часть блоков собрана,
но ещё не верифицирована на живом стенде.

## 4. Техническая архитектура

### Стиль
**Modular monolith**: один рантайм (`apps/web`), одна БД PostgreSQL, монорепо. Доменная
логика — в переиспользуемых пакетах и feature-сервисах. Без микросервисов и без второй
параллельной архитектуры.

### Стек
- **Next.js 15** (App Router) + **React 18** + **TypeScript strict**
- **Tailwind CSS** + shadcn-style примитивы (`@nb/ui`, Radix + CVA + Lucide)
- **PostgreSQL** + **Drizzle ORM** (`@nb/db`)
- Tiptap (rich text), @dnd-kit (drag&drop), sharp (картинки), @aws-sdk/client-s3 (storage)
- **Vitest** (тесты), **Docker Compose** (Postgres 16 + Mailpit)
- Sentry + PostHog (наблюдаемость — adapter-скелеты)
- Пакетный менеджер — **pnpm** (workspaces; недавняя миграция с npm)

### Раскладка монорепо
```
apps/
  web            — основной рантайм Next.js: app/(public|app|admin|api), features/*, components/, lib/, tests/
  bridge         — облачный мост MQTT ↔ WebSocket ↔ Postgres для BrewForge
  device-sim     — симулятор устройства BrewForge
packages/
  @nb/db                  — schema (src/schema.ts), миграции, seed/reset
  @nb/auth                — session / password / OAuth / OTP / magic-link
  @nb/brewing-core        — расчёты, style fit, brew-steps
  @nb/content             — BJCP/контент data layer (file-backed)
  @nb/brewforge-protocol  — замороженный zod-контракт протокола устройства
  @nb/ui / @nb/shared     — UI-примитивы / env-контракты и общие утилиты
  @nb/push                — push-уведомления (скелет)
  @nb/search              — ТОЛЬКО scaffold, не основной search runtime
```

### Зоны маршрутов
- `(public)` — без авторизации: `/`, `/catalog`, `/recipes`, `/bjcp`, `/calculators`,
  `/guides`, `/login`. **Cache-safe** (публичные страницы не читают сессию).
- `(app)` — требует логин (`requireUser()`), обёрнуто в `AppShell`: `/app`, `/app/recipes`,
  `/app/saved`, `/app/ingredients` (склад), `/app/equipment`, `/app/brew-batches`,
  `/app/devices`, `/profile`.
- `(admin)` — требует роль editor+: `/admin/articles`, `/admin/ingredients` (+ модерация, merge),
  `/admin/settings/currency`.
- `api/` — auth, ingredients search/proposals/custom, recipe-images upload, inventory suggestions,
  admin ingredients/merge/moderation.

### Архитектурные инварианты (соблюдаются)
1. **Ingredient identity** — ингредиенты это сущности, а не free-text (где есть source linkage).
2. **Единый picker/search** — один `IngredientPicker` и один поиск на catalog/inventory/recipes.
3. **Entered + normalized единицы** — хранятся обе; нормализация только на сервере.
4. **Ownership & permissions на сервере** — нельзя редактировать чужое; доступ не зависит от скрытых кнопок.
5. **Доменная логика в service layer** (`features/*` / `@nb/*`), не в компонентах/страницах.
6. **Public recipe access** — только через recipe service, gating серверный.
7. **Content/BJCP** — file-backed через `@nb/content`, без ad-hoc парсинга в страницах.
8. **Reuse over rebuild** — расширять существующее, не строить параллельные слои.

## 5. Доменное ядро расчётов (`@nb/brewing-core`)

Production-grade, покрыто юнит-тестами, без БД/React:
- **gravity.ts** — OG (points + efficiency, **per-fermentable**: экстракты/сахара на ~100%),
  FG (аттенюация), ABV.
- **ibu.ts** — 5 формул (Tinseth Classic, Tinseth Whirlpool V2, Rager, Garetz, Noonan Legacy);
  boil / first-wort / whirlpool / dry-hop, late-boil carryover, высота, флокуляция, hop utilization.
- **color.ts** — MCU → SRM (Morey) → EBC.
- **water.ts** — солвер целевого профиля воды (hill-climbing по солям), оценка pH затора (Kolbach RA),
  подбор кислоты (binary search). Соли: gypsum, calcium chloride, epsom, table salt, baking soda,
  chalk, slaked lime. Кислоты: молочная, фосфорная.
- **calculator-tools.ts** — конвертеры для всех публичных калькуляторов.
- **scaling.ts** — масштабирование рецепта + пересчёт статов.
- **brew-steps/**, **styles/** — генерация шагов варки, BJCP-стили и style fitting.

## 6. Модель данных (основное, `@nb/db`)

- **Auth/User:** `users`, `sessions`, `accounts` (OAuth), `verifications`, `authRateLimits`.
- **Каталог:** `ingredients` (основной runtime), `ingredientAliases`, `ingredientSources`,
  `ingredientPackageVariants`, `ingredientFamilies`, `proposedIngredients` (модерация).
  *(legacy-таблица `ingredient_catalog_items` удалена.)*
- **Пользовательский домен:** `userCustomIngredients`, `userIngredientPreferences`,
  `userIngredients` (**инвентарь**: entered+normalized, цены в минорных единицах + валюта, свежесть),
  `userBrewingSettings`.
- **Оборудование:** `equipmentProfiles` (объём партии, КПД, испарение, поглощение зерна, утилизация хмеля, высота).
- **Рецепты:** `recipes` (семейство + версия, publicationState, slug, статы, денормализованные
  `rating_avg`/`rating_count`/`save_count`, JSONB-мета снапшотов, `cloned_from_recipe_id`),
  `recipeIngredients` (стабильный ключ между версиями, source linkage), `recipeImages`,
  `recipeRatings` (1–5), `recipeSaves`.
- **Варка:** `brewBatches` (снапшот рецепта/оборудования/воды + `device_id` + `brew_day_progress`),
  `brewMeasurements` (журнал SG/OG/FG); **аллокации** `recipeInventoryAllocations` +
  `inventoryTransactions` (списание на варку, привязка к `brew_batch_id`).
- **Контент-CMS:** `contentArticles` (guide/review, draft/published/archived, Tiptap bodyJson, SEO).
- **Устройства BrewForge:** `brewDevices`, `devicePairingTokens`, `brewTelemetry`, `brewLogEvents`,
  `deviceCommands`, `deviceProfiles`.

**Нормализация:** юзер вводит «500g»/«1 kg» → сервер нормализует к канонической единице; хранятся обе.

## 9. Известные ограничения (честно)

**Закрыто недавно:**
- P1-безопасность: логирование токенов, заглушка captcha, cleanup verifications — **исправлено**.
- Legacy-таблица каталога `ingredient_catalog_items` — **удалена**.
- Занижение OG для экстрактов — **исправлено** (per-fermentable efficiency).

**Остаётся:**
- `recipe-designer.tsx` — очень крупный компонент (бизнес-логика частично в UI) → архитектурный
  блокер для тестируемости.
- Magic-link токен в GET-параметрах; отдельные N+1 в сервисах; нет строгих row-lock на
  consume/restore склада (риск низкий для single-owner).
- Тестовые пробелы: API-роуты и пакеты `@nb/auth`/`@nb/ui`/`@nb/shared` — почти без тестов, нет e2e.
- Нет CI-проверок (migration drift, coverage), i18n (строки захардкожены на русском), a11y-пробелы.
- Точность калькулятора рецептов: известные расхождения по FG (несбраживаемые сахара),
  IBU хмелестояния/first-wort, формуле SRM — числа карточек берутся из источника, но доверие
  к калькулятору для пользовательских рецептов ограничено.

## 10. Как запустить локально

```bash
cp .env.example .env
pnpm install
docker compose up -d          # PostgreSQL 16 + Mailpit
pnpm run dev                  # авто migrate + seed, затем Next.js
```

QA-данные:
```bash
pnpm run seed:qa              # QA-юзеры (admin/moderator/editor/user) + каталог + инвентарь
pnpm run seed:sample          # склад + оборудование + 6 рецептов для DEV_AUTH_EMAIL
```

**Dev-автологин:** задать `DEV_AUTH_EMAIL` в `.env` (жёстко отключён при `NODE_ENV=production`).
