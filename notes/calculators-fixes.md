# ТЗ: доводка калькуляторов до уровня «проверенных»

Итог аудита 2026-07-17 (5 агентов: выжимка эталона из 5 проверенных + критика 12 непроверенных, контрольные примеры пересчитаны руками, ключевые находки перепроверены по коду). Математика везде верна; чиним три класса проблем: «тихо неверные» результаты, обязательные поля с неизвестными пользователю значениями, бедную подачу результата.

Ключевые файлы:
- `apps/web/features/calculators/definitions.ts` (D) — определения полей/расчётов
- `apps/web/features/calculators/catalog.ts` (C) — карточки/SEO/статические секции
- `apps/web/components/calculators/calculator-page-client.tsx` (P) — рендерер
- `packages/brewing-core/src/calculations/calculator-tools.ts` (T), `mash.ts`, `efficiency.ts`, `ibu.ts` — ядро

Эталонный чек-лист «что делает калькулятор проверенным» (сверяться на каждом пункте):
дефолты дают осмысленный результат без ввода · пустое поле = «не указано», не 0 · фолбэки в текущей шкале · неизвестный параметр = опционален с фолбэком + предупреждение «как улучшить точность» · переключение шкалы конвертирует значение (`GRAVITY_PREFERENCE_CONFIG`, P:1908) · предупреждения с тонами вместо молчания/запретов · заполненные commonMistakes/formula в C · в конце — slug в `verifiedCalculatorSlugs` (C:70).

Правило миграций: любое изменение дефолтов/полей — только с `migrateStoredState` (образцы: abv D:1109, hydro D:1251) и проверкой входящих ссылок `applyQuery`.

## Волна 1 — корректность (убирает «тихую ложь», дёшево)

**К1. Unit-aware фолбэки пустых полей плотности.** Один класс бага в 4 местах: фолбэк — литерал SG, при шкале Plato читается как ~1.004 SG.
- Разбавление: D:856 `n(state.currentGravity, 1.06)` и D:860 `targetGravity …1.05`.
- IBU: D:1425 `n(state.wortGravity, 1.05)` — молча завышает IBU на ~15% при °P.
- Эффективность: D:2258 `n(state.measuredOg, 1.05)` — при °P пустой замер даёт «эффективность ~0%» + ложное предупреждение.
- Образец фикса — эталонный ABV: D:735-738 (`unit === "SG" ? 1.05 : 12.4`, с комментарием).
- Приёмка: на каждом из трёх калькуляторов переключить шкалу на °P, очистить поле плотности → результат считается от разумного °P-дефолта, без мусора и ложных предупреждений. Юнит-тест на каждый compute с state `{gravityUnit:"Plato"}` и пустым полем.

**К2. Цвет пива: динамическая единица цвета солода.** D:2107 — статичная подпись `"EBC | °L"` при переключателе шкалы над полем; разница шкал ×2 — та самая «частая ошибка» из C:409. Механизм готов: `dynamicUnit` (обр. D:2213), рендер P:186. Подпись должна показывать выбранную шкалу («EBC» или «°L»).

**К3. Засев дрожжей: клетки в пакете зависят от типа.** D:1735 `cellsPerPackBillion: 100` фиксирован; сухой пакет 11 г ≈ 200 млрд → дефолт даёт ложный «недосев» вдвое.
- При переключении «Тип дрожжей» (D:1760) подставлять пресет: жидкие ~100, сухие ~200 (transformOnChange-паттерн, обр. D:454) — только если пользователь не менял значение руками (флаг touched, как `gravityUnitTouched`).
- Хелпер поля: «Жидкая пачка ~100 млрд, сухая 11 г ~200 млрд».
- Опционально (решение по ходу): для сухих — ввод в граммах с пересчётом ~18-20 млрд/г.
- Приёмка: дефолтный сценарий «Сухие, 1 пачка, 20 л, 12.4 °P» не показывает «Мало дрожжей».

**К4. Предупреждения вместо молчаливых нулей.**
- Шпайзе: при `targetCo2 ≤ residualCo2` (кламп T:592) — warning «Пиво уже карбонизировано до цели — добавка не нужна» (код в ядро + перевод в `coreWarningCopy` D:246).
- Бутылки: при потерях ≥ объёма — warning вместо молчаливого «0 шт».
- Эффективность, режим «Прогноз» (D:2235-2255): пустая/беспотенциальная засыпь → «—» + предупреждение, как в measure-режиме; сейчас ветка вообще без warnings и кажет «0.0 °P» как результат.
- Приёмка: ни один калькулятор не показывает 0 как «нормальный» результат без пояснения.

**К5. IBU: связать два «времени вирпула».** Глобальное поле D:1364 управляет только переносом горечи кипятильных внесений; строки типа «Вирпул» считаются по своему полю «Время» (`ibu.ts:269`) — дефолты 15/15 совпадают случайно. Решение: пустое время у вирпул-строки = фолбэк на глобальное поле + развести подписи («Отстой после кипячения» у глобального, у строки — «Время внесения»). Приёмка: изменение глобального времени меняет IBU вирпул-строк с пустым временем.

**К6. Разбавление: подавить второе предупреждение со ссылкой на скрытое поле.** В режиме «Уварить до плотности» при цели ниже текущей ядро пушит и `target_gravity_below_current`, и `target_volume_above_current` («Проверьте „Целевой объём“» — поля нет в форме). T:180-185 либо фильтр в `computeDilutionView`.

**К7. Мелочь одной пачкой (текст, без логики):**
- «Мед» → «Мёд» D:415 (пропуск свипа Ф15).
- «CO2» → «CO₂» в подписях полей/статов (D:1497, 1517, coreWarningCopy:266-267 и по grep).
- «Испарение, л/ч» → «Выкипание, л/ч» D:1040 (+ проверить brewing-water-volume).
- «Гранулы / Листовой» → «Гранулы / Шишки» D:1396-1399.
- Ты/вы: хелперы праймера D:1486, D:1503 привести к «вы» (весь раздел на «вы»).
- Свежесть хмеля, слоп-хелперы: удалить «Сколько этого хмеля требует рецепт» (D:2443); в хелпере даты оставить только «Пусто — считаем хмель свежим» (D:2429).
- Цвет пива: убрать дубль SRM/EBC/MCU из stats (primary уже показывает всё, D:2128-2135), оставить разбивку по солодам; вклады >6 — добавить «и ещё N» вместо молчаливого `slice(0,6)` (D:2136).
- Шпайзе: «Температура» → «Температура пива» + хелпер «В конце брожения, даже если пиво уже охладили» (как в праймере D:1493-1496); убрать дубль «Финальный объём» (D:2406-2408); хелпер «по температуре пива» у остаточного CO₂ скрывать, если CO₂ введён вручную (D:2410).

**❓ К8 (решение владельца). «Кройцен» → «краузен».** В РУ-сообществе устоялось «краузен/краузенинг»; «кройцен» — сомнительная транслитерация, и алиаса «краузен» нет — по правильному слову калькулятор не ищется (C:369-378, D:2377). Минимум (безопасно, делаем сразу): добавить алиасы «краузен», «краузенинг». Максимум (после «да»): переименовать в title/seoTitle/полях; slug не трогаем.

## Волна 2 — «не заставлять знать» (главный разрыв с Brewfather)

**К9. Вода и pH: пресеты исходной воды.** Сейчас требуется 6 ионов (D:1550-1555), дефолт — молчаливая заглушка, неотличимая от «моей воды».
- Chips/select над ионными полями: «Осмос/дистиллят» (все ~0) · «Мягкая (пример)» (текущий дефолт) · «Средняя водопроводная» · «Своя» (раскрывает ручной ввод).
- Подпись у пресета-дефолта: это пример; точность — из анализа воды или отчёта водоканала.
- Ссылка на полноценный мастер водоподготовки (в редакторе рецептов) в related/nextSteps — калькулятор остаётся лёгким, не дублирует мастера.
- Приёмка: новичок без анализа воды получает честный расчёт от пресета и понимает, что улучшит точность.

**К10. Вода и pH: промывочная вода не должна незаметно разводить ppm.** `spargeWaterVolumeL:12` в advanced (D:1564, D:1592), соли делятся на `mash+sparge=27 л` (T:704-705) — пользователь видит заниженные ppm и не видит поле-причину. Решение: вынести объём промывки из advanced (или показывать строку «соли разведены на X л (затор + промывка)» в результате). Разделение дозировки затор/промывка — не в этой волне.

**К11. Праймер: пресеты целевого CO₂ по стилю.** D:1497 — голое число 2.4. Chips рядом с полем (переиспользовать диапазоны стилей из keg-carbonation, K-блок/константы ядра): «Лагер 2.4–2.6 · Эль 2.0–2.4 · Пшеничное 3.2–3.6 …» — тап подставляет середину, поле остаётся редактируемым.

**К12. IBU: выбор хмеля из каталога с автоподстановкой AA.** Переиспользовать `IngredientPicker`-паттерн строки засыпи brewhouse-efficiency (D:2190-2201); typical-альфы в каталоге есть (работы Б2). Ручной ввод AA остаётся (сорт не найден / цифра с пачки). Закрывает «частую ошибку» из C:199.

**К13. Цвет пива: выбор солода из каталога.** Тот же паттерн; цвет подставляется из базы, в разбивке вкладов вместо «Солод 1 / Солод 2» — имена солодов (D:2137).

**К14. Свежесть хмеля: непрерывный температурный фактор.** T:780 — ступенька 0.25/0.55/1/1.8 с порогами −10/4/20 °C: сдвиг 4→5 °C почти удваивает скорость деградации. Заменить на непрерывную экспоненту (Garetz), откалиброванную по текущим точкам (границы должны давать примерно те же значения — не ломать существующие расчёты сильно). Заодно в C:445 назвать коэффициент «HSI-подобным» (это не спектрофотометрический HSI A275/A325).

## Волна 3 — подача и структура (дороже, по одному калькулятору)

**К15. Настойный долив: связность режимов + многошаговый затор.**
- Минимум: перенос объёма воды и температуры между режимами «Начало затирания» → «Долив кипятка» (посчитал strike — infusion стартует от его результата); согласовать дефолты (66 vs 63 °C, D:1955-1958).
- Целевое: массив пауз (array-field, как строки хмеля в IBU): лестница температур → объём долива на каждую ступень, суммарная вода, итоговый гидромодуль. Это главный сценарий калькулятора.
- Попутно: «Термомасса котла, экв. л» → «Теплоёмкость заторника» с хелпером (D:1980-1985); «Текущая пауза» → «Температура затора» (D:1991); обратная задача «перегрел — сколько долить холодной» (mash.ts:85-124 умеет только вверх).

**К16. Бутылки и розлив: смешанная тара — либо сделать, либо вычистить.** SEO/whenToUse обещают смешанные размеры (C:351,353), ядро берёт только первый (`T:557 .find(size => size > 0)`).
- ❓ Решение владельца: (а) реализовать 2 размера тары с распределением и советом «остаток 0.3 л → +1 бутылка 0.33»; (б) не делать — вычистить обещание из C, добавить стат «Бутылок нужно» в праймер и рассмотреть слияние.
- До решения — ничего не менять.

**К17. Разбавление: тумблер «объём замерен горячим» (−4% усадка).** Свои «Частые ошибки» (C:176) называют ошибку, расчёт не закрывает. Чекбокс в fields + поправка в `computeDilutionView`.

**К18. Эффективность: подпись «Экстрактивность (PPG)» → «Потенциал (PPG)».** В РФ «экстрактивность» — % на СВ с мешка; впишут «80» и получат космос (D:2204). Опционально: принимать и % СВ с конвертацией (PPG ≈ %СВ × 0.46).

**К19. IBU: предупреждение о потолке модели.** Сумма >~100-110 IBU — Тинсет и растворимость изо-альфа-кислот ломаются; код в `ibu.ts` + перевод в coreWarningCopy.

**К20. Вода на варку: метод-специфичные дефолты.** Впитывание/потери подставлять по выбранному методу (BIAB ≠ заторник, D:1870-1872) с touched-защитой; хелпер у испарения «обычно 3–5 л/ч, уточните по своим варкам». Опционально: поле объёма заторника + предупреждение «затор не влезает».

**К21. Стартер: качество выдачи.** Плотность стартера (~1.036) и пропорция вода:DME — в статы результата, а не только в nextSteps (C:292); «Статус внесения: Мало дрожжей» → однословное «Недосев/Норма/Перебор» (`formatPitchStatus`). Ступенчатый стартер — отдельным решением (не в этом ТЗ).

**К22. Перевод доведённых калькуляторов на эталонную анатомию + верификация.** Для каждого калькулятора, прошедшего свои пункты волн 1-3: compute*View-рефактор при необходимости, конверсия значений при смене шкалы + строка в `GRAVITY_PREFERENCE_CONFIG` (P:1908; кандидаты: dilution уже частично, ibu, brewhouse-efficiency, speise), проверка commonMistakes/formula в C — затем добавить slug в `verifiedCalculatorSlugs` (C:70). Кандидат №1 на бейдж сразу после волны 1: priming-sugar (лучший из непроверенных).

## Порядок и приёмка

1. Волна 1 (К1-К7 + алиасы из К8) — один заход, после неё непроверенным можно доверять.
2. Волна 2 (К9-К14).
3. Волна 3 — по калькулятору за заход, К22 закрывает каждый.

Открытые решения владельца: **К8** (переименование «кройцен»→«краузен»), **К16** (судьба смешанной тары в «Бутылках»).

Общая приёмка каждой волны: `npm run typecheck` + vitest-сьют; живой прогон затронутых калькуляторов (SSR 200, дефолтный результат осмыслен, переключение шкал не портит значения); входящие ссылки между калькуляторами (`buildCalculatorHref`) не сломаны; для изменённых дефолтов/полей — `migrateStoredState`.
