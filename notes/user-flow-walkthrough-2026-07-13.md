# Сквозной проход user-flow (2026-07-13)

Живой прогон в браузере под **новым пользователем** (`flowtest@yandex.ru`, чистый аккаунт):
регистрация → профиль → склад → оборудование → рецепт → варка → замеры → брожение →
завершение → публикация. Каждый шаг делался руками через UI, находки подтверждены
кодом/БД.

---

## A. Баги (ломают доверие к цифрам и данным)

### A1. Дрожжи со склада НИКОГДА не списываются
Склад нормализует «1 пачка» в **граммы** (`normalized_unit = 'g'`, 22 г), а строка
рецепта хранит **`pack`**. Списание требует точного совпадения единиц:

```
apps/web/features/recipes/inventory-service.ts:186
const inventoryItemCanCoverRecipeLine = (line, item) => (
  inventorySourceMatchesRecipeLine(line, item)
  && line.amountNormalizedUnit === item.normalizedUnit   // 'pack' !== 'g' → всегда false
);
```

Итог живого прогона: солод −4 кг и хмель −20 г списались, дрожжи остались нетронуты
(2 пачки как были). Пользователь думает, что склад ведёт учёт, а по дрожжам он врёт
всегда. Матч (`match-service.ts`) для дрожжей presence-based и говорит «есть» — то есть
две подсистемы расходятся в трактовке одной строки.

### A2. Списание под партию само создаёт «нехватку» для этой же партии
Списал 4 кг Пильзнера под партию → на странице партии тут же: **«Не хватает 1 позиция»**,
в «Чего не хватает» — **«Пильзнер 3 кг · Для партии: Летний пилснер»**. То есть
потребность считается по остатку склада, а уже списанное под эту партию не
засчитывается как покрытие. Пользователь идёт «докупать» то, что уже в котле.

### A3. Дашборд и список рецептов противоречат друг другу на одних данных
Дашборд, карточка «Можно сварить сейчас»: **69 %** и рядом зелёная плашка
**«Хватает всего»**. На `/app/recipes` тот же рецепт — **«Почти хватает»** (корректно:
солода 1 кг из 4). Семантика бейджа (`recipe-match-badge.tsx:47`): «Хватает всего» =
все типы есть И количеств достаточно. На дашборде `qtyShort` теряется.

### A4. Заметки варки «пропадают» после завершения (уточнено при разборе)
Во время варки заполнил «Заметки», сохранил (`brew_batches.notes`). После «Завершить варку»
блок называется уже **«Дегустационные заметки»** — и это ТА ЖЕ колонка `notes` под другим
именем (`brew-notes.tsx:51`, тернарник по `completed`). Данные не терялись — они лежат в той
же textarea, просто заголовок врёт. Но потеря была **латентной и в одно сохранение**: любая
дегустация, записанная на завершённой партии, затирала журнал варки. Поля `tasting_notes` в
схеме не существовало вовсе.
Заодно: блок «Склад» (списано / вернуть / история движений) на завершённой партии не
рендерился совсем, хотя в device-ветке того же акта — рендерился.

### A5. Пустое время хмеля молча = полное кипячение
Поле «мин» у хмеля можно оставить пустым. IBU при этом считается как за 60 минут:

```
apps/web/features/recipes/service.ts:608
return resolveHopUseType(...) === "boil" ? boilTimeMinutes : 0;
```

Публичная страница рецепта показывает «Хмель · Кипячение · 20 г» — **без времени**, а
IBU 12 стоит. Ни ошибки, ни подсветки. Либо поле обязательное, либо дефолт видимый.

### A6. Плейсхолдер поля OG показывает FG-значение
Блок «Начальная плотность (OG)», плейсхолдер — `3.07` (это `1.012 SG`,
`brew-journal.tsx:216`). Типичное **финальное** значение в поле начальной плотности.
Для новичка это прямая подсказка ввести не то.

### A7. Вторая варка того же рецепта молча не списывает склад (найдено на проверке фиксов)
Варю рецепт второй раз, пока первая партия ещё не завершена, галку «Списать ингредиенты со
склада» ставлю. Варка создаётся, ошибки нет — а со склада **не списывается ничего** (ноль
аллокаций, ноль движений). Страница партии при этом пишет **«Ингредиенты рецепта уже списаны
со склада»**, то есть утверждает обратное.

Корень: защита от двойного списания привязана к РЕЦЕПТУ, а не к партии —
`hasBlockingConsumedAllocations(userId, recipeId)` (`features/recipes/inventory-service.ts:87`).
Consumed-аллокации первой (незавершённой) партии блокируют аллокацию второй. Но двойного
списания и так быть не может: склад уменьшается физически, вторая партия должна списывать из
остатка. Варить один рецепт дважды — совершенно нормальный сценарий.

## B. Перемудрили

### B1. Три места для одной операции «списать со склада»
1. В редакторе рецепта — секция «Ингредиенты со склада» с кнопками «Обновить наличие»
   и «Списать со склада».
2. В диалоге «Сварить» — чекбокс «Списать ингредиенты со склада».
3. На странице партии — блок «Склад» + «Вернуть на склад».

При этом секция в редакторе на живом рецепте с тремя позициями «Со склада» пишет
**«Нет готовых к списанию складских позиций»** — то есть самая заметная из трёх точек
входа не работает и молчит о причине. Списание — операция варочного дня; в редакторе
рецепта ей делать нечего.

### B2. Черновики-призраки
Заход в конструктор + ввод названия → рецепт немедленно в БД. Ушёл — остался мусорный
«Летний пилснер» с пустыми ABV/IBU/OG (у меня их два; у QA-админа на дашборде висят
«Новый рецепт 2», «Новый рецепт 4»). Удалить черновик из редактора нечем, кнопки нет.

### B3. «Завершить варку» одним кликом на 1-й день брожения
Страница говорит «День 1 из 10», кнопка «Завершить варку» — активна, без подтверждения.
Один клик → статус «Завершена», блок склада и заметок исчезает. Деструктивное по сути
действие идёт без `ConfirmActionDialog`, хотя конвенция проекта его требует.

### B4. Профиль пустой, но публичная зона большая
`/profile` = имя, валюта, единица плотности. При этом есть публичные рецепты с
авторством, «Маркет» и «Витрина мастеров». Ни аватара, ни города, ни «о себе».
Заполнять в профиле нечего, хотя флоу начинается именно с него.

## C. Чего не хватает (must have)

1. **Комментарии к рецептам.** На публичной странице есть только «Оценки» («Нельзя
   оценивать собственный рецепт»). Для раздела «Рецепты сообщества» обсуждение под
   рецептом — базовая вещь; сейчас поделиться опытом негде.
2. **Розлив / карбонизация как этап.** Из «Брожение идёт» единственный выход —
   «Завершить варку». Нет вопроса о дате розлива, объёме в бутылках, праймере, дате
   готовности. При этом генератор наклеек и `/beer/<slug>` уже есть — им неоткуда взять
   дату розлива.
3. **История варок.** После завершения партия пропадает с дашборда («Активных партий
   нет»), последней варки не видно. Свой пивной архив — главная ценность возврата.
4. **Связь партия → рецепт по факту.** Замеры (OG 11.2 при цели 11.0, сбраживание 78 %
   при цели 80 %) никуда не возвращаются: рецепт не предлагает поправить эффективность
   или FG-модель по реальным данным.

## D0. Объём варки: «пересчитать под ваше оборудование» — СДЕЛАНО

Хвост «карточка обещает под профиль (20 л), а варка берёт объём рецепта (30 л)» закрыт по
решению владельца: объём варки — **явный выбор в диалоге «Сварить»**.

- Блок «Объём варки» появляется, ТОЛЬКО если объём рецепта разошёлся с объёмом дефолтного
  профиля (>0.1 л). Совпали — диалог как был.
- Предвыбора нет: «Создать варку» неактивна, пока не выбрано «Как в рецепте · 30 л» /
  «Моё оборудование · 20 л» / «Другой» (ручной объём). Тот же блок — в ветке автоматики.
- «Моё оборудование» подставляет **профиль целиком** (объём, выпаривание, потери, впитывание
  зерна), а не только цифру объёма: иначе водный план варочного дня считался бы по чужому котлу.
- Пересчёт материализуется ОДИН раз, до сборки снапшотов (`features/brew-batches/brew-setup.ts`),
  поэтому план варочного дня, слепок состава, засыпь, водный план и списание склада считают одно
  и то же число. Ядро пересчёта — уже существовавшая `scaleRecipeToVolume` (плюс новая обёртка
  `scaleRecipeDetailToVolume` для полного DTO).

Живой прогон (рецепт 30 л, профиль «BIAB 20 л»): партия создана на 20 л, засыпь 5.7 → 3.8 кг,
слепок «Пэйл Эль 3.33 кг / Магнум 14.7 г / US-05 7.3 г», склад списан ×2/3 (−3.33 кг, −7.3 г),
профиль партии — «BIAB 20 л». Рецепт 20 л при профиле 20 л — блока нет, кнопка активна сразу.

### Эффективность: засыпь дожимается — СДЕЛАНО

Решение владельца: варка на своей эффективности должна давать **то же пиво**, а не более жидкое.
Поэтому засыпь дожимается множителем `эфф_автора / эфф_моя` (75/65 = ×1.154), а цели OG/FG/ABV
остаются авторскими — и это не «оставили как есть», а математически верно:
`og_points = Σ(вес × ppg × эфф) / объём`, и при таком дожиме сахарной массы на литр выходит
ровно столько же (живая проверка: автор 0.1250, варка 0.1250 — совпало до знака).

Дожим применяется ТОЛЬКО к тому, на что действует эффективность затирания (солод, зерновые
добавки — тот же предикат `fermentableAppliesMashEfficiency`, что и в движке OG). Сахар и
экстракт усваиваются полностью → только объём; хмель и дрожжи — только объём.

Единый множитель знают ТРИ потребителя, иначе интерфейс снова начнёт врать:
- слепок партии (`brew-setup.ts` → `scaleRecipeDetailForBrew`);
- списание склада (`inventory-service.ts`, опция `efficiencyFactor` + пер-строчный резолвер:
  техданные каталога догружаются одним запросом и только когда дожим есть);
- матч «сколько нужно» (`match-service.ts`: у партии — из её плана, вне партии — из дефолтного
  профиля; иначе карточка обещала бы «хватает», а варка требовала больше солода).

Обе эффективности (своя и авторская) фиксируются в плане партии
(`brew_plan_snapshot.recipe.efficiencyPct` / `recipeEfficiencyPct`) — списание и матч повторяют
множитель по ним, а не по живому рецепту (его могли поправить после старта). Старые партии полей
не имеют → дожим 1, прежнее поведение.

Живой прогон (рецепт 30 л/75%, профиль «BIAB 20 л»/65%): Пэйл Эль 5 → **3.85 кг**, Мюнхенский
0.4 → 307.7 г, Карамель 0.3 → 230.8 г (×0.769), а Цитра 125 → 83.3 г, Магнум 22 → 14.7 г,
US-05 11 → 7.3 г (×0.667, без дожима). Засыпь в плане 5.7 → 4.38 кг. Цель OG 1.044 — авторская.
Фантомной нехватки нет.

Цвет при дожиме чуть темнее (солода на литр больше) — осознанный побочный эффект, цель SRM в
слепке не хранится.

## D. Хвосты, вскрытые при починке (не закрыты)

1. **Матч не ведёт бюджет складской позиции.** Если рецепт использует одну и ту же позицию склада
   в двух строках, каждая строка видит ПОЛНЫЙ остаток — сумма потребностей не сверяется с
   остатком. `matchLineAgainstInventory` считает строки независимо против неизменяемого индекса.
   Это дефект движка матча, старше наших правок; списание при этом честно упрётся в остаток.
2. **Загрузка фото создаёт черновик мимо гейта.** `recipe-images-section.tsx` создаёт рецепт своим
   экшеном; порог «рецепт стоит сохранять» его не покрывает.
3. **Прод-данные перед выкатом.** Могут остаться `consumed`-аллокации с `brew_batch_id IS NULL`
   (следы снесённой кнопки списания из редактора) — разово перевести в `released`.
4. **`ON DELETE SET NULL` на `brew_batches.recipe_id`.** Удаление рецепта осиротит партии (снапшот
   остаётся, связь и «Вернуть на склад» теряются). Подтверждение теперь об этом предупреждает, но
   сама модель — под вопросом.
5. **Мобильные кнопки редактора без подписей** (`recipe-actions-menu.tsx`, `hidden sm:inline`) —
   на телефоне остаются голые иконки; тултипы на тач-устройствах не работают.
6. **Блок «Склад» на странице партии пишет «Ингредиент» вместо названия** (найдено при живом
   прогоне пересчёта объёма). `loadInventoryNames` (`features/brew-batches/inventory.ts:173`)
   читает ТОЛЬКО `user_ingredients.ingredient_display_name_snapshot` — без фолбэка на связанный
   каталог. У позиций с пустым снапшотом (сидовые/импортированные) в списании вместо «Пэйл Эль»
   стоит «Ингредиент», хотя на всех остальных экранах имя резолвится (`inventory/service.ts:306`
   берёт живой каталог, снапшот — только фолбэк). UI, добавляющий позицию со склада, снапшот
   пишет, поэтому в проде дефект видят не все. Фикс — тот же порядок резолва, что в inventory.

## Что работает хорошо

- OTP-вход, автосоздание аккаунта — 3 клика, без формы регистрации.
- Пикер ингредиентов: категория → источник (склад/каталог/свой) → параметры, с остатком
  склада прямо в строке.
- Живой пересчёт статистики и шкалы BJCP с вердиктом «В стиле / Ниже».
- Варочный день: шаги с таймерами, «Сейчас» + «Следом», прогресс 0/8.
- Гейт публикации честно перечисляет, чего не хватает (описание), и не даёт опубликовать.
- Мобильная вёрстка партии — без горизонтального overflow.
