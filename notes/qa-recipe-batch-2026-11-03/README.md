### B01 Потерянный ответ списания не восстанавливается повтором

**Предусловия:** активная партия с достаточным складом, открыт диалог списания.

**Шаги:**

1. Нажать «Списать N позиций».
2. Доставить POST до сервера и дождаться ответа сервера, но оборвать доставку ответа браузеру. В Playwright использованы `route.fetch()` и последующий `route.abort("failed")` для Server Action списания.
3. После сообщения «Не удалось списать ингредиенты» восстановить сеть и повторить списание.
4. Закрыть диалог.

**Ожидается:** повтор сверяет подтверждённое состояние партии, закрывает диалог и показывает списанные ингредиенты и действие возврата. Если операция уже выполнена, дальнейшее списание недоступно.

**Фактически:** повтор показывает красное «По этой партии ингредиенты уже списаны со склада». Диалог сохраняет активную кнопку списания. После закрытия страница продолжает показывать, что ингредиенты не списывались, предлагает списание и не показывает возврат. Перезагрузка страницы восстанавливает правильное состояние.

**Влияние:** пользователь не понимает результат операции и не видит возврат без reload. Повторного уменьшения остатков не обнаружено. Такой же устаревший экран сохраняет проигравшая вкладка при одновременном списании одной партии.

**Повторяемость:** основной полный рецепт, независимый рецепт с одним ингредиентом, столкновение двух вкладок — проблема подтверждена во всех трёх вариантах. В независимом воспроизведении было 10 г, после потерянного ответа 4 г, после повтора по-прежнему 4 г; кнопок возврата на устаревшем экране — 0.

**Доказательства:** [диалог после повтора](screenshots/13-consume-retry-stuck.png), [устаревшая страница](screenshots/14-stale-batch-after-consume.png), [правильное состояние после reload](screenshots/15-reload-recovers-consumed-state.png), [проигравшая вкладка](screenshots/18-two-tabs-consume-a.png), [независимое воспроизведение](screenshots/B01-independent-reproduction.png), [результаты проверки БД](defect-reproduction.json).

**Место причины:** [обработка ALREADY_CONSUMED](../../apps/web/app/(app)/app/brew-batches/[id]/actions.ts) возвращает ошибку без актуального представления и повторной валидации страницы; [диалог списания](../../apps/web/features/brew-batches/components/consume-preview-dialog.tsx) при `!result.ok` только сохраняет текст ошибки. В текущем коде это строки 344–345 и 258–264 соответственно.

**Критерий исправления:** после потерянного ответа и после конфликта двух вкладок повтор получает актуальное состояние, запрещает лишнее списание и показывает возврат. В БД остаётся один фактический расход.

### B02 Отмена партии при отказе сети не объясняет результат

**Предусловия:** запланированная партия, открыто меню «Действия с партией» → «Отменить партию».

**Шаги:**

1. Отключить сеть браузерного контекста после открытия подтверждения.
2. Нажать красную кнопку «Отменить партию».
3. Дождаться неуспешного POST и завершения индикатора выполнения.

**Ожидается:** внутри подтверждения появляется понятная ошибка соединения; пользователь знает, что отмена не подтверждена, и может повторить её после восстановления связи.

**Фактически:** диалог остаётся без сообщения об ошибке, кнопка снова активна. Браузер получает необработанный `Failed to fetch`. В БД партия остаётся `planned`. Повтор после восстановления сети работает.

**Повторяемость:** 2/2 на двух независимых аккаунтах. При независимом повторе: число сообщений `role=alert` в диалоге — 0, событие `pageerror` — `Failed to fetch`, статус партии — `planned`.

**Влияние:** пользователь не получает объяснения и не знает, выполнена ли отмена. Потери складских данных в этом сценарии нет.

**Доказательства:** [диалог после сетевой ошибки](screenshots/23-cancel-offline-no-feedback.png), [независимое воспроизведение](screenshots/B02-independent-reproduction.png), [событие браузера](browser-events.json), [проверка статуса в БД](defect-reproduction.json).

**Место причины:** [BatchMenu.apply](../../apps/web/features/brew-batches/components/batch-menu.tsx) на строках 57–70 обрабатывает серверный `{ok:false}`, но сетевое исключение из `await setBrewBatchStatusAction(...)` проходит через `finally` без `catch`. Диалог подтверждения сам исключение не перехватывает.

**Критерий исправления:** сетевое исключение отображается внутри диалога, не порождает необработанное событие, повтор остаётся доступным. Потеря ответа после фактического изменения статуса должна разрешаться сверкой с сервером.

### T01 Браузерные регрессии расходятся с текущими подписями

Штатный [recovery-browser.integration.test.ts](../../apps/web/integration/recovery-browser.integration.test.ts) завершился результатом **3 passed / 4 failed**. Разбор показал несовпадение текстовых ожиданий с текущим интерфейсом.

| В тесте | В текущем интерфейсе |
|---|---|
| Не удалось загрузить объём и оборудование | Не удалось загрузить объёмы и параметры оборудования |
| Не удалось рассчитать подготовку | Не удалось рассчитать параметры варки |
| пересчитаны на 10 л | пересчитано на 10 л |
| Запас в 2 лотах | Запас в 2 партиях закупки |
| Количество использованного | Сколько использовали |

В отдельной [копии тестов](tools/recovery-current.integration.test.ts) обновлены только эти ожидания и пути импортов для запуска из каталога отчёта. Копия прошла **7/7**. Эти четыре падения не являются четырьмя продуктовыми багами.

**Влияние:** штатный набор восстановления после сетевых отказов остаётся красным из-за подписей и не даёт чистого сигнала о новых регрессиях.

**Критерий исправления:** привести исходный набор к текущему интерфейсу и сохранить проверки пользовательского поведения, числа списаний, восстановления ввода и прав доступа. [Исходный лог](tools/browser-baseline.log), [повтор с актуальными подписями](tools/browser-current-labels.log).

## Проверенный путь и баланс

Тестовый рецепт: 20 л, эффективность 70%, 4 кг Best Pale Ale Malt, два внесения Cascade по 20 г, одна пачка US-05 11,5 г. Оборудование: 10 л с той же эффективностью. Данные подготовлены сервисами приложения; через UI проверены редактирование и сохранение названия, повторное открытие, переключение объёма, создание партий и все последующие действия.

В партии 10 л снимок содержит 2 кг солода, два внесения хмеля по 10 г и 5,75 г дрожжей. Интерфейс округляет дрожжи до 5,8 г, фактический расход — 5,75 г. Исходный рецепт остаётся на 20 л. Цели исходника и партии согласованы: OG 1.043, FG 1.009, ABV 4,46% до округления для UI.

| Позиция | До проверок | После одного списания на 10 л | После всех возвратов |
|---|---:|---:|---:|
| Солод | 5000 г | 3000 г | 5000 г |
| Хмель, первый лот | 12 г | 0 г | 12 г |
| Хмель, второй лот | 10 г | 2 г | 10 г |
| Дрожжи | 23 г, 2 пачки | 17,25 г, 1,5 пачки | 23 г, 2 пачки |

Для партии 20 л с потребностью 40 г хмеля интерфейс заранее показал дефицит 18 г и порядок распределения между внесениями. Списаны только доступные 22 г; после отмены и возврата оба лота восстановились. Солод и дрожжи также вернулись полностью.

Основной аккаунт создал три партии: обычную на 10 л, партию на 10 л с потерей ответа и повтором создания, партию на 20 л с дефицитом. Все три в конце отменены. В 36 складских транзакциях суммарное изменение каждого остатка равно нулю. Списания и возвраты после повторов и гонок не дублируются. Это проверено отдельным [контролем баланса](balance-verification.json) по [итоговому снимку](30-final-state.json).

Дополнительно проверены два одновременных возврата, запрет списания после отмены в другой вкладке, повторный перевод отменённой партии в план, закрытие подтверждения без отмены и повторная отмена. Визуально проверены основные диалоги на 1280×900 и диалог списания на 390×844: [устойчивое мобильное состояние](screenshots/24-mobile-consume-settled.png). Это проверка Chromium с viewport, без проверки физической клавиатуры телефона.

## Стенд и воспроизведение

Ubuntu 24.04, Node.js 24.13.1, PostgreSQL 16.15, Next.js 15.5.28 в dev-режиме, Playwright 1.61.1, Chromium 149.0.7827.55. Локаль ru-RU, часовой пояс Europe/Moscow. Приложение: `127.0.0.1:3000`. Изолированная БД: `nb_qa_20261103` на `127.0.0.1:55434`.

Docker Desktop был недоступен. PostgreSQL извлечён из пакетов Ubuntu во временный каталог `/tmp/nb-qa-postgres-20261103`, без системной установки. Миграции и 1403 позиции каталога загружены в отдельную QA-базу. Основная база `nb` не использовалась. Автологин администратора отключён; браузеры использовали реальные сессии обычных QA-пользователей. Доставка писем и регистрация через UI в этом проходе не проверялись.

Повтор при поднятых QA PostgreSQL и приложении, из корня репозитория:

```bash
source notes/qa-recipe-batch-2026-11-03/tools/qa-env.sh
TSX_TSCONFIG_PATH=apps/web/tsconfig.json node \
  --import ./notes/qa-recipe-batch-2026-11-03/tools/qa-loader.mjs \
  --import tsx \
  notes/qa-recipe-batch-2026-11-03/tools/reproduce-bugs.mts

node node_modules/vitest/vitest.mjs run \
  --config notes/qa-recipe-batch-2026-11-03/tools/vitest.config.mts

python3 notes/qa-recipe-batch-2026-11-03/tools/verify-artifacts.py
```

Для штатного PostgreSQL-набора из `apps/web`: `node ../../node_modules/vitest/vitest.mjs run --config integration/vitest.config.ts integration/user-flow.integration.test.ts`. Для исходного браузерного набора заменить имя на `integration/recovery-browser.integration.test.ts`.

`qa-loader.mjs` только для запуска сервисов вне Next.js заменяет маркер `server-only` пустым модулем, как штатный `vitest.setup.ts`. Браузерное приложение работает с обычным кодом Next.js. `reproduce-bugs.mts` сам создаёт и удаляет отдельный аккаунт и требует точного адреса изолированной QA-базы. Локальный файл с cookies основной браузерной сессии хранился в `/tmp` и не включён в отчёт.

После проверки Chromium, веб-сервер и временный PostgreSQL остановлены. Созданные аккаунты удалены, файл с тестовой сессией удалён. Снимки, скриншоты, логи и [машиночитаемая сводка](results.json) сохранены в этом каталоге.
