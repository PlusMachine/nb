## Воспроизведение и повторные проверки

### B03 — неверное число заменяется рабочим значением

Изменить рецепт, явно передав объём 0, затем NaN. Исходный сервис принимал ввод и подставлял 20 л. В исследовательских циклах N01/N02 проверка останавливалась на первом принятом значении; отрицательные числа и Infinity по тому запуску не объявлялись воспроизведёнными.

После исправления PostgreSQL-тесты отдельно перебирают 0, −1, NaN, ±Infinity и переполнение; исходные 30 л остаются. Время кипячения 0, −1, 1,5 и Infinity отклоняется, прежние 90 минут целы. Отсутствующие поля создания получают 20 л/60 минут, отсутствующие поля частичного обновления не меняют запись.

Доказательства: [N01/N02 до исправления](db-exploration.json), [регрессии сохранения](../../apps/web/integration/recipe-persistence.integration.test.ts).

### B04 — положительный объём становится нулём

Создать рецепт с объёмом 0,0004 л. Первичная проверка получила введённый и нормализованный объём 0. Теперь такой ввод отклоняется до вставки, UI получает ошибку поля.

В соседнем коде нормализации обнаружено повторное округление уже нормализованной массы при возврате к кг. Оно убрано; PostgreSQL подтверждает 40 мг = 0,04 г = 0,00004 кг при создании и смене единиц. Модульно проверен также 1 мг. Ранний отдельный зонд массы был прерван отказом диска; вывод о массе опирается на анализ кода и последующие проверки.

Доказательства: [N03](db-exploration.json), [единицы](../../apps/web/tests/recipe-units.test.ts), [масса в PostgreSQL](../../apps/web/integration/recipe-persistence.integration.test.ts).

### B05 — одинаковый ключ теряет внесение

Отправить две строки одного persistentKey, 5 г и 7 г. Сервер отвечал успешно, оставалось только 7 г. Теперь одинаковые непустые ключи отклоняются при создании и изменении; прежняя строка 20 г остаётся. Отсутствующие ключи разрешены: их генерирует сервер.

Доказательства: [N07 до исправления](db-exploration.json), [атомарная регрессия](../../apps/web/integration/recipe-persistence.integration.test.ts).

### B06 — две вкладки теряют подтверждённые правки

Открыть рецепт в двух вкладках. В первой изменить название и дождаться «Сохранено». Во второй изменить только объём на 21 л. Вторая вкладка раньше отправляла полный старый payload и возвращала старое название в БД.

Редактор теперь передаёт editorUpdatedAt — ревизию последнего подтверждённого сохранения содержимого. Сервис проверяет её после блокировки своей строки; при несовпадении не пишет. Во второй вкладке видна ошибка, локальные 21 л остаются; название первой вкладки и 30 л в БД целы. После копирования своих правок и reload пользователь сохраняет их поверх актуального документа. Автоматическое слияние полей не реализовано.

Общая дата updatedAt меняется также при работе с фотографиями и агрегатами. Поэтому для защиты редактора введена отдельная editorUpdatedAt. Она меняется при записи содержимого, а обновление одной обложки не вызывает ложного конфликта. Проверка этой соседней операции первоначально получила RECIPE_CONFLICT, после чего защита уточнена: [диагностика](tools/editor-metadata-before-refinement.log).

Доказательства: [первичный UI](ui-exploration.json), [до исправления](screenshots/P05-first-tab.png), [конфликт после исправления](screenshots/P05-retest-conflict-local-input.png). При одновременной записи с одной ревизией PostgreSQL подтверждает ровно один успех.

### B07 — дубль после потерянного ответа создания

В новом редакторе ввести название. Доставить Server Action через route.fetch(), проверить сообщение «Рецепт создан.», затем оборвать ответ через route.abort("failed"). БД уже содержит одну новую запись. Нажать «Повторить»: первоначальный тест получил две записи с одинаковым названием и разными ID.

Перехватывается именно сохранение. Предварительный расчёт не прерывается; ранний неоднозначный исследовательский зонд не используется как доказательство.

Редактор теперь сохраняет UUID попытки и исходные payload/signature до разрешения неизвестного результата. UUID становится ID новой строки; первичный ключ обеспечивает атомарность повторов. Сервис возвращает существующий рецепт только владельцу и не переписывает дальнейшие изменения. Если во время отказа изменён ввод, сначала разрешается создание, затем очередной update сохраняет новые правки. Для дедупликации создания миграция БД не нужна; отдельная ревизия B06 добавляет миграцию 0072.

Доказательства: [до исправления: две записи](tools/lost-create-before-fix.log), [экран дубля](screenshots/P03-after-retry-before-fix.png), [UI-регрессии](../../apps/web/integration/recipe-persistence-browser.integration.test.ts). PostgreSQL дополнительно проверяет три конкурентных запроса с одним ключом, сохранность позднейших правок, чужой ключ и неверный формат ключа.

Идентификатор незавершённой попытки хранится в памяти редактора. Закрытие/перезагрузка вкладки с неизвестным результатом до восстановления не покрыты этим исправлением. После успешного повтора проверяется сохранённый URL продолжения мастера и reload.

### B08 — обновление данных стирает введённые объёмы

На странице брожения ввести «Разлито» = 18 л, не сохранять. Из другой сессии обновить объём до кипячения, затем в первой вкладке добавить задачу. Обновление страницы после сохранения задачи приносит новые серверные props. До исправления поле «Разлито» становилось пустым.

При первичном разборе также наблюдались две формы объёмов после обновления: блоки объёмов и задач использовали одинаковый React key. Их ключи теперь различны. После отдельного исправления ключей повторный тест всё ещё получил пустое поле вместо 18 — это самостоятельное подтверждение потери ввода. Форма теперь сохраняет изменённые локальные поля и принимает серверные изменения только для нетронутых.

Доказательства: [18 → пусто до исправления формы](tools/volume-input-before-form-fix.log), [ранняя диагностика дублирования](tools/volume-input-before-fix.log), [две целевые регрессии после исправления](tools/volume-form-after-fix.log). В этом диагностическом логе общий сценарий ещё требовал ожидания гидратации кнопки; обе отдельные проверки B08/B09 прошли. В финальном прогоне прошли и все три сценария этого файла. Итоговый общий прогон вынесен в таблицу проверок.

### B09 — отдельное поле затирает чужой замер

Открыть форму, когда «До кипячения» = 24 л. В ней изменить только «Разлито» на 18 л. Из второй сессии записать «До кипячения» = 28 л. Сохранить первую форму. Прежде она отправляла все поля, включая устаревшие 24 л: PostgreSQL получил 24 вместо подтверждённых 28.

Теперь отправляется только изменённое поле «Разлито». Сервер уже объединяет частичный patch под блокировкой своей строки; 28 л сохраняются вместе с новыми 18 л. Очистка явно изменённого поля по-прежнему отправляет null. Ошибка сохранения не снимает отметку локальных изменений.

Доказательства: [PostgreSQL: ожидались 28, сохранены 24](tools/volume-concurrency-before-fix.log), [браузерная регрессия](../../apps/web/integration/batch-records-browser.integration.test.ts), [исправленная форма](../../apps/web/features/brew-batches/components/batch-volumes.tsx). Два одновременных изменения одного и того же поля этим исправлением не получают отдельного разрешения конфликта.
