# QA NB: продолжение — сохранение, обмен рецептами и фотографии

3 ноября 2026 года, Europe/Moscow. Следующий проход сохранённого [плана](../../docs/qa-test-plan.md), после [B01–B09](../qa-recipe-persistence-2026-11-03/README.md). База исходного кода — 21831fa с ранее внесёнными исправлениями; изменения этого прохода включены в общий снимок исходников.

## Найденные ошибки

| ID / приоритет | Воспроизведение и результат до исправления | Исправление и повторная проверка |
|---|---|---|
| B10 / P2 | В редакторе изменить название существующего рецепта. После успешного ответа Server Action на стороне сервера оборвать доставку ответа вкладке. БД уже содержит правку, но «Повторить» получает «Рецепт изменён в другой вкладке»; новые правки тоже блокируются. Оба браузерных варианта воспроизведены | UUID операции сохраняется до получения подтверждения; сервер под блокировкой строки узнаёт повтор последнего сохранения и возвращает его без повторной записи. Сначала согласуется прежний запрос, затем отправляются новые локальные правки. Проверены простой повтор, более новый ввод, reload, три параллельных повтора, права владельца и сохранение настоящих конфликтов |
| B11 / P1 | Гость загружает публичное фото, модератор скрывает рецепт: прямой HTTP уже возвращает 404, но повторный fetch в том же Chromium получает 200 из кэша. Публичный ответ разрешал immutable-кэш на год, приватный — на час | Все варианты фото получают private, no-store. Генерация ссылок объединена и получила ?v=2, чтобы обновлённый UI обходил прежние неизменяемые ответы. Проверены скрытие после просмотра и выход владельца после просмотра приватного фото. Ранее сохранённые пользователем копии удалить удалённо невозможно; старые ссылки вне обновлённого UI могут оставаться в прежнем кэше |
| B12 / P2 | Авторизованный POST загрузки с повреждённым multipart body возвращает 500 и исключение парсера | Ошибка чтения FormData перехватывается, клиент получает JSON с ok:false и HTTP 400. Реальный HTTP-повтор проходит |
| B13 / P2 | Примеры APA, Dubbel и NEIPA: Brewfather → сохранение в PostgreSQL → BeerXML → повторное сохранение. У ряда ингредиентов timeOffset=60 превращается в null. В расширение NB переносились единица и этап, но время отсутствовало | NB_INGREDIENT экспортирует и восстанавливает timeOffset, включая null и 0; старые файлы сохраняют прежнее чтение стандартных полей. Все шесть файлов-примеров проходят сравнение проверяемых полей после повторного импорта |

[До исправления B10](tools/lost-update-before.log), [B11/B12](tools/media-before.log), [B13](tools/server-tests-after.log). В последнем логе сервисные повторы B10 уже исправлены; три падения относятся к времени ингредиентов при обмене файлами.

В B10 ответ формируется из снимка рецепта и ингредиентов, прочитанного до снятия блокировки транзакции. Это не даёт более поздней конкурентной записи подменить ревизию подтверждаемой операции. Повтор старой операции после последующего сохранения остаётся конфликтом; запись из старой вкладки не применяется автоматически. Идентификатор попытки в браузере хранится в памяти вкладки; восстановление несогласованного запроса после её полного закрытия не реализовано.

[Общий PostgreSQL/Chromium-прогон](tools/all-integration.log), [целевые повторы](tools/targeted-after.log), [импорт и изображения после исправления](tools/interop-media-after.log), [скачивание через UI](tools/transfer-browser.log), [TypeScript web](tools/types-web.log), [TypeScript db](tools/types-db.log).

Исправления автоматизации отделены от продуктовых ошибок: API Brewfather-парсера принимает объект после JSON.parse, а не строку JSON; ошибка построения импортируемого набора может быть синхронной. Ожидания хука теперь проверяют согласование старой попытки перед новым вводом. Неверные ранние ожидания и первый TypeScript-диагноз сохранены в диагностических логах; итоговые проверки используют исправленные ожидания.

Стенд: Node.js 24.13.1, Next.js 15.5.28 dev с отдельным NEXT_DIST_DIR, PostgreSQL 16 в Docker nb-qa-next-20261103, 127.0.0.1:55434, данные в tmpfs. База nb_qa_20261103, отдельные QA-аккаунты. Локальные фотографии — отдельный STORAGE_BUCKET=qa-interop-20261103. Обычный контейнер nb-postgres и база nb используются только для штатного применения миграции после резервного копирования, без тестовых фикстур.

Для повторения создать такой же временный контейнер с --tmpfs /var/lib/postgresql/data:rw; дождаться pg_isready. Подключить [qa-env.sh](../qa-recipe-batch-2026-11-03/tools/qa-env.sh), установить STORAGE_PROVIDER=mock и STORAGE_BUCKET=qa-interop-20261103, выполнить миграции и seed, запустить Next из apps/web. Затем из apps/web: node ../../node_modules/vitest/vitest.mjs run --config integration/vitest.config.ts. Модульные тесты запускаются там же с APP_URL=http://localhost:3000; хук — через Playwright recipe-autosave.spec.ts, проект laptop. Все эти команды должны использовать QA DATABASE_URL. Полные миграции и данные для обычного запуска проекта не сбрасывать.

## Миграция и границы прохода

[0073_recipe_editor_save_key.sql](../../packages/db/drizzle/0073_recipe_editor_save_key.sql) добавляет nullable UUID последней операции редактора. В других окружениях перед запуском обновлённого приложения требуется штатный db:migrate; текущая локальная база уже обновлена. Резервная копия обычной локальной базы создана и проверена через pg_restore --list; [метаданные копии](local-db-backup.json). Миграция применена к обычной локальной базе nb в Docker после проверенного dump. До и после совпадают количества и контрольные суммы строк в пяти таблицах: 32 пользователя, 126 рецептов, 36 партий, 103 складские позиции, 1403 записи каталога. Все прежние поля сохранены; новый UUID пуст у существующих записей. [Результат применения](local-docker-update.json). Повтор мигратора на QA завершился успешно.

Ограничения: Next dev, Chromium, локальное файловое хранилище. Другие движки, реальный мобильный файловый менеджер, S3/CDN, production/PWA, вся матрица версий/публикации, большие библиотеки и произвольные внешние профили, этикетки PDF/PNG и печать этим проходом не подтверждены. Полное восстановление рабочей БД из dump и аппаратные BrewForge/датчики ещё впереди. no-store увеличивает повторную загрузку фотографий; оценка трафика и производительности остаётся в нагрузочном проходе.

Следующий проход по плану — production/PWA: установка, офлайн-экран, возврат сети, обновление вкладки, смена аккаунта и личные кэши. Полная готовность всех 16 векторов к выпуску пока не заявляется.
