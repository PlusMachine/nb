## TL;DR

Защита в приложении есть, но она **лоскутная** и в трёх местах пробита насквозь на системном уровне — из-за этого даже те лимиты, что стоят, обходятся простым скриптом. Плюс на **основных сущностях (рецепты, склад, оборудование, партии) квот нет вообще**, хотя рабочий паттерн квот в проекте уже есть (фото, витрина мастера).

Приоритеты: **P0** — системные дыры, из-за которых остальные лимиты не работают. **P1** — квоты на сущности и дорогие незащищённые эндпоинты. **P2** — точечное упрочнение.

## P0 — системные дыры (чинить первыми, иначе всё остальное бессмысленно)

### P0-1. Гонка (TOCTOU) в основном лимитере — обходится параллелью
`packages/auth/src/service.ts:89` `assertRateLimit`: делает `SELECT count` → потом отдельным запросом `UPDATE SET count = row.count + 1`. Между чтением и записью нет атомарности и нет блокировки строки.

- При `count=4, limit=5` сто **параллельных** запросов все читают `count=4`, все проходят проверку `4 < 5`, все пишут `count=5`. Прошло 100 вместо 1.
- Это ломает **все** персистентные лимиты разом: SMS (слив денег), клоны рецептов, загрузки, предложения ингредиентов, вход.
- Последовательный флуд лимитер держит; параллельный (`Promise.all` на 100 запросов) — нет.

**Фикс:** один атомарный statement. Инкремент внутри `INSERT ... ON CONFLICT DO UPDATE SET count = auth_rate_limits.count + 1` с обнулением по `reset_at` в том же запросе (через `CASE`/`WHERE`), и `RETURNING count` для проверки лимита. Либо `SELECT ... FOR UPDATE` в транзакции.

### P0-2. Per-IP лимиты держатся на подделываемом `X-Forwarded-For`
`apps/web/lib/anti-abuse.ts:76` `clientIpFrom` берёт **первый** элемент `x-forwarded-for` (или `x-real-ip`). Клиент шлёт `X-Forwarded-For: <случайный IP>` на каждый запрос → каждый запрос = «новый IP» → все per-IP лимиты (auth send/attempt, наклейки, фидбек) обходятся полностью.

- `docs/deploy-checklist.md:12` это **уже осознаёт**: «без корректного заголовка все IP схлопнутся в один ключ». Но защита односторонняя — чеклист про «прокси должен *проставить* заголовок», а не про «прокси должен *перезаписать* клиентский».
- В репозитории **нет** конфига реверс-прокси (только Postgres/mailpit/mosquitto в `docker-compose.yml`). Значит на сегодня доверенной границы, которая санирует заголовок, нет.

**Фикс:** не доверять первому слева. Знать число доверенных прокси-хопов (env, напр. `TRUSTED_PROXY_HOPS=1`) и брать IP на этой позиции **справа**. Плюс в `deploy-checklist` явно: edge обязан **перезаписывать** входящий `X-Forwarded-For`, а не дополнять. Без прокси в проде (нельзя) per-IP защиты нет вообще.

### P0-3. In-memory лимитеры (наклейки, фидбек) растут без границы → OOM
`apps/web/features/labels/rate-limit.ts` и `apps/web/features/feedback/rate-limit.ts` — `Map<ip, number[]>`, ключ — тот же подделываемый IP (P0-2), записи **никогда не вытесняются**.

- Скрипт крутит `X-Forwarded-For` по кругу → в Map попадает новый ключ на каждый IP → Map растёт неограниченно → OOM процесса. Это буквально «положить сайт» одним циклом.
- Плюс лимитер сбрасывается на каждый редеплой и не разделяется между инстансами (комментарии в коде это признают: «пока рантайм один монолит»).

**Фикс:** перенести оба на персистентный `assertRateLimit` (после P0-1 он атомарен и в БД). Если оставлять in-memory — обязательно вытеснение по размеру (LRU-кап) и периодический sweep протухших ключей.

**Фикс (паттерн в проекте уже есть):**
- Повесить `assertRateLimit(user.id, "recipe_create", N, 3600)` на все пути создания рецептов/партий/профилей/склада — по образцу `recipe-image-upload`.
- Ввести квоты-константы рядом с существующими (`RECIPE_IMAGE_MAX_COUNT=8`, `MASTER_ITEM_MAX_COUNT=12`): напр. max рецептов / профилей оборудования / позиций склада на юзера. Проверка `count()` перед вставкой → понятная ошибка. Числа согласовать с владельцем (черновики тоже считать).
- Закрыть **обходные пути**: `createRecipeCustomIngredientAction`, `addCustomIngredientAction`, `proposeRecipeIngredientAction` должны звать тот же `assertRateLimit`, что и их «главные» аналоги (сейчас лимит стоит на одном входе, а сущность создаётся с трёх).
- Импорт: ограничить размер входной строки/JSON **до** парсинга (напр. ≤256 КБ).

### P1-2. Дорогие эндпоинты без лимита
- `/api/labels/[recipeId]` (`app/api/labels/[recipeId]/route.ts`) — растеризация resvg + sharp на каждый вызов, требует логин, но **лимита ноль**. Один аккаунт в цикле жжёт CPU. → `assertRateLimit(user.id, "label_render", N, ...)`.
- `/api/labels/custom` — anon, самая тяжёлая CPU-операция в приложении, защита только Map-лимитером из P0-3.
- `/api/ingredients/search`, `/api/ingredients/picker-quick-start` — **anon, лимита нет**, каждый запрос грузит весь каталог и ранжирует в памяти. 5-мин кеш гасит БД, но не CPU ранжирования. → лёгкий per-IP лимит + короткий кеш ответа.

### P1-3. Пул БД без предохранителей
`packages/db/src/client.ts:48` — `new Pool({ connectionString })` без `max`, без `statement_timeout`, без `connectionTimeoutMillis`. Дефолт pg — `max=10`, запросы без таймаута.

- Один тяжёлый/зависший запрос, помноженный на 10 параллельных, занимает весь пул → сайт «лёг» без всякого хитрого эксплойта.

**Фикс:** задать `statement_timeout` (напр. 10–15 с), осмысленный `max`, `connectionTimeoutMillis`. Дёшево, снимает целый класс read-DoS.

## P2 — точечное упрочнение

- **Тело запроса без лимита размера:** 23 роута читают `request.json()`/`formData()` без проверки размера (только `firmware/download` проверяет). Задать `serverActions.bodySizeLimit` в `next.config` и/или проверять `Content-Length` до чтения на самых открытых роутах.
- **`/api/firmware/manifest` + `/download/[version]`:** любой запрос с мусорным `Authorization: Bearer` заставляет `findDeviceByToken` делать SELECT в Postgres до отказа (amplification), лимита нет. → лёгкий per-IP лимит перед обращением к БД.
- **`/api/devices/claim`:** залогиненный юзер может брутфорсить `claimCode` без лимита (перехват пейринга). → `assertRateLimit` на попытки claim.
- **`/api/notifications/test`:** жжёт push/VAPID-квоту без лимита (самому себе, но всё же). → лимит.
- **`telemetry/history`:** до 20 000 строк на запрос без per-user лимита (в рамках своих устройств). → per-user лимит.
- **Капча fail-open:** `verifyCaptchaHook` при недоступности валидатора Яндекса пропускает (fail-open) — осознанно, но означает «валидатор лёг = капча выключена». Учесть в мониторинге.
- **Капча не настроена:** по памяти ключи Yandex SmartCaptcha **не созданы**. В проде без секрета `verifyCaptchaHook` = fail-closed (вход блокируется целиком — тоже плохо), в dev = fail-open. Перед продом ключи создать обязательно, иначе либо вход закрыт, либо бота на auth ничто не держит.
