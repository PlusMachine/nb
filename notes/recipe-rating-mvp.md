## Решение (итог обсуждения)

Проблема двоякая: (а) сортировка «По рейтингу» — голый `rating_avg DESC`, из-за чего
рецепт с одной оценкой 5.0 стоит выше рецепта с 4.8×120; (б) на старте проекта
данных мало, и социальные счётчики/сорты выдают пустоту сайта.

Принято:

1. **Механизмы ввода не трогаем** — форма оценки (1–5 звёзд + текст) и «Сохранить»
   остаются как есть с первого дня. Нулевые счётчики на витрине уже не показываются
   (`RecipeRatingOrNew`: рейтинг → бейдж «Новый» → ничего), это сохраняем.
2. **Ранжирование по рейтингу — байесовское среднее** (формула IMDb): скор для
   ORDER BY, наружу продолжаем показывать честное среднее + `(N)`.
3. **Сорты «По рейтингу» и «Популярные» — count-conditional**: опции появляются в
   селекте, только когда данных достаточно. URL-контракт не меняется — прямые ссылки
   (`?sort=popular` со страниц стилей) продолжают работать всегда.
4. **«Выбор редакции»** — кураторская метка как замена социального доказательства
   на старте (роль editor+ уже есть).
5. **Вне скоупа (этап 2, когда появится трафик):** счётчик «сварено N раз»,
   «оценка после варки» (verified), затухание популярности по времени / trending,
   просмотры, комбинированный скор для «Рекомендуемых». Правило переходного периода:
   ничего нового поверх голого `rating_avg` не строить.

## П1. Байесовский скор рейтинга

**Формула:** `bayes = (C·m + rating_avg·rating_count) / (C + rating_count)`,
где `m = 3.8` (априорное среднее), `C = 10` (вес прайора в псевдо-оценках).
При `rating_count = 0` → `NULL`.

Проверка на глаз: 1 оценка 5.0 → ≈3.91; 120 оценок 4.8 → ≈4.72 (побеждает вторая) —
это и есть цель.

### Схема (`packages/db/src/schema.ts`)

- В `recipes` рядом с `ratingAvg` (строка ~470): `ratingBayes: doublePrecision("rating_bayes")`
  (nullable). Обновить комментарий про денормализованные агрегаты.
- Индекс по аналогии с `ratingAvgIdx` (строка ~499): `recipes_rating_bayes_idx`.
- Миграция `db:generate` + **бэкфилл в той же миграции**:
  ```sql
  UPDATE recipes
  SET rating_bayes = (10 * 3.8 + rating_avg * rating_count) / (10 + rating_count)
  WHERE rating_count > 0;
  ```
- ⚠️ Известный капкан: журнал drizzle-миграций имеет инфлированные таймстампы
  (0042/0043), из-за чего новые миграции могут молча не применяться. После
  `db:migrate` руками проверить, что колонка реально появилась в dev-БД.

### Домен

- Новый модуль `apps/web/features/recipes/rating-score.ts`: константы
  `RATING_PRIOR_MEAN = 3.8`, `RATING_PRIOR_WEIGHT = 10` и чистая функция
  `computeBayesianRating(avg: number | null, count: number): number | null`.
  Никакой БД — юнит-тестируется изолированно.
- `recomputeRecipeRatingAggregates` (`apps/web/features/recipes/service.ts:2341`):
  считать и писать `ratingBayes` в том же `UPDATE`, что `ratingAvg`/`ratingCount`
  (транзакция и row-lock уже есть — точка записи одна, расхождение невозможно).

### Сортировка

- `publicRecipeSortColumns` (`service.ts:2085`): ключ `rating` → `recipes.ratingBayes`
  (вместо `ratingAvg`).
- План сортировки (`public-recipe-query.ts:156`) не меняется: `desc`, `nullsLast: true`
  (кто выбрал «По рейтингу», хочет видеть оценённые первыми; неоценённые — в конец),
  вторичный ключ `updatedAt desc` остаётся.
- Отображение НЕ меняется: карточки и страница рецепта показывают `rating.average`
  (честное среднее) + count; `ratingBayes` наружу не выводится и в DTO не добавляется.

### Тесты

- Юнит на `computeBayesianRating`: `count=0 → null`; `1×5.0 < 120×4.8`;
  монотонность по count при фиксированном avg.
- Сервисный (по образцу существующих тестов рейтинга): после `rateRecipe` /
  `deleteRecipeRating` агрегат `ratingBayes` пересчитан; удаление последней оценки
  → `NULL`.

## П2. Count-conditional сорты в селекте

- Сервис: `getPublicRecipeSortAvailability()` в `features/recipes/service.ts` —
  два дешёвых count'а по `published`-рецептам:
  `ratedRecipes` (`rating_count > 0`) и `savedRecipes` (`save_count > 0`).
- Константы порогов в `features/recipes/contracts.ts`:
  `MIN_RATED_RECIPES_FOR_SORT = 5`, `MIN_SAVED_RECIPES_FOR_SORT = 5`.
- Чистый хелпер в `features/recipes/recipes-url.ts` (клиент-безопасный):
  `resolveVisibleSortOptions({ ratedRecipes, savedRecipes, activeSort })` →
  фильтрует `recipeSortOptions`: `rating` скрыт при `ratedRecipes < 5`, `popular` —
  при `savedRecipes < 5`. **Активный сорт всегда остаётся в списке**, даже если
  подпороговый (пользователь пришёл по прямой ссылке — селект не должен показывать
  «ничего не выбрано»).
- `app/(public)/recipes/page.tsx` → пробросить availability в `RecipesToolbar`
  (`components/recipes/recipes-toolbar.tsx`), который сейчас рендерит
  `recipeSortOptions` целиком.
- Парсер (`parsePublicRecipeFilters` / `parseSort`) НЕ трогаем: `?sort=rating` и
  `?sort=popular` валидны всегда — ссылки со страниц стилей
  (`style-community-recipes.tsx:38`) и подбор рецептов для устройства работают
  независимо от порогов.
- Юнит-тест на `resolveVisibleSortOptions` (пороги, activeSort ниже порога).

## П3. «Выбор редакции»

- Схема: `recipes.featuredAt: timestamp("featured_at", { withTimezone: true })`
  (nullable; null = не отмечен; timestamp даёт сортировку «когда отметили»
  бесплатно) + индекс. Прецедент паттерна — `contentArticles.isFeatured`, но для
  рецептов берём timestamp одной колонкой.
- Сервис: `setRecipeFeatured(recipeId, featured: boolean)`; гейт `requireRole("editor")`
  на уровне server action; отмечать можно только `published`.
- UI:
  - Бейдж «Выбор редакции» на карточке (`recipe-card-parts.tsx`) — отдельный пилл
    рядом с чипом стиля, в обоих вариантах (grid overlay / list inline). Показывается
    независимо от рейтинга/«Нового» (это разные слоты). Без пояснительных подписей.
  - Тумблер для editor+ на публичной странице рецепта
    (`components/recipes/public-recipe-page.tsx`): кнопка «В выбор редакции» /
    «Убрать из выбора» через server action + toast. Обычным пользователям не рендерится.
  - В DTO списка (`PublicRecipeListItem`) добавить `featured: boolean`.
- Ранжирование НЕ меняем (featured не буст, только метка). Блок «Выбор редакции»
  на главной/витрине — отдельная задача, не в этом ТЗ.
