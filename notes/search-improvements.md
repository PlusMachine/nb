# Поиск: выравнивание всех поисковых строк (ТЗ 2026-07-17)

Источник: аудит всех поисковых поверхностей (код + живой прогон на dev).
Диагноз: ядро — движок ингредиентов (`features/ingredients/ranking.ts` +
`normalization.ts`) и BJCP-поиск (`brewing-core/src/styles/search.ts`) —
зрелое и правильное: транслит в обе стороны, исправление раскладки,
семейные синонимы, лестница exact → префикс → префикс-по-токену →
substring(≥4), фаззи Левенштейн только в нижнем tier, обрезка шумного
хвоста при наличии сильных совпадений. Живой прогон подтвердил:
«мозаик» = «mosaic» = `vjpfbr` = «мозайк», мусор `qqqzzz` → честно пусто.

Проблема — **неравномерность покрытия**: рядом с умными строками живут
«глупые». Поиск по складу — голый SQL `ilike` (ни ё/е, ни транслита,
ни раскладки: «цытра» и `wbnhf` не находят Цитру, хотя пикер добавления
в том же экране всё это умеет). Галерея своих рецептов —
`toLowerCase().includes()` по названию и стилю. Карты транслита/раскладки
скопированы в двух местах. Rescue-результаты (фаззи/раскладка) внешне
неотличимы от точных — пользователь не видит, что запрос был исправлен.

## Принципы (кодифицировать, не менять)

- **Rescue-механики — только фолбэк.** Раскладка, фаззи, token-scatter
  включаются лишь когда «честная» выдача пуста, и режутся при появлении
  сильных совпадений. Никакого «показать хоть что-нибудь» поверх
  нормальных результатов. Это уже так в BJCP и на витрине `/recipes` —
  распространить как универсальное правило на все поверхности.
- **Одна лестница совпадений** для всех: exact > префикс по границе
  слова > токен > substring (только от 4 символов) > cross-script
  (транслит) > rescue (раскладка/фаззи).
- **Обязательный минимум любой поисковой строки:** trim, ё=е,
  case-insensitive, debounce 180–250 мс, пустое состояние с CTA.
- **Без нейрослопа:** никаких новых пояснительных подписей у полей;
  единственная новая надпись — пометка rescue-выдачи (§С4), и она несёт
  реальный смысл.

Анти-скоуп (решено НЕ делать в этом ТЗ):

- Глобальный поиск / Cmd+K-палитра — отдельный проект, не «дырка».
- Полнотекстовый индекс (pg_trgm/tsvector) — объёмы каталога и склада
  не требуют, всё ранжируется в памяти.
- Подсветка `<mark>` во всех списках — делаем только пометку
  rescue/алиас-матчей (§С4), сплошную подсветку не заводим.
- Переписывание каталожного тулбара в combobox — это фильтр списка,
  а не автокомплит; менять паттерн не нужно.

## Волна 1 — ядро

### С1. Общий пакет `@nb/search` (P1)

Сейчас карты `ruToLatMap` / `latToRuTokens` / `keyboardMapPairs` живут
двумя почти дословными копиями: `features/ingredients/normalization.ts`
и `brewing-core/src/styles/search.ts` (у второй уникален
`foldBjcpSearchDiacritics` — NFKD + ß→ss, у первой его нет).
`packages/search` — пустой scaffold, никем не импортируется.

Сделать:

- Перенести в `@nb/search` слой **нормализации и вариантов запроса**:
  карты транслита/раскладки, `normalizeAndCollapse` (+ фолдинг
  диакритики из BJCP-копии — он становится общим), `transliterate*`,
  `swapKeyboardLayout`, построитель вариантов с флагом
  `{ includeLayoutVariants }`.
- `features/ingredients/normalization.ts` и `brewing-core/styles/search.ts`
  переводятся на импорт из `@nb/search`; свои curated-словари
  (`canonicalIngredientFamilyGroups`, `styleAliasMap`) остаются на месте —
  это доменные данные, не движок.
- **Унифицировать политику раскладки:** в ингредиентном
  `buildQueryVariants` раскладка сейчас подмешивается безусловно
  (компенсируется tier'ами, но принцип должен быть один). Перевести
  ингредиентный поиск на ту же двухпроходность, что BJCP/витрина:
  первый проход без раскладки, второй (при нуле результатов) — с ней.
  Регресс-гард: `vjpfbr` → Мозаик обязан остаться зелёным.
- Скоринг-лестницу (`scoreTextMatch`-подобную) выносить в `@nb/search`
  можно вторым шагом, если не раздувает диф; минимум волны — единые
  нормализация+варианты.
- `brewing-core` не может импортировать из `apps/web` — поэтому именно
  пакет, а не reexport из features.

Приёмка: typecheck + полный сьют зелёные; живой прогон каталога, пикера,
`/recipes`, `/bjcp` — прежние результаты на кейсах из шапки ТЗ.

## Волна 2 — доверие и унификация пикеров

### С4. Пометка rescue-выдачи (P2)

Когда выдачу спасла раскладка, фаззи или token-scatter — результат
внешне неотличим от точного. Пользователь должен видеть, что это
исправление, а не случайность (иначе доверие к выдаче падает ровно
в тех случаях, ради которых rescue сделан).

Сделать:

- Прокинуть из ранкера признак «rescue»: тип совпадения уже известен
  (`MatchKind`/tier ≥ 8, layout-вариант, fuzzy). В DTO выдачи —
  поле `matchRescue?: "layout" | "fuzzy" | "scatter"` (имя уточнить
  по месту).
- UI: одна строка-разделитель над rescue-блоком выдачи —
  «Возможно, вы имели в виду:» (каталог, пикер, склад). Не бейдж на
  каждой строке, не подпись под полем.
- На витрине `/recipes` при срабатывании второго (раскладочного)
  прохода — та же строка над сеткой: «Показаны результаты для
  „стаут“» (исправленный запрос кликабелен = подставить в поле).
- Алиас-матчи (нашлось по «HBC 394», а показана «Цитра») в v1 не
  помечаем — это точные совпадения, шума от пометки больше, чем пользы.

Приёмка: «цытра» в каталоге показывает Цитру под строкой «Возможно,
вы имели в виду»; `cnfen` на витрине показывает исправление; точные
запросы никаких новых надписей не получают.

Приёмка: выбор стиля в редакторе полностью с клавиатуры; axe/ручная

### С7. Серверный гейт длины запроса в API (P3)

`/api/ingredients/search` не гейтит короткие запросы — `q=м` отдаёт
выдачу (клиентский пикер гейтит ≥2, но API открыт и дёргается импорт-
диалогом/скриптами).

Сделать: в route (`api/ingredients/search/route.ts`) — нормализованная
длина < 2 → пустой ответ `{ items: [], total: 0 }` (не 400: клиенту
проще). Синхронно с клиентским `shouldSearchIngredients`
(`ingredient-picker.tsx:154`). Исключение: `searchOnEmptyQuery`-сценарии
(соли воды) шлют пустой q со scope-параметрами — их не ломать
(гейтить только непустой-но-короткий q без scope).

Приёмка: `curl ?q=м` → пусто; пикер солей воды работает; rate-limit
не трогаем.
