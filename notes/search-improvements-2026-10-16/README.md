# Поэтапные изменения поиска и откат

Работа начата 16 октября 2026 года. Цель — ускорить поиск и исправить согласованные ошибки выдачи, сохранив намеренные различия каталога, пикера и склада.

## Исходное состояние

- Базовый HEAD: `80fd137c90a563a0ed564d176e72b2caefb3d465`.
- До начала работы в checkout уже были незакоммиченные изменения. Патчи этапов строятся относительно фактического состояния файлов перед этапом, а не HEAD; предыдущая работа в них не входит.
- Исходный аудит: typecheck web проходит; пакет поиска — 22 теста; web — 3828 успешных и 21 упавший тест на Node 24.13.1. Известные причины падений: server-only в тестах списания, немокированный rate limit в API поиска, обращение sitemap-теста к PostgreSQL.
- Предыдущие замеры ранжирования — локальные микробенчмарки, а не HTTP SLA. Сравнения новых этапов выполняются на одинаковом наборе данных и Node.

## Правила сохранения качества

- Порог и порядок совпадений, словари, лимит вариантов и двухпроходная раскладка сохраняются при оптимизации.
- Каталог продолжает отсекать слабые совпадения; пикер сохраняет семейные замены и дополнительные термины расходников.
- Избранное, custom-позиции и зависящие от фильтров сигналы не помещаются в общий кэш пользователей.
- При исправлении поведения допустимые различия выдачи описываются в соответствующем этапе.

## Как откатывать

В каталоге `patches/` для каждого завершённого этапа хранится прямой патч только этого этапа. `manifest.json` содержит пути и SHA-256 файлов до и после. Патчи включают добавленные тесты и вспомогательные файлы этапа; этот журнал остаётся историей работы.

Из корня репозитория, сначала проверка без изменения файлов:

```bash
git apply --reverse --check notes/search-improvements-2026-10-16/patches/07.patch
```

Если проверка прошла, откат этапа:

```bash
git apply --reverse notes/search-improvements-2026-10-16/patches/07.patch
```

Несколько этапов откатываются в обратном порядке: последний, предпоследний и далее. Если `--check` сообщает конфликт, остановиться: после этапа файл менялся, и требуется выборочное применение обратного патча с сохранением последующих правок. `git reset --hard` и `git restore` от HEAD для этой работы не использовать — они затронут изменения, существовавшие до неё.

Подробности выполненных этапов и проверок добавляются ниже.

## Этап 01 Подготовка запроса

- `createIngredientRanker` анализирует запрос один раз на проход. Применён в каталоге, хабе, пикере и ранжировании склада. Family scope тоже подготавливается один раз на фильтрацию.
- Старые публичные функции ранжирования сохранены как совместимые обёртки. Порог, score, fallback, порядок вариантов и сигналы пользователя не менялись.
- Зафиксирована выдача до изменений: 34 запроса × 2 режима раскладки × 18 кандидатов, включая упаковки, PBW, коды, опечатки и избранное. 70 тестов подготовленного ранжирования; всего 205 поисковых тестов прошли. Typecheck web прошёл.
- Дополнительно старый и новый ранкер дали полностью одинаковые результаты на 12 запросах по 1229 кандидатам из seed-файлов.
- Микробенчмарк Node 24.13.1, 7 чередующихся замеров на запрос: `citra` 38,23 → 20,92 мс; `pilsner` 141,66 → 74,63 мс; `vjpfbr` 85,51 → 45,61 мс; `qqqzzz` 80,83 → 45,78 мс. Ускорение 1,77–1,90 раза. Данные: `01-benchmark.json`. Это только ранжирование, без HTTP/БД; нормализация кандидатов пока выполняется на запросе.
- Откат: обратное применение `patches/01.patch`; проверка `git apply --reverse --check` прошла.

## Этап 02 Отключённые алиасы

- Общий поисковый текст исключает алиасы с `isEnabled === false`; остальные источники поиска сохранены.
- Новый тест сначала воспроизвёл ошибку, затем прошёл после исправления. Дополнительно проверены включённый алиас и совпадение с реальным названием при отключённом одноимённом алиасе.
- 137 профильных тестов прошли, включая PBW, семейные замены и контрольную выдачу ранкера.
- Единственное ожидаемое изменение выдачи: исчезают совпадения, основанные только на отключённом алиасе.
- Откат: `patches/02.patch`, проверка обратного применения прошла.

## Этап 03 Ошибки API

- HTTP 429/500/503 больше не преобразуются в пустую выдачу. Отказ не доходит до записи в клиентский кэш; сетевые/JSON-ошибки также получают локальное состояние ошибки.
- Добавлена кнопка «Повторить поиск». Автоматических повторов нет; отмена запросов при вводе не показывается как ошибка. Успешный пустой ответ продолжает означать «ничего не найдено».
- 91 тест пикера/API прошёл. Исправлен только тестовый mock rate limit в `ingredient-search-api.test.ts`: два ранее известных падения API теперь проходят без обращения к БД.
- Откат: `patches/03.patch`, проверка обратного применения прошла. UI проверен статическим рендером и тестами fetcher; интерактивный браузерный прогон пока не выполнен.

## Этап 04 Кэш каталога

- Холодные запросы одного ключа ожидают общую загрузку. TTL 5 минут и процессная область сохранены; завершённых записей не более 32.
- Инвалидация меняет поколение: старая загрузка может завершить исходный запрос, но не заполняет кэш заново и не удаляет более новую загрузку. Ошибки загрузки не кэшируются.
- 66 тестов прошли, включая 10 одновременных запросов, TTL, гонку инвалидации, повтор после ошибки и разные ключи фильтров. Тип Date сохраняется без сериализации. Прежний обход кэша для тестов с db-моками сохранён; сам production-механизм отдельно покрыт тестами.
- Откат: `patches/04.patch`, проверка обратного применения прошла. Распределённого кэша между процессами не добавлено.

## Этап 05 SQL нормализация

- Сохранены исходные ILIKE-совпадения; добавлены совпадения по нормализованным исходным полям склада и title/автору публичных рецептов. Данные разных полей не склеиваются, код US05 автоматически не приравнивается к US-05.
- Реализация без миграции и изменения данных: нормализованное SQL-выражение. `ILIKE ANY` обрабатывает все варианты с одной нормализацией поля вместо повтора на каждый вариант. Для крупной базы сохранённые нормализованные поля остаются возможной следующей оптимизацией после измерений.
- 133 сервисных теста прошли; typecheck web прошёл. Проверки реального PostgreSQL 16 выполнены в READ ONLY транзакции: 17/17 сравнений SQL с JS-нормализацией, 8/8 положительных и отрицательных примеров совпадений. Скрипт: `05-normalization-check.sql`.
- Примеры: «Мёд» находится по мед/мёд; SafAle US-05 — по US-05/US 05; US05 не совпадает без отдельного алиаса; !!! и буквальный % не расширяют выдачу на всё.
- EXPLAIN ANALYZE синтетических 10000 строк одного поля: 80,12 мс. Это стоимость самого выражения, а не замер HTTP или больших production-таблиц. Нормализация добавляет работу PostgreSQL; для роста нужен повторный нагрузочный тест и, при необходимости, подготовленные поля с индексами.
- Откат: `patches/05.patch`, проверка обратного применения прошла; откат БД не нужен.

## Этап 06 Выбранная категория

- Слабые и семейные совпадения отсекаются внутри выбранной категории/подтипа/группы. Глобальная выдача сохраняет прежнюю общую обрезку шума.
- Счётчики категорий, подтипов и групп на списках/лендингах отражают результат перехода в соответствующий контекст. Счётчики вкладок custom/catalog по-прежнему относятся к глобальной выдаче. Глобальный хаб и его секции не переделаны.
- Оценки кандидатов и популярность брендов используют тот же исходный набор, что раньше. Результат вычисления кандидата повторно используется при расчёте счётчиков в рамках запроса.
- 100 тестов каталога прошли. Новые сценарии: Citra по citro при точном Citro в другом разделе; сильный результат в той же категории; подтипы; локальное исправление раскладки; пустой view=mine без попадания системных ингредиентов.
- Ожидаемое изменение: на узком лендинге могут появиться полезные приблизительные результаты, прежде подавленные точным результатом из другого раздела; они помечены rescue. Без выбранного контекста основной список не расширяется.
- Откат: `patches/06.patch`, проверка обратного применения прошла.

## Этап 07 Подготовленные данные ингредиентов

- Нормализованные имена, активные алиасы и упаковки подготавливаются лениво один раз на объект снимка каталога и повторно используются в запросах. WeakMap не удерживает заменённые снимки только ради индекса.
- Публичные поисковые данные не содержат isFavorite, inventoryUsageCount, recipeUsageCount и brandMarketCount. Эти преимущества накладываются заново из текущего запроса. Custom-данные привязаны к собственным объектам запроса, а не к глобальному ID.
- Контрольная выдача до оптимизации проверена для обычного и подготовленного кандидата. Дополнительно проверены изменение избранного между пользователями и обновлённый снимок с отключённым алиасом. 209 профильных тестов прошли; заключительный набор изменённых поисковых сценариев — 196/196.
- Старый и подготовленный ранкер полностью совпали на 12 запросах по 1229 кандидатам seed. Замеры: `07-benchmark.json`, 7 чередующихся измерений, Node 24.13.1. p50: citra 37,72 → 8,89 мс; pilsner 250,50 → 81,88 мс; vjpfbr 187,75 → 38,05 мс; qqqzzz 145,07 → 27,45 мс. Ускорение относительно исходного ранкера 3,06–5,28 раза в этом запуске. Предварительная обработка заняла 24,30 мс; JSON подготовленных структур — 827421 байт, это не измерение RSS. Замеры разных запусков отличаются по абсолютному времени; сравнивать следует пары одного запуска.
- Это микробенчмарк прогретого ранжирования, не HTTP-нагрузочный тест. Первый запрос после замены снимка оплачивает подготовку; для cold/warm HTTP p95 требуется повторный нагрузочный стенд.
- Откат: `patches/07.patch`, проверка обратного применения прошла.
