## Концепция

**Главная — это продукт в миниатюре, а не брошюра о нём.** Каждый блок — работающий фрагмент
продукта или его честный срез, не маркетинговая плитка. Пивовар доверяет цифрам и процессу,
а не эпитетам. Ничего выдумывать не нужно: всё уже есть в коде, текущая главная это просто не показывает.

**Сквозной визуальный язык — цвет пива (SRM-палитра).** Палитра уже живёт в продукте
(`apps/web/features/recipes/beer-color.ts`) и красит карточки рецептов, свотчи и фильтр цвета.
На главной она становится айдентикой: стакан в hero, спектр BJCP.

Чем плоха текущая главная (`apps/web/app/(public)/page.tsx`): честная, но статичная — она
*рассказывает* про продукт (плитки-ссылки, четыре иконки петли), не даёт ничего потрогать
и вообще не упоминает BrewForge — флагманское отличие от «ещё одного каталога рецептов».

## UX-принципы знакомства

- Анониму всё доступно: hero-переключатель, рецепты по семействам, любой калькулятор в один клик.
  Логин возникает только у действий «сохранить / собрать / сварить» (прогрессивная регистрация — канон).
- Никаких пояснительных подзаголовков — порядок блоков и есть объяснение (см. `docs/roadmap.md`, принципы UI).
- Терминология живой речи пивоваров: засыпь, затирание, паузы, аттенюация, об.%, °P, EBC.
- Cache-safety публичной страницы сохраняется: per-user данных нет, сессия — только существующий
  редирект залогиненного на `/app`.
- Мобайл: hero складывается в столбец, раскадровка петли — горизонтальный свайп со снапом.

## Этапы реализации (каждый — самостоятельный PR)

1. **Hero + витальная панель** — серверный резолв 6 стилей из `@nb/content`, клиентский островок с чипами.
2. **Чипы семейств + рецепты** — `getPublicRecipeFamilyCounts` + `searchPublicRecipes` на 3 карточки.
3. **Петля мастерской** — статичная вёрстка, замена текущего блока «Как работает мастерская».
4. **BrewForge-секция** — статичная (телеметрия — иллюстрация, не живые данные).
5. **Карточки калькуляторов** — переиспользование `CalculatorCard` с `/calculators`, 6 популярных.
6. **Разобраться + два входа + чистка** — перекомпоновка гайдов/BJCP, финальная развилка, удаление старых блоков.

Порядок 1–2 важен (выше сгиба), 3–6 можно перетасовывать.
