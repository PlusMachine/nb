# Редизайн flow «Сварить»: от кнопки на главной до списания со склада (ТЗ 2026-07-16)

Источник: живой прогон владельца 2026-07-16. Боли: страница-двойник `/app/recipes?intent=brew` с тем же видом, но другим поведением; название «Сварить самому»; нет варианта «начать прямо сейчас» без даты; слепая галка «Списать ингредиенты» (не знает, что на складе); кнопка «Списать со склада» на странице партии показывается даже когда не хватает всех позиций.

Решения владельца зафиксированы: единая страница выбора с честным заголовком (Ф1), реклама BrewForge в диалоге — да, но как промо, а не как псевдо-вариант (Ф2), «Начать сейчас» без даты (Ф3), списание — только на странице партии через существующий диалог с превью, **частичное списание разрешить** (Ф4), кнопка списания должна знать про нехватку (Ф5).

Ключевые файлы: `apps/web/components/recipes/brew-picker-dialog.tsx` (диалог старта), `apps/web/components/recipes/my-recipes-gallery.tsx` + `app/(app)/app/recipes/content.tsx` (галерея/intent=brew), `apps/web/features/brew-batches/inventory.ts` (списание, `consumeBrewBatchInventory`, `previewBrewBatchConsumption`), `apps/web/features/brew-batches/components/brew-inventory.tsx` + `consume-preview-dialog.tsx` (панель склада и диалог списания на странице партии), `apps/web/app/(app)/app/brew-batches/[id]/page.tsx` (`prepShortage`), `apps/web/app/(public)/recipes/[slug]/brew-actions.ts` (server action старта).

## Ф1. Единая страница выбора рецепта, без скрытой смены поведения

Сейчас `?intent=brew` рисует ту же галерею, но: прячет табы (закладки/витрина) и фильтр публикации, а клик по карточке вместо открытия рецепта открывает диалог варки. Пользователь видит «ту же страницу», которая ведёт себя иначе.

- [x] Заголовок brew-режима говорит, что это шаг выбора: **«Выберите рецепт и начните варку»** (вместо просто «Сварить»). Кнопка возврата «К рецептам» остаётся.
- [x] Табы (мои/закладки/витрина) и поиск в brew-режиме **не прятать** — отсюда логично дотягиваться до сохранённых и общих рецептов. С табов «закладки/витрина» варка стартует так же (кнопкой «Сварить» на карточке / детальной странице).
- [x] Клик по карточке ведёт себя **одинаково в обоих режимах** — открывает рецепт. Вместо перехвата клика в brew-режиме на карточке появляется явная primary-кнопка **«Сварить»**, открывающая `BrewPickerDialog` (в manage-режиме она остаётся в кебаб-меню, как сейчас).
- [x] Сортировка «сначала можно сварить» и матч-бейджи в brew-режиме остаются как есть.
- Приёмка: в brew-режиме клик по телу карточки открывает рецепт; варка стартует только явной кнопкой; табы и поиск доступны; из режима manage поведение не изменилось.

## Ф2. Диалог: убрать экран выбора из одного пункта, промо BrewForge

Сейчас экран `mode` показывается всегда, даже когда реального выбора нет (у большинства нет устройства). «Сварить самому» читается как «а кто-то может сварить за меня». «Подключить BrewForge» подан как равный вариант варки, хотя вариантом не является.

- [x] Если brew-способного устройства **нет** — экран `mode` пропускается, диалог сразу открывает форму варки (текущий экран `virtual`).
- [x] Если устройство **есть** — выбор из двух: **«Вручную»** / **«На BrewForge»** (переименовать «Сварить самому» / «Сварить на автоматике»).
- [x] Промо автоматики: внизу формы варки (когда устройства нет и `devicesEnabled`) — ненавязчивый промо-блок: мысль «варить можно не только вручную — есть BrewForge», ссылка на подключение (`/app/devices?returnRecipe={id}`) и/или страницу о продукте. Форму не распирать: одна строка/компактная карточка, не псевдо-кнопка выбора режима. Точная формулировка — по месту, без слоп-подписей.
- Приёмка: юзер без устройств попадает в форму за один клик и видит промо; юзер с устройством видит выбор «Вручную / На BrewForge».

## Ф3. «Начать варку» сейчас vs «Запланировать»

Сейчас единственный видимый сценарий — поставить дату (опциональную, но выглядит обязательной), партия всегда создаётся `planned`.

- [x] Primary-действие — **«Начать варку»**: партия создаётся без `plannedFor`, редирект на страницу партии как сейчас.
- [x] Secondary — **«Запланировать»**: раскрывает поле даты (по умолчанию скрыто), после выбора даты создаёт партию с `plannedFor`.
- [x] То же на ветке device-confirm.
- Приёмка: старт без единого лишнего поля в 1 клик из формы; планирование с датой доступно, но не мешает.

## Ф4. Списание: убрать слепую галку, единая точка — диалог с превью; частичное списание разрешить

Сейчас галка «Списать ингредиенты со склада» в `BrewPickerDialog` не знает про склад вообще (показывается и при пустом складе), списание exact-only, при нехватке любой не-presence позиции падает вся транзакция (`INSUFFICIENT_STOCK`). Полноценный превью-диалог с exact/заменами/нехваткой уже есть на странице партии (`ConsumeInventoryDialog`).

- [x] Убрать галку `consumeIngredients` из обоих экранов `BrewPickerDialog` (virtual и device-confirm) и связанный проброс из `startBrewFromRecipeAction` при старте (server-путь `consumeBrewBatchInventoryForStart` не удалять — используется диалогом партии).
- [x] Единственная точка списания — страница партии, `ConsumeInventoryDialog` (превью: exact / замены / нехватка).
- [x] **Частичное списание.** Владелец: «на складе не забита рисовая лузга — а мне не даёт списать ничего». В диалоге списания строки `missing`/`exact_short` не блокируют операцию: списывается то, что есть (short-строки — по остатку, как сейчас для дрожжей), отсутствующие пропускаются с явной пометкой в превью («нет на складе — будет пропущено»). Ядро `consumeBrewBatchInventory`: вместо жёсткого `INSUFFICIENT_STOCK` — режим partial (явный флаг из диалога, чтобы API-инварианты для других вызовов не поменялись молча). Пропущенные/клампнутые строки фиксировать в результате — панель склада после списания показывает «списано частично, N позиций не было».
- [x] Умный призыв на странице партии: когда партия не списана и покрытие полное (все строки exact) — заметный призыв «Все ингредиенты есть на складе — списать?» рядом с кнопкой. При частичном покрытии призыва нет — просто кнопка (см. Ф5).
- Приёмка: в диалоге старта нет упоминаний склада; на странице партии рецепт с 9/10 позициями списывается одним подтверждением, пропущенная позиция явно видна в превью и в результате; полный матч — виден призыв.

## Ф5. Кнопка «Списать со склада» знает про нехватку

Сейчас `canConsume` = «не списано и не терминальна», про склад кнопка не знает; `prepShortage` считается, но передаётся только в акт `prep`.

- [x] Прокинуть данные о покрытии (`missingCount`/`totalLines` из `computeRecipeMatch`) во все акты, где кнопка видна (`prep`, `brewday`, `fermentation`, device-ветка).
- [x] Если на складе **нет ни одной** позиции рецепта — кнопку не показывать; вместо неё текст «Ингредиентов этого рецепта нет на складе» + ссылка на «Чего не хватает» (`/app/shopping`).
- [x] Частичное покрытие — кнопка остаётся, рядом честная подпись «на складе N из M позиций» (существующая ссылка «Не хватает N позиций» согласуется с этим, не дублировать).
- Приёмка: пустой склад → кнопки нет, есть ссылка на покупки; частичный → кнопка + «N из M»; полный → кнопка (+ призыв из Ф4).

## Статус (2026-07-17)

Реализовано целиком Ф1-Ф5 (не закоммичено). Ревью 4 линзами + адверсарная верификация: 7 находок (включая P0 — overbook-гард диалога блокировал частичное списание) — все починены и перепроверены. Полный typecheck + сьют apps/web (252 файла / 3491 тест) зелёные. Живой прогон Playwright: 6/6 сценариев приёмки PASS, 0 console/5xx. Отклонение от текста ТЗ: `consumeBrewBatchInventoryForStart` всё же удалён — ТЗ ошибочно считало его потребителем диалог партии, тот зовёт `consumeBrewBatchInventory` напрямую; других вызовов не было. «Запланировать» на device-ветке создаёт planned-партию БЕЗ deviceId и без запуска устройства (virtual-путь): нагрев на будущую дату устройство не поддерживает, а партия с deviceId рендерила бы device-дашборд вместо акта «Подготовка». Промо BrewForge в форме вживую не проверено (у qa.admin остались устройства прошлых прогонов — экран режима не пропускается); код промо покрыт юнит-логикой.

## Порядок и зависимости

Ф2, Ф3 — независимые, чисто диалог. Ф1 — галерея, независимая. Ф4 и Ф5 связаны (оба про панель склада партии; Ф5 использует те же match-данные) — делать одной волной, Ф4 включает серверную правку ядра списания (partial-режим) + тесты на неё. Перед завершением — typecheck + vitest затронутых кустов + живой прогон: старт варки без устройства, старт с датой, списание при 9/10, пустой склад.
