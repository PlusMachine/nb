Источник: продуктовый разбор раздела `/app/shopping`. Диагноз: производное ядро
(нехватки из запланированных партий + «Почти хватает на:») — правильное и
сохраняется как есть. Но сейчас это «отчёт о нехватках», а не список покупок:
им нельзя пользоваться в момент реальной закупки (магазин/корзина интернет-
магазина, телефон в руке). Три дыры: нельзя добавить своё (дезинфектант,
пробки, CO₂, «хмель про запас»), нечего отмечать по ходу покупки (единственный
способ убрать строку — тут же оприходовать её на склад с вводом количеств),
список нельзя унести (переслать в Telegram, показать продавцу). Четвёртая
находка: «докупить 37 г» — бесполезная цифра, хмель продаётся пачками
50/100 г (закрывает давний тикет «граммовок пачек»).

Принципы (не ломать):

- **Производный список остаётся производным.** Строки §3.2/§3.3 не
  материализуются в БД; персистентными становятся только отметки «куплено»
  (по `lineKey`) и ручные позиции (своя таблица). Список никогда не
  протухает и не требует ручной уборки.
- **Замыкание цикла — через склад.** «Куплено» ≠ «на складе»: отметка — это
  галочка в магазине, перенос на склад — отдельное явное действие дома.
- **Складская лексика** раздела сохраняется («Добавить на склад», «позиции»),
  никаких «корзин» и «заказов».
- **Без нейрослопа:** ни новых ярусов, ни бейджей, ни пояснительных
  подзаголовков. «Почти хватает на:» (§3.3) в этом ТЗ не трогаем вообще
  (кроме неизбежного сдвига вёрстки).

Анти-скоуп (решено НЕ делать): цены/магазины/интеграции с продавцами;
отдельная сущность «заказ/корзина»; дедупликация ручной позиции с производной
строкой (v1 — сосуществуют); чекбоксы в секции «Почти хватает на:» (там
«возможности», а не обязательства).

## П1. Ручные позиции («Своё»)

Пользователь должен уметь дописать в список то, чего не породит ни один
рецепт: дезинфектант, кроненпробки, CO₂-баллон, «Каскад про запас». Иначе он
заводит параллельный список в заметках — и раздел проигрывает блокноту.

### Модель данных

Новая таблица `shopping_manual_items` (миграция 0068):

- `id` uuid pk default random
- `userId` uuid notNull → `users.id` (cascade)
- `name` varchar(180) notNull — свободный текст
- `quantity` doublePrecision null, `unit` varchar(32) null — **оба вместе или
  оба null** (CHECK, тот же принцип «число без единицы не подставляем», что в
  `catalog-links.ts`); unit — из `inventoryUnits` (`features/inventory/units.ts`)
- `category` ingredientCategoryEnum null — для группировки и для
  предзаполнения deeplink «На склад»
- `ingredientCatalogItemId` text null → `ingredients.id` (set null),
  `userCustomIngredientId` uuid null → `user_custom_ingredients.id` (set null) —
  опциональная привязка (даёт ссылку на каталог и полноценный «На склад»);
  максимум одна из двух (CHECK)
- `checkedAt` timestamp null — отметка «куплено» живёт прямо здесь (в отличие
  от производных строк, ручной позиции не нужен `lineKey`)
- `position` integer notNull default 0 — ручной порядок не нужен, но
  стабильная сортировка (createdAt) обязана быть детерминированной
- `createdAt`/`updatedAt`

Индексы: `(userId)`, `(userId, checkedAt)`.

Квота: максимум **100** активных ручных позиций на пользователя — проверка в
server action по паттерну существующего abuse-hardening (атомарный барьер,
как у других create-действий), + rate limit на add.

### Server actions

`apps/web/features/shopping/actions.ts` (`"use server"`, гейт `requireUser`,
все — только над своими записями):

- `addManualShoppingItem({ name, quantity?, unit?, category?, catalogId?, customId? })`
  — валидация: name после trim непустое, ≤180; quantity > 0 и конечное;
  unit ∈ `inventoryUnits`; пара quantity/unit целиком или никак.
- `updateManualShoppingItem(id, { name?, quantity?, unit? })`
- `deleteManualShoppingItem(id)`
- `toggleManualShoppingItem(id, checked: boolean)` — пишет/чистит `checkedAt`.

После мутаций — `revalidatePath("/app/shopping")` и `/app` (виджет дашборда).

### Сервис и контракты

- `buildShoppingListForUser` дополнительно читает ручные позиции (всегда, и
  для дашборда тоже — это дёшево, один запрос по индексу userId).
- Новый DTO `ShoppingManualItemDto`: `{ id, name, quantity, unit,
  quantityLabel, category, catalogHref, addToStockHref, checked }`.
  `catalogHref`/`addToStockHref` — через существующий
  `resolveIngredientHrefs` (привязка → карточка каталога + deeplink;
  без привязки — фолбэк на поиск и «Добавить свой», как у П3-строк).
- `ShoppingListDto` получает `manualItems: ShoppingManualItemDto[]`.
- `totalItems` (бейдж таба «Чего не хватает» и виджет дашборда) =
  производные строки + **неотмеченные** ручные позиции. Отмеченные в счётчик
  не входят: счётчик отвечает на вопрос «сколько ещё купить».
- `emptyReason`: `nothing_to_do` больше не ставится, если есть хоть одна
  ручная позиция — блок со «Своим» рендерится и без запланированных партий.

### UI

- Группа **«Своё»** в блоке «Добавить на склад» — после категорийных групп,
  тем же плотным списком (иконка `Package`, нейтральный цвет как у «Прочее»).
- Блок «Добавить на склад» теперь рендерится, если `plannedBrews.length > 0`
  **или** есть ручные позиции. Когда партий нет — строку «Для запланированных
  партий:» не показывать (только «Своё»).
- Кнопка **«Добавить позицию»** — внизу блока (и в пустом состоянии
  `nothing_to_do` — вторичной кнопкой рядом с «К рецептам»). По конвенции
  «сущностей мало → инлайн»: клик раскрывает инлайн-строку формы прямо на
  месте списка, без модалки и без URL-параметра (состояние клиентское):
  текстовое поле имени + `NumericInput` количества + селект единицы
  (опциональные) + «Добавить»/Esc. Enter в поле имени = submit.
- Строка ручной позиции: чекбокс (см. П2) · имя · количество · кебаб или две
  иконки-действия (редактировать инлайн, удалить). Удаление — БЕЗ
  `ConfirmActionDialog`: позиция списка покупок — копеечная сущность,
  подтверждение здесь — трение (это осознанное исключение из конвенции
  деструктивных действий).
- Саджест из каталога при вводе имени (переиспользовать
  `components/ingredients/ingredient-picker.tsx`, если он встаёт в инлайн-строку
  без доработок) — **опциональный** пункт: если дёшево — сделать (выбор из
  саджеста пишет привязку `catalogId` + category), если picker заточен под
  модалку — v1 остаётся plain text, привязка появится позже.

Приёмка П1: позиция «Дезинфектант Star San» добавляется в 2 клика без
количества; позиция «Каскад 100 г» — с количеством; обе видны в группе
«Своё», входят в бейдж таба; редактируются и удаляются на месте; при нуле
запланированных партий блок с ручными позициями всё равно виден; квота и
rate limit срабатывают.

## П2. Отметка «куплено» + «Перенести купленное на склад»

Сценарий «стою в магазине»: отмечаю купленное галочками, ничего не ввожу;
дома одним действием переношу купленное на склад.

### Модель данных

Новая таблица `shopping_line_checks` (та же миграция 0068):

- `id` uuid pk, `userId` uuid notNull → users (cascade)
- `lineKey` text notNull — ключ производной строки §3.2 (формат
  `resolveLineKey`: `catalog:<id>|<unit>` / `custom:<id>|<unit>` /
  `name:<lower>|<unit>`)
- `checkedAt` timestamp notNull defaultNow
- unique `(userId, lineKey)`

Семантика: отметка живёт, пока в производном списке есть строка с тем же
ключом. Изменилось количество (добавилась вторая партия) — отметка остаётся,
строка показывает новое число: пользователь видит «куплено, но цифра
выросла» и сам решает. Строка исчезла (партию отменили/списали/оприходовали)
— отметка становится мусором и **лениво чистится**: при сборке списка в
`buildShoppingListForUser` отметки, не нашедшие строку, удаляются одним
`delete where userId and lineKey not in (…)` (никаких кронов; коллизий с
параллельной сборкой нет — unique-ключ, повторная вставка идемпотентна).

Ручные позиции (П1) в эту таблицу не пишут — у них свой `checkedAt`.

### Server actions

- `toggleShoppingLineChecked(lineKey, checked)` — upsert/delete по
  `(userId, lineKey)`. Валидация lineKey: непустой, ≤512 символов; формат не
  парсим (ключ — непрозрачный идентификатор).
- `transferCheckedToStock(lines: { lineKey, quantity, unit }[])` — см. ниже.

### Сервис и контракты

- `ShoppingListLineDto` получает `checked: boolean` (join отметок по ключу
  при сборке).
- `ShoppingListDto` получает `checkedCount: number` (по производным строкам +
  отмеченным ручным).
- `totalItems` считает только неотмеченные (согласовано с П1) — «сколько ещё
  купить». В шапке блока рядом с числом — «куплено K» когда K > 0.

### UI: отметка

- Чекбокс слева в `ShoppingLineRow` (и в строке ручной позиции) — реальный
  `<input type=checkbox>` в стилистике UI-кита, тач-таргет ≥44px (строка
  становится чуть выше — это ок, мобильный кейс главный).
- Отмеченная строка: имя зачёркнуто (`line-through`), строка приглушена
  (`text-muted-foreground`), количество и «На склад» остаются кликабельными.
  Отмеченные строки НЕ переезжают в конец группы (перескоки строк под пальцем
  в магазине — зло), остаются на месте.
- Оптимистичное переключение (useOptimistic/локальный стейт + action), без
  ожидания сервера — в магазине связь плохая.
- Секция §3.3 «Почти хватает на:» чекбоксов НЕ получает.

### UI: перенос на склад

- Когда `checkedCount > 0` — в шапке блока «Добавить на склад» появляется
  primary-кнопка **«Купленное — на склад (K)»**.
- Клик открывает `Dialog` (из `@nb/ui`) со списком отмеченных строк:
  имя · `NumericInput` количества (предзаполнен: производная строка —
  `quantityToBuy` с округлением до фасовки из П4, когда она есть; ручная —
  её quantity) · единица. Количество редактируемое — купил больше/меньше.
- Строки **без каталожной/кастомной привязки** (name-only производные и
  непривязанные ручные) перенести пачкой нельзя (CHECK
  `user_ingredients_source_linkage_chk` требует привязку): в диалоге они
  показываются отдельным хвостом «Добавьте вручную: …» со своими
  существующими deeplink-ами «Добавить свой» — честно, без молчаливого
  пропуска.
- Подтверждение: один server action `transferCheckedToStock`, внутри —
  существующий путь добавления позиций склада из `features/inventory/service.ts`
  (тот же, каким пользуется модалка `/app/ingredients`; НЕ дублировать
  нормализацию единиц). На каждую строку создаётся позиция склада; отметка и
  (для ручных) сама ручная позиция удаляются в той же транзакции. Производная
  строка после ревалидации исчезает сама — нехватка закрыта складом.
- Результат: тост `useToast` «На склад: N позиций» + ссылка «Запасы»
  (`/app/ingredients`). Частичный сбой транзакции невозможен — всё или ничего.

## П4. Округление до покупабельных фасовок

«Докупить 37 г» → «пачка 50 г»: расчётная нехватка переводится в то, что
реально продаётся. Данные уже есть — `ingredient_package_variants`
(`packageAmount`/`packageUnit`, `stockContentAmount`/`stockContentUnit`,
`isDefaultForStock`). Закрывает тикет «граммовок пачек».

### Логика (чистая функция в `features/shopping/pack-rounding.ts` + юнит-тесты)

`resolvePackSuggestion(need: {quantity, unit}, variants): PackSuggestion | null`

- Работает только для строк с `ingredientCatalogItemId` и только когда
  нехватка и содержимое фасовки приводятся к одной размерности (конверсия —
  `convertWeight`/`convertVolume` из `@nb/brewing-core`, как в
  `features/inventory/units.ts`). Иначе `null` → поведение как сегодня.
- Если единица нехватки уже `pack`/`item` (дрожжи «1 пачка» из Б6) — `null`,
  не дублировать существующую механику.
- Выбор фасовки: вариант с `isDefaultForStock`, иначе наименьшая фасовка,
  покрывающая нехватку одной штукой, иначе просто наименьшая. Количество:
  `count = ceil(need / packContent)`. Комбинаторику «2×100 г + 1×50 г
  дешевле» НЕ делать — цен нет, это слоп.
- Результат: `{ count, packLabel, totalQuantity, totalUnit }` →
  «1 пачка 50 г», «2 пачки по 100 г» (pluralize), «5 кг» для солода
  (фасовка 1 кг × 5 — если packLabel вырождается, показывать просто итог).

### Интеграция

- Сервис: для строк §3.2 с каталожной привязкой батчем тянутся варианты
  (`inArray` по всем catalogId списка — один запрос) и в
  `ShoppingListLineDto` добавляется `packSuggestion: { label, totalQuantity,
  totalUnit } | null`.
- UI строки: основным числом становится фасовочное («пачка 50 г»),
  исходная нехватка — вторичной подписью серым («нужно 37 г»). Без
  packSuggestion — как сегодня.
- Deeplink «На склад» при наличии packSuggestion предзаполняет
  `addQty/addUnit` фасовочным итогом (`totalQuantity/totalUnit`), а не
  остатком. Если форма добавления умеет предвыбор варианта фасовки
  (`user_ingredients.packageVariantId` существует — проверить по месту в
  `app/(app)/app/ingredients/content.tsx`) — прокинуть и
  `addVariantId=<id>`; если не умеет — НЕ дорабатывать форму в этом ТЗ,
  достаточно количества.
- Диалог переноса П2 предзаполняется фасовочным количеством (уже учтено в П2).
- §3.3 фасовки не получает (карточки и так плотные; выравнивание — по месту
  при следующем проходе, если попросится).

Приёмка П4: нехватка Citra 37 г при фасовках 50/100 г показывает «пачка
50 г» + «нужно 37 г», «На склад» предзаполняет 50 г; нехватка 120 г → «2
пачки по 100 г» (default-for-stock 100 г); ингредиент без вариантов — как
сегодня; дрожжи «1 пачка» не задеты; юнит-тесты на выбор варианта, ceil,
несводимые размерности.
