# ТЗ: точность расчётных параметров рецепта (IBU / FG / эффективность)

Статус: **реализовано 2026-07-11** (Э1–Э3 + Э1.4; итоги — раздел «Результаты» внизу).

## Контекст

Движок прогнали на 20 реальных публичных рецептах (6 клонов BYO, 7 Brewer's Friend с явным Tinseth/Morey и полными входными данными, 7 Brülosophy) — заявленные параметры сняты дословно со страниц первоисточников. Харнес и датасет закоммичены: `apps/web/scripts/validate-recipe-stats/` (запуск: `npx tsx apps/web/scripts/validate-recipe-stats/run.ts`, БД не нужна). Независимое подтверждение той же картины — `docs/recipe-stats-divergence.md` (37 рецептов через каталожную цепочку).

### Базовая линия (до фиксов)

| Метрика | ср.\|Δ\| | медиана \|Δ\| | max \|Δ\| | сист. сдвиг |
|---|---|---|---|---|
| OG (пункты) | 3.20 | 2.0 | 9.0 | +2.70 |
| FG (пункты) | 2.95 | 2.0 | 9.0 | +2.75 |
| ABV (%) | 0.44 | 0.42 | 0.98 | −0.02 |
| IBU | 7.40 | 4.6 | 30.6 | **−6.31 (17%)** |
| SRM | 0.69 | 0.20 | 5.0 | −0.39 |

Выводы: **формула OG верна** (обратный расчёт эффективности из заявленного OG воспроизводит эффективность источника с точностью ±1–3 п.п. на 13 рецептах, где она указана; весь сдвиг +2.7 — от дефолта 75% на рецептах BYO, которые считаны при ~65%). **SRM/Morey верен.** Проблемы три: IBU систематически занижен, FG систематически завышен, дефолт эффективности завышен.

## Э1. IBU: утилизация по плотности в котле + нормировка на объём партии

### Суть ошибки

Тинсет требует считать **утилизацию** по плотности сусла **в котле на момент внесения** (оно жиже готового пива — до уварки), а **концентрацию изо-альфа-кислот** — на **конечный объём партии**. У нас:

1. `apps/web/features/recipes/service.ts:1361` передаёт `preBoilVolumeL: null` → `resolveBitternessContext` (в `packages/brewing-core/src/calculations/ibu.ts`) схлопывает preBoil=postBoil → SG на момент внесения = OG готового пива → утилизация занижена. На плотном сусле драматично: Imperial Stout 83.8 → 58.1, Barleywine 99.8 → 69.2.
2. **Замаскированный баг:** `calculateAdditionIbu` делит массу изо-альфа на **объём на момент внесения**, не пересчитывая на конечный объём (при уварке горечь концентрируется). Пока preBoil=null, это no-op; если просто начать передавать объём кипения — станет **хуже** (проверено: Imperial Stout 58.1 → 50.9). Чинить оба места строго вместе.

### Э1.1 Нормировка (`packages/brewing-core/src/calculations/ibu.ts`)

В `calculateTinsethWhirlpoolV2` (ветка boil/first_wort_hop) и `calculateRager`: объём на момент внесения (`resolveBoilVolumeAtAddition`) используется **только** для расчёта SG (bigness factor); деление в `calculateAdditionIbu` — всегда на `context.postBoilVolumeL`.

- `tinseth_classic` уже делит на `batchVolumeL` — не трогать (голдены `calculations.test.ts:92` = 31.3 и `:165` = 33.1 не должны измениться).
- Вирпул/dip_hop и carryover-ветка уже делят на postBoil — не трогать.
- В `BitternessContribution.volumeL` записывать объём деления (postBoil); `gravityAtAddition` оставить как SG на момент внесения. Задокументировать в типе.

### Э1.2 Передача объёма кипения (`apps/web/features/recipes/service.ts`, `computeRecipeStatsSnapshot`)

`preBoilVolumeL = postBoilVolumeL + evaporationRate × boilTimeMinutes / 60`, где `evaporationRate = input.equipmentProfileSnapshot?.evaporationRateLPerHr ?? 3`. Снапшот профиля уже приходит в input (строка 1238) и уже содержит `evaporationRateLPerHr` (дефолт стартового профиля — 3 л/ч, `apps/web/features/equipment-profiles/contracts.ts:45`) — вынести общую константу, не дублировать литерал. Усадку при охлаждении (`coolingShrinkagePct`) в v1 сознательно игнорируем; `postBoilVolumeL = batchVolumeL` остаётся как есть.

`fermentableGravityPoints` не менять — это суммарный экстракт, он от объёма не зависит.

### Э1.3 Потребители и голдены

- **Калькулятор IBU** (`apps/web/features/calculators/definitions.ts:1422`) preBoil не передаёт → нормировочный фикс для него no-op; семантика его поля «плотность сусла» и так соответствует котловой. Опционально (не блокер): добавить поле «объём до кипячения».
- `scaling.ts` → `calculateIbuTinseth` → classic — не затронут.
- Новый голден на v2 с уваркой (ручной расчёт): 56.7 г @ 13% AA, 60 мин при кипячении 90 мин, batch 20.06 л, preBoil 30.28 л, OG 1.092 → объём при внесении 26.87 л, SG 1.0687, утилизация ≈0.195, **IBU ≈ 71.6** (сейчас 58.1; эталон Brewer's Friend 83.8 — остаток объясняется тем, что BF исключает вносимую в ферментер декстрозу из котловой плотности, это не гонимся).
- Обновить снапшот-тесты web (`recipe-service.test.ts` и соседние), где запинены IBU.

### Э1.4 Пересчёт сохранённых рецептов

Статы лежат в строках `recipes` и пересчитываются только при редактировании. Нужен одноразовый скрипт массового пересчёта (по образцу CLI-скриптов в `apps/web/scripts/`), **пропускающий** кураторские рецепты витрины: у них числа авторитетные из первоисточника (`importMeta.seedSource === "demo-public-recipes"` и вообще всё с `sourceAttribution`). Запуск согласован (В2).

## Э2. FG: взвешенная сбраживаемость вместо аддитивных поправок с потолками

### Суть ошибки

`apps/web/features/recipes/fg-estimate.ts`: поправка за простые сахара упирается в потолок `min(share×0.20, 3)` — при 20% сахарозы в засыпи даёт +3 п.п. вместо честных ~+4.4, а `MAX_EFFECTIVE_ATTENUATION_PCT = 90` дожимает сверху. Итог на датасете: FG завышен на +2.75 пт, хуже всего на сухих сортах (Tripel 1.004→1.013, Rye IPA 1.008→1.015).

### Что сделать

Заменить блок аддитивных поправок (строки ~355–362) на взвешенную модель: у каждого класса своя видимая сбраживаемость, итог — среднее по долям gravity-вклада (доли уже считаются, `simpleSugarSharePct` и т.д.):

```
attBase   = baseAttenuationPct + mashAdjPctPoints        // как сейчас
attEff    = shareBase×attBase + shareSugar×100 + shareLactose×0 + shareCrystal×(attBase×0.6)
```

- `simple_sugar` → 100 (видимая аттенюация сахарозы/декстрозы ~100%).
- `lactose_nonfermentable` (лактоза/мальтодекстрин) → 0.
- `crystal_dextrin` → `attBase × 0.6`.
- Клампы: `MIN_EFFECTIVE_ATTENUATION_PCT` 60 → **50** (молочные стауты с большой долей лактозы легитимно ниже 60), `MAX` 90 → **98**.
- `fgRangeMin/Max` пересчитывать той же моделью от min/max аттенюации дрожжей.
- Контракт `RecipeFgEstimateDetails` не ломать: в поля `simpleSugarAdj`/`crystalDextrinAdj`/`lactoseAdj` писать эффективные дельты (вклад класса в `attEff − attBase`), проверить места отображения деталей в UI.
- Обновить `apps/web/tests/recipe-fg-estimate.test.ts` + добавить кейсы: трипель с 20% сахарозы (78% дрожжи → ~82.4% итог), milk stout с 8% лактозы, засыпь без спецклассов (модель обязана дать ровно `attBase`).

Честная граница метода: сухость сэзонов/бельгийцев (реальная аттенюация 90%+ при лабораторных 75–80%) моделью не покрывается — это свойство штамма, а не засыпи. Не гнаться.

## Э3. Эффективность по умолчанию: 75 → 70

`DEFAULT_EFFICIENCY = 75` живёт в двух местах: `apps/web/features/recipes/service.ts:113` и `apps/web/components/recipes/recipe-designer/helpers.ts:440`. Стартовый профиль оборудования уже несёт 70% (`equipment-profiles/contracts.ts:44`) — рассинхрон. Реальные домашние варки: 65–72%; BYO неявно считает при ~65% (подтверждено обратным расчётом на 6 рецептах: 64.3–66.4%).

- Оба места → **70**, константу по возможности свести в одно место (`@nb/shared` или `features/recipes/contracts.ts`).
- Проверить: если у рецепта выбран профиль оборудования, эффективность должна предзаполняться из профиля (если это не так — сделать; дефолт 70 остаётся только для рецептов без профиля).
- Статы существующих рецептов с `efficiency = null` изменятся — согласовано (В1, приложение не в проде).

## Критерии приёмки

Прогнать `npx tsx apps/web/scripts/validate-recipe-stats/run.ts` до и после; вписать «после» в этот документ.

1. IBU: сист. сдвиг с −6.3 до **|сдвиг| ≤ 4**; ср.|Δ| с 7.4 до **≤ 5.5**; Imperial Stout (BF) с 58.1 до **≥ 70**.
2. FG: сист. сдвиг с +2.75 до **≤ +2.0**; на трипеле |Δ| строго меньше базовых 9 пт; ни на одном рецепте датасета FG не ухудшается более чем на 1 пт.
3. OG: формулу не трогать; сдвиг на BYO-подмножестве уменьшается за счёт Э3.
4. SRM: без изменений (|дельта против базовой линии| < 0.1 на каждом рецепте).
5. Голдены classic (31.3 / 33.1) не изменились; новый голден v2-с-уваркой ≈ 71.6 ± 0.5.
6. `pnpm --filter @nb/brewing-core test`, тесты web, `npm run typecheck` — зелёные.
7. Перегенерировать `docs/recipe-stats-divergence.md` (`npm run seed:public`) — сводка по IBU/FG должна улучшиться.

## Решения владельца (2026-07-11, все вопросы закрыты)

- **В1.** Приложение ещё не в проде — дефолт эффективности и прочее меняем свободно, миграционных оговорок нет.
- **В2.** Массовый пересчёт сохранённых статов (Э1.4) — запускать. Кураторская витрина (`sourceAttribution`) по-прежнему не трогается.
- **В3.** Потолок аттенюации — **98%**. Кламп — предохранитель от мусорных данных каталога, не параметр модели: взвешенная модель сама выше 100 не выдаёт, а 98 не режет ни один реальный сорт (сэзоны 90–95%, brut IPA ~100 — за ним не гонимся).

## Порядок работ

Э1.1 (+голдены) → Э1.2 → Э2 → Э3 → прогон харнеса и фиксация «после» → Э1.4 → перегенерация divergence-отчёта. Э1.1 и Э1.2 — строго в одном PR/коммите: по отдельности каждый ухудшает точность.

Главный риск — расползание запиненных значений в тестах: обновлять их осознанно, каждое изменение голдена сверять с ручным расчётом, а не переписывать под фактический вывод.

| FG (пункты) | 2.95 → 2.95 | +2.75 → **+2.65** | сдвиг ≤ +2.0 | ⚠ частично, см. ниже |
| ABV (%) | 0.44 → **0.33** | −0.02 → −0.19 | — | ✅ |
| IBU | 7.40 → **4.94** | −6.31 → **−3.53** | \|сдвиг\| ≤ 4, ср.\|Δ\| ≤ 5.5 | ✅ |
| SRM | 0.69 → 0.69 | −0.39 → −0.39 | без изменений | ✅ |

Точечные цели: Imperial Stout (BF) 58.1 → **71.7** (цель ≥70) ✅; трипель FG |Δ| 9 → **8** ✅; ухудшение FG >1 пт против базовой линии — ни на одном рецепте (после Э3) ✅. Голдены classic 31.3/33.1 не сдвинулись; новый голден v2-с-уваркой 71.6 сошёлся с ручным расчётом. Сьюты: brewing-core 97/97, web 2202/2202, tsc чистый. Массовый пересчёт: 39 рецептов пересчитано, 37 кураторских пропущено, 0 ошибок. `docs/recipe-stats-divergence.md` перегенерирован: сдвиг IBU −5.2 → −3.5.

**Почему FG-цель ≤ +2.0 не добита (+2.65) и почему это принято.** Остаточные промахи — сухие сорта (трипель +8, Rye IPA +7, сэзон +6): (а) в датасете у BYO-рецептов нет аттенюации дрожжей — харнес падает на дефолт 75% вместо реальных ~80% у US-05 и им подобных, в проде рецепт связан с дрожжами каталога, у которых диапазон аттенюации есть; (б) нет профилей затирания — поправка за температуру всегда 0, в проде она есть; (в) реальная сухость бельгийских/сэзонных штаммов (90%+ при лабораторных 75–80%) — свойство штамма, из засыпи не выводится (ожидаемая граница метода, зафиксирована в Э2); (г) «заявленный» FG клонов BYO — сам прикидка их софта по грубой модели без штрафов за состав засыпи. Коэффициент кристалла 0.6 проверен по реальным данным (Lagunitas: US-05 ~80% лаб., ~13% кристалла, заявленная видимая аттенюация 74% → штраф ~0.3–0.4 п.п. на 1% доли — ровно что даёт 0.6) и оставлен; смягчать его ради подгонки под чужие грубые оценки — оверфит на бенчмарк.

Известный нетронутый выброс: Pliny-подобные рецепты с гигантским поздним охмелением — Тинсет без модели насыщения изо-альфа (~100–110 мг/л) даёт 200+ IBU при реальных ~100. Потенциальный v2: кламп/сатурация IBU. Не делалось сознательно.
