# «Чего не хватает» — рефактор страницы `/app/shopping`

> Актуальные названия после итераций владельца (S4–S6, 2026-07-06/07): раздел —
> «Чего не хватает» (бывш. «Список покупок» → «Докупить»; «Докупить» отклонено —
> читалось как ссылка на магазин; URL не меняется); секция §3.3 — «Почти
> хватает на:». Отдельного пункта меню у раздела НЕТ — это ТАБ раздела
> «Мой склад»: на /app/ingredients и /app/shopping общая шапка (H1 «Мой склад»
> + InventoryTabs «Запасы | Чего не хватает · N»); другие входы — виджет
> дашборда и строка «Не хватает N позиций» в подготовке варки; в меню
> подсвечивается «Склад». Лексика складская, не магазинная: блок §3.2 называется
> «Добавить на склад» (сверху строки партий-источников «Для запланированных
> партий:», ниже ингредиенты по категориям плотным списком; при all_in_stock —
> строка «Всё нужное уже на складе»); метка в карточках §3.3 — «Не хватает»,
> в карточке всегда видны 2 строки нехваток, остальные — под стрелочкой
> «Ещё N позиций», карточки одной высоты. Ниже — исходный текст спеки S1–S3
> с историческими названиями.

> Заземлено на аудит кода 2026-07-06: `features/shopping/service.ts`,
> `components/shopping/shopping-list-view.tsx`, `features/recipes/match-service.ts`,
> виджет на `/app` (`app/(app)/app/page.tsx`), акт «Подготовка» партии
> (`features/brew-batches/components/brew-prep-card.tsx`).
> Статус: спека на реализацию.

## 0. Рамки

- **Что переделываем:** страницу `/app/shopping` (ИА + новая секция по избранным),
  сервис `buildShoppingListForUser` (баг + эффективность), входы в раздел из
  сценария планирования варки.
- **Что НЕ трогаем:** движок матча (`matchLineAgainstInventory`, каскад брендов,
  нормализация единиц) — только потребляем его API; модалку добавления на склад
  (`/app/ingredients?addSource=…`) — формат deeplink'а уже единый
  (`features/ingredients/catalog-links.ts`); дашборд-виджет — доработка косметическая.
- **Без миграций и новых таблиц.** Список остаётся полностью вычисляемым — это
  осознанное свойство (см. §2), а не долг.

## 1. Диагноз текущей страницы

| # | Симптом (как видит пользователь) | Причина в коде |
|---|---|---|
| 1 | **Баг:** строка показывает «0.5 кг», клик «На склад» предзаполняет 0.25 | `service.ts:79-89` — при агрегации второй варки досуммируется `quantityToBuy`, но `addToStockHref` собран один раз при создании строки с нехваткой только первой варки и не пересобирается |
| 2 | Непонятно, откуда список взялся: «2 запланированные варки» — текст без имён и ссылок | `plannedBrews` есть в `ShoppingListDto`, но `ShoppingListView` рендерит только счётчик в подзаголовке |
| 3 | Раздел — тупик: запланировал варку, а о появившихся нехватках никто не сказал | Ни планирование варки, ни акт «Подготовка» (`brew-prep-card.tsx`), ни секция склада партии (`brew-inventory.tsx`) не ссылаются на `/app/shopping` |
| 4 | Пусто и бесполезно без запланированных варок, хотя у пользователя 20 избранных рецептов | Сервис считает только `status === "planned"` + `recipeId`; избранные (`recipe_saves`) и свои рецепты не участвуют |
| 5 | N+1 по инвентарю: 5 рецептов = 5 полных загрузок склада | `service.ts:47-53` зовёт `computeRecipeMatch` на каждый рецепт; каждый вызов сам грузит весь инвентарь (`match-service.ts:421+`). Батч `computeRecipeMatchesForUser` (грузит склад один раз) уже существует и не используется |
| 6 | Варка «без рецепта» (recipeId=NULL после удаления источника) молча выпадает из списка | Матч считается от живого рецепта, а не от `recipeSnapshot` партии — при том что снапшот объявлен источником истины варки |
| 7 | Нехватка считается под дефолтный объём партии пользователя, а не под объём запланированной варки | `computeRecipeMatch({userId, recipeId})` без `targetBatchVolumeL`; объём партии живёт в снапшоте |

П.6–7 — известные ограничения, честный фикс — матч от снапшота (§7, отложено).

## 2. Принципы

| Принцип | Основание |
|---|---|
| Список — **производный, ничего не хранит**. Изменил рецепт / отменил варку — список сам пересчитался | Хранимый список с чекбоксами протухает; замена ингредиента — решение уровня рецепта (match-панель), не списка |
| Две секции с разной семантикой: запланированное = **обязательство** (агрегируем в один поход в магазин), избранное = **возможность** (по рецептам, без агрегации) | Человек с 20 избранными не варит все 20; сумма их нехваток — список на пол-магазина, шум |
| Раздел объясняет себя **структурой** (блок источников, группировка), а не подзаголовками-простынями | Конвенция UI проекта |
| Вход в раздел — из момента, когда нехватка возникла (планирование варки), а не только из меню | Устраняет «тупик» §1.3 |
| Секция возможностей мотивирует: «докупи 1 позицию — сможешь сварить X», а не «купи ещё вот это всё» | Рамка opportunity; переиспользует семантику `resolveBrewabilityBadge` |

## 3. Целевая ИА страницы

```
Чего не хватает
N позиций докупить · M запланированных варок

К ПОКУПКЕ                              ← агрегированная секция (§3.2, есть сейчас)
  Для варок: [чипы запланированных варок, §3.1]
  Солод
    Pale Ale (RU) …        0.5 кг  [На склад]
  Хмель
    Citra …                 50 г   [На склад]

ДОКУПИТЬ И СВАРИТЬ                     ← новая секция-карточки по избранным/своим (§3.3)
  [Юэлл Хазик IPA]        Докупить: Citra 50 г              [На склад]
  [Пшеничное летнее]      Докупить: US-05 · кориандр 20 г
  Ещё 17 рецептов ▸                    ← свёрнуто
```

### 3.1 Блок источников

Горизонтальный ряд чипов — по одному на запланированную варку: название варки,
дата (`plannedFor`, если есть), число позиций к покупке по этой варке. Клик —
на страницу партии. Данные уже в DTO (`plannedBrews`); добавить в
`ShoppingListSourceBrew` поле `missingCount` (число строк списка, где варка в
`neededBy`).

Без интерактивной фильтрации в MVP: у домашнего пивовара 1–3 запланированные
варки, контекст «для какой варки» у каждой строки уже есть. Фильтр-чипы —
кандидат на v2, если появится боль.

### 3.2 Секция «К покупке» (доработка существующей)

Остаётся как есть: агрегация по ингредиенту+единице, группировка по категориям
(формат похода в магазин), строка = `ShoppingLineRow`. Изменения:

- **Фикс бага §1.1:** `addToStockHref` собирать после цикла агрегации — в том же
  проходе, где проставляется `quantityLabel`, из итогового `quantityToBuy`.
- Заголовок секции «К покупке» появляется только когда на странице есть и вторая
  секция; одна секция — без заголовка-капитанства.

### 3.3 Секция «Докупить и сварить» (новая)

**Источник:** избранные рецепты (`listSavedRecipes`) + свои рецепты пользователя,
за вычетом рецептов, уже стоящих за запланированными варками (они в §3.2 —
дублировать нельзя, иначе «купил по верхней секции, а нижняя всё ещё просит»).

**Матч:** один вызов `computeRecipeMatchesForUser({userId, recipeIds})` — склад
грузится один раз на всю страницу (заодно закрывает §1.5 и для верхней секции:
`buildShoppingListForUser` переводится на тот же батч).

**Отбор и порядок.** Семантика — как у бейджа готовности карточек
(`resolveBrewabilityBadge`):

| Ярус | Условие | Показ |
|---|---|---|
| Развёрнуто | `almost`: покрыто ≥70% типов, не хватает 1–2 позиций | Строка рецепта с нехватками инлайн, сортировка по `missingCount` asc, затем по имени |
| Свёрнуто «Ещё K рецептов» | нехватка ≥3 позиций при покрытии ≥70% | По клику — те же строки |
| Не показываем | `ready` (докупать нечего) и покрытие <70% типов (мусорное совпадение) | — |

**Карточка рецепта (S4):** визуальный язык `BrewableRecipeCard` — обложка,
чип стиля, название сверху; снизу блок нехваток с меткой «Докупить» и строками
(`ingredientDisplayName` + `suggestedAddQuantity/Unit`). У каждой нехватки — та
же пара действий, что в §3.2: ссылка на карточку каталога и «На склад» с
предзаполнением (`buildIngredientCatalogActionHref`). Количества —
**per-recipe, без агрегации между рецептами** (принцип §2).

Кап: развёрнутый ярус — максимум 8 рецептов, дальше «Показать все» (не рендерим
простыню на 20 разборов).

### 3.4 Пустые состояния

| Планируемых варок | Избранных/своих с нехватками | Экран |
|---|---|---|
| 0 | 0 | Текущий empty state «список пуст» (CTA к рецептам/варкам) |
| 0 | >0 | Только секция §3.3 + компактная подводка «Запланируйте варку — соберём точный список» (ссылка на рецепты) |
| >0 | * | Полная раскладка §3; при `all_in_stock` вместо §3.2 — текущий блок «Всё готово к варке» |

`emptyReason` в DTO расширяется, чтобы различать эти случаи.

## 6. Порядок реализации

1. **S1 — сервис:** фикс бага + батч-матч + тесты. Самостоятельная ценность,
   можно катить отдельно.
2. **S2 — страница:** блок источников + секция возможностей + пустые состояния.
3. **S3 — входы:** строка нехваток в акте «Подготовка».

## 7. Отложено (не делать сейчас)

- **Матч от снапшота партии** (закрывает §1.6–1.7: варки без `recipeId`, объём
  партии). Требует матчер по снапшот-строкам — отдельная задача, п. синхронизировать
  со спекой помощника варки.
- Персистентность: «скрыть позицию», чекбоксы «куплено», ручное добавление.
  Противоречит производной природе списка; вернуться, только если появится боль.
- Фасовки (`ingredient_package_variants`: «докупить 112 г» → «2 × 100 г») и
  источники покупки (`ingredient_sources`) в строках списка.
- Экспорт/шаринг текстом, пуш-напоминание перед `plannedFor`.
- Фильтр по варке-источнику (чипы §3.1 как фильтры).
