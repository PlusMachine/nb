# ТЗ: динамические OG-картинки (превью ссылок в Telegram и мессенджерах)

> Статус: ТЗ готово, реализация не начата. Разведка по коду и правилам
> мессенджеров — 2026-07-16. Владелец: фокус на Telegram; охват — рецепты,
> калькуляторы, ингредиенты, стили BJCP, статьи, мастера, /beer, разделы.

## 1. Цель

Каждая расшаренная ссылка на NB должна разворачиваться в мессенджере в большую
информативную карточку, которая продаёт страницу сама: для рецепта — цвет пива
и статы, для калькулятора — что он считает (v2 — сам результат расчёта), для
ингредиента — ключевые параметры. Сейчас почти все страницы падают на одну
статичную заглушку «NB» (`apps/web/app/opengraph-image.png`).

Витрина — канал привлечения (SEO/шаринг); основной органический сценарий —
пивовар кидает ссылку в чат. Карточка с данными → выше кликабельность каждой
расшаренной ссылки с первого дня.

## 2. Правила рендера превью (результат ресерча 2025–2026)

**Telegram:**
- Большая карточка (картинка во всю ширину) включается **тегом
  `twitter:card = summary_large_image`**, а не размером картинки. Без него даже
  1200×630 рисуется мелким квадратиком. У нас тег уже стоит глобально
  (`app/layout.tsx:40-42`), но **точечно перебивается на `summary`** в
  `recipes/seo.ts:205-209`, `content-articles/seo.ts:61-65`, `masters/seo.ts`
  когда нет фото — это надо починить (см. §7).
- Размер: стандарт 1200×630 (1.91:1). Вес ≤ 5 МБ (жёсткий лимит TG), URL —
  абсолютный HTTPS без авторизации (`metadataBase` из `APP_URL` уже настроен,
  `layout.tsx:27`).
- Кэш агрессивный и общий на всех пользователей; принудительный сброс — бот
  **@WebpageBot** (до ~10 ссылок за сообщение). Заголовок/описание рядом с
  картинкой рендерятся нативно — кириллица без проблем; шрифт нужен только
  **внутри** картинки.
- Краулер TG не исполняет JS — все теги должны быть в серверном HTML.

**Прочие (пересечение требований):**
- WhatsApp: вес **< 600 КБ** (целиться ≤ 300 КБ), пропорции ≤ 4:1, только HTTPS
  с валидным сертификатом, `og:image:width/height` желательны.
- VK: большой сниппет от ~537×240; читает `og:image`.
- Max: не документирован — стандартный `og:*` набор 1200×630 ≤ 300 КБ.

**Вывод по бюджету:** карточка 1200×630, плоский дизайн (текст + заливки, без
фото-фонов) → PNG из `ImageResponse` весит ~30–150 КБ и проходит везде.
Карточки с фото-врезкой (Ф5) — контролировать вес, при > 300 КБ дожимать
`sharp().jpeg()` (см. §6).

## 4. Визуальная система

Одно семейство карточек, чтобы любая ссылка NB узнавалась в ленте чата:

- **Холст:** 1200×630, тёмный фон `#09090b` (совпадает с иконкой приложения;
  тёмная карточка контрастна в обеих темах TG). Текст `#f4f4f6`, вторичный
  `#a1a1aa`, акцент — изумрудный primary.
- **Шрифт:** Rubik (regular/500/700) из `features/labels/fonts/`.
- **Постоянные элементы:** eyebrow-строка (тип сущности + контекст), заголовок
  (до 2 строк, кегль ступенчато уменьшается при длинном тексте), строка
  фактов, подвал: wordmark «NB» + домен.
- **Фирменный элемент:** вертикальная полоса цвета слева (SRM сущности — у
  рецепта/стиля/солода; SRM-спектр — у разделов и сущностей без цвета).
- **Без эмодзи** (Satori тянет их с CDN twemoji — внешняя зависимость и точка
  отказа). Иконки — инлайн-SVG (пути из lucide).
- Никаких пояснительных подписей-«объяснялок»: карточка = факты.

## 5. Карточки по типам страниц

Приоритет по продуктовой ценности: рецепты → калькуляторы → ингредиенты →
стили BJCP → статьи/мастера/beer → обложки разделов.

### 5.1 Рецепт `/recipes/[slug]` — Ф1

Данные уже в `generateMetadata` (`RecipeDetailDto` через `loadRecipe`):
title, стиль (`nameRu` + код BJCP), og/fg/abv/ibu, colorSrm, объём партии,
rating{average,count}, completedBrewCount, authorDisplayName, heroImageId.

```
┌────────────────────────────────────────────────────┐
│█                                                   │
│█  РЕЦЕПТ · ЧЕШСКИЙ ПРЕМИУМ ПИЛСНЕР · BJCP 3B       │ ← eyebrow
│█                                                   │
│█  Курский пилснер                                  │ ← title, ≤2 строки
│█                                                   │
│█  ABV 4.9%   IBU 35   OG 1.048   20 л              │ ← статы
│█  ★ 4.7 (12) · сварен 8 раз                        │ ← только если есть
│█                                                   │
│█  NB · <домен>                              (бокал)│
└────────────────────────────────────────────────────┘
 ↑ полоса srmToHex(colorSrm) на всю высоту; бокал — srmToGlassStops
```

- Фолбэки: нет стиля → eyebrow «РЕЦЕПТ»; нет рейтинга/варок → строка
  скрывается; нет colorSrm → нейтральная полоса.
- **Рецепт с фото (`heroImageId`): в v1 поведение не меняем** — фото остаётся
  `og:image` (как сейчас, `seo.ts:43-45`). Карточка генерится только когда
  фото нет (сегодня это большинство рецептов → строгое улучшение без
  регресса). Единая карточка с фото-врезкой — Ф5 (решение владельца принято:
  делаем; до Ф5 фото-рецепты временно остаются как сейчас).
- UGC-гейт `isRecipeIndexable` не трогаем: noindex не мешает превью в TG.

### 5.2 Калькуляторы `/calculators/[slug]` — Ф2 (v1) и Ф4 (v2)

**v1 — статичные брендовые карточки, 17 штук.** Роуты SSG
(`generateStaticParams`), данные — статический каталог
(`features/calculators/catalog.ts`: `shortTitle`, `seoTitle`, `description`).
Карточка: eyebrow «КАЛЬКУЛЯТОР ПИВОВАРА», название, 1 строка описания, иконка
раздела, wordmark. Генерится на билде — рантайм-стоимость нулевая.

**v2 — результат расчёта в превью.** Разведка подтвердила: share-ссылка несёт
полное состояние (`serializeCalculatorStateToQuery`,
`definitions.ts:2711`), и весь пайплайн server-safe:
`parseCalculatorQuery → initialCalculatorStateFromQuery →
definition.calculate(state)` → `CalculatorResult{primary, stats}` — готовые
русские строки. Движки — чистые функции `@nb/brewing-core`.

Конфликт: страницы калькуляторов **сознательно статические** (чтение
`searchParams` в `generateMetadata` их динамизирует — такую регрессию уже
ловили как P0). Решение — **не трогать основные страницы**:

- Новый тонкий динамический саброут `/calculators/[slug]/share?<query>`:
  `generateMetadata` читает query, считает результат, кладёт
  `og:image = /api/og/calculators/<slug>?<query>` и заголовок вида
  «Горечь пива: 42 IBU»; canonical — чистый `/calculators/<slug>` (текущая
  политика §4 seo-playbook сохраняется), robots noindex. Тело — тот же
  `CalculatorPageClient` (он и так читает query на клиенте).
- Кнопка «Скопировать ссылку на расчёт» (`calculator-page-client.tsx:2225`)
  начинает копировать `/share`-вариант.
- Карточка v2: primary-результат крупно («42 IBU»), под ним 2–3 ключевых
  входа мелко («OG 1.056 · 60 мин · 25 л»), имя калькулятора в eyebrow.
- `keg-carbonation` и `unit-converter` без кнопки шаринга
  (`showResultActions=false`) — остаются на v1-карточке.

### 5.3 Ингредиент `/catalog/[source]/[id]` — Ф2

Фото у ингредиентов нет вообще → карточка всегда генерённая. Данные уже в
metadata (`UserCatalogIngredientDto`): название RU, category/subtype, бренд,
страна, techData. Строка фактов по типу:

- хмель: `α 12–14% · гранулы · США`
- солод: `4–6 EBC · Курский солод · Россия` + полоса цвета из EBC
  (`ebc/1.97 → srmToHex`)
- дрожжи: `аттенюация 78–82% · 18–24°C · сухие`

Кастомные/архивные (noindex) — карточку тоже отдаём: noindex не влияет на
превью, а ссылками на кастомные делятся.

### 5.4 Стиль BJCP `/bjcp/[slug]` — Ф2

Данные в metadata (`ContentArticle` из `@nb/content`): `bjcpId`, title RU/EN,
`vitalStatistics` — диапазоны строками («1.044 – 1.052»), `colorBand`.
Карточка: eyebrow «СТИЛЬ BJCP · 3B», title RU + titleEn мелко, строка vitals
`OG 1.044–1.052 · IBU 30–45 · ABV 4.2–5.8%`, полоса-градиент цветового
диапазона стиля (по границам srm из vitals).

Сейчас у 128 стилей есть иллюстрации (`public/images/bjcp/*.png`) и реальное
фото уходит в og:image, а плейсхолдер отсекается
(`resolveHasRealHeroImage`). Как с рецептами: **фото остаётся, карточка — для
случаев плейсхолдера**; композиция иллюстрации в карточку — Ф5.

### 5.5 Статья `/articles/[slug]` — Ф2

Есть `coverImageUrl` → остаётся как есть. Нет обложки → карточка: eyebrow
«СТАТЬЯ», title, `readingMinutes` + дата, wordmark.

### 5.6 Мастер `/masters/[slug]` — Ф2

Есть фото галереи → остаётся. Нет → карточка: displayName, специализации,
город, eyebrow «МАСТЕРСКАЯ · МАРКЕТ NB».

### 5.7 Гостевая страница пива `/beer/[slug]` — Ф2

Страница уже динамическая (читает `?k` в metadata), фактов бутылки нет в
карточке, хотя они в query (`?b` дата розлива, `?n` партия, `?abv`) и DTO
(style, abv, ibu, colorSrm, og, author). Ссылку сканируют с QR на бутылке —
превью в TG здесь особенно уместно. Карточка: название, стиль + код, полоса
цвета, `ABV 5.2% · IBU 40`, «разлито 12.07.2026 · партия #14» (из query,
через существующий `parseBottleParams`), автор. `og:image` →
`/api/og/beer/<slug>?b=…&n=…&abv=…&k=…` (ключ `?k` нужен, чтобы роут отдал
карточку непубличного пива).

### 5.8 Обложки разделов — Ф3

`/`, `/recipes`, `/catalog` (+7 лендингов `/catalog/[source]`),
`/calculators`, `/bjcp`, `/articles`, `/market`, `/demo`, `/labels`,
`/brewforge`. Статичные генерённые обложки: название раздела + SRM-спектр
(`BJCP_SPECTRUM`) как фирменная полоса + wordmark. Лендингам каталога — свой
заголовок из `catalogCategoryLandings`. `/legal/*`, `/login` — остаются на
сайтовом дефолте.

## 6. Техническая архитектура

### Модуль

`apps/web/features/og/` (доменная логика — в features, по конвенции):

- `fonts.ts` — `readFile` Rubik TTF из `features/labels/fonts/` на module
  scope (один раз на инстанс). Файлы не дублировать; если захочется убрать
  cross-feature путь — поднять TTF в `apps/web/assets/fonts/` и поправить оба
  потребителя.
- `theme.ts` — цвета/размеры/константы карточек.
- `card.tsx` — базовые блоки под Satori: корень, eyebrow, title с
  автоподбором кегля, строка статов, полоса цвета, wordmark-подвал.
- `templates/*.tsx` — по шаблону на тип сущности (чистые функции
  `(данные) → JSX`, тестируемые без рендера).

### Два механизма доставки

| Механизм | Где применяем | Почему |
|---|---|---|
| **File convention** `opengraph-image.tsx` в сегменте | Калькуляторы v1 (SSG по `generateStaticParams`), обложки разделов (Ф3) | Страница не задаёт своих `openGraph.images` → конфликта нет; рендер на билде, Next сам проставляет `og:image` + width/height/alt |
| **Route handler** `app/api/og/<entity>/route.tsx` + явный URL в `seo.ts` | Рецепты, ингредиенты, BJCP, статьи, мастера, beer, калькуляторы v2 | Нужна логика «фото если есть, иначе карточка» и/или query-параметры. ⚠ File convention здесь нельзя: file-based metadata **перебивает** config-based — сгенерённая карточка вытеснила бы существующие фото-og:image |

В `seo.ts`-билдерах ставить `images: [{url, width: 1200, height: 630, alt}]`.

### Рантайм и Satori

- `runtime` — nodejs (дефолт; нужен `fs` для TTF). Edge не использовать.
- Satori = flexbox-подмножество CSS: `display` только flex/contents/none
  (не block!), div с несколькими детьми обязан быть flex; нет grid, calc(),
  z-index; кириллица — только из переданного TTF. Держать шаблоны примитивными.
- `emoji`-опцию не задействовать (CDN-зависимость).

### Кэширование

- File convention наследует segment config → калькуляторы/разделы
  генерятся на билде.
- Route handlers: `revalidate` в тон сущности (рецепты 300 как у страницы,
  BJCP 3600) либо `Cache-Control: public, s-maxage=…`; для query-зависимых
  (calc v2, beer) — `s-maxage=3600` по полному URL. TG всё равно кэширует на
  своей стороне.
- Инвалидация TG-кэша при редизайне карточек — версия в URL
  (`?v=2`) дешевле, чем сброс через @WebpageBot по одной ссылке.

### Устойчивость и бюджет веса

- Любой генератор — в try/catch; при ошибке отдавать простую
  wordmark-карточку (`ImageResponse` из констант), **никогда 500** — иначе
  мессенджер покажет превью без картинки.
- Плоский дизайн → PNG ~30–150 КБ. Порог: **≤ 300 КБ**; юнит-тест рендерит
  каждый шаблон с максимально длинными строками и ассертит размер буфера и
  PNG-сигнатуру (паттерн самопроверки уже есть в
  `scripts/generate-og-image.mjs` — `assertNotFlat`/`assertExactSize`).
- Длинные названия: кламп 2 строки + ступени кегля 64→52→44 по длине
  (метрики строк — простая эвристика по количеству символов, opentype.js не
  тащить).

### Что НЕ делаем

- Не читаем `searchParams` в metadata статических страниц (SSG-инвариант).
- Не тянем шрифты/эмодзи/картинки с внешних CDN — всё из репо/стораджа.
- Не заводим новые зависимости (satori/@vercel/og уже в next).

## 7. Правки метаданных (сопутствующие)

1. `recipes/seo.ts` (Ф1, сделано): `twitter.card` всегда `summary_large_image`
   — у рецепта картинка есть всегда (фото или генерённая карточка).
   ⚠ **Важно (проверено вживую):** сайтовый дефолт `app/opengraph-image.png`
   **НЕ наследуется** листом, если лист задаёт свой `openGraph` без `images`
   (Next пересобирает openGraph только из листа). Значит поднимать
   `twitter.card` до `summary_large_image` у статей/мастеров **нельзя, пока у
   них нет своей картинки** — иначе получится большая пустая карточка. Поэтому
   `content-articles/seo.ts` и `masters/seo.ts` остаются на условном
   `hasCover ? summary_large_image : summary` — их `summary_large_image`
   включится в **Ф2**, когда появится генерённая карточка.
2. Генерённый og:image — с `og:image:alt` (заголовок) и width/height=1200×630
   (Ф1, сделано). ⚠ width/height ставить ТОЛЬКО на генерённую карточку; фото
   рецепта произвольного аспекта — без размеров (иначе врём WhatsApp/VK).
3. `/articles` (список) — добавить openGraph (Ф2/Ф3).

## 7a. Хардненинг route-хендлера (Ф1, сделано — из адверс-ревью)

- **Rate-limit:** публичный Satori-рендер троттлится per-IP (`assertIpRateLimit`,
  `og_render` 300/5мин); при превышении → 302 на статичный
  `/opengraph-image.png`, не 429 (сломанное превью в чате).
- **Тонкая выборка:** `getPublicRecipeOgData` (не тяжёлый `getPublicRecipeBySlug`
  с N+1 по ингредиентам) — карточке нужны только скаляры+рейтинг+число варок.
- **NOT_FOUND:** дешёвый 302 на статику, БЕЗ Satori-рендера (иначе поток
  случайных slug = амплификатор DoS).
- **Фолбэк обёрнут:** если и фолбэк-рендер упадёт (напр. шрифты) → 302 на
  статику; эндпоинт никогда не отдаёт 500. TTF внесены в
  `outputFileTracingIncludes` для standalone-сборки.
- **Эмодзи:** вырезаются из названия рецепта (Satori тянул бы twemoji с CDN →
  битый рендер без egress).
- **Остаточный риск (P3):** ошибки Satori всплывают при чтении стрима, `try/catch`
  route их не ловит; держится на статически-валидной flat-раскладке `card.tsx`.
  При правках `card.tsx` соблюдать flex-инвариант (у каждого div с >1 ребёнком
  `display:flex`).

| Этап | Состав | Приёмка |
