# ТЗ: Сторонние устройства ферментации (iSpindel, RAPT Pill, Tilt и совместимые)

Статус: черновик на согласование · Дата: 2026-07-14
Связанные документы: `docs/brewforge-integration.md`, `docs/brewery-command-center-l2-redesign.md`, `notes/PROJECT-BRIEF.md`

---

## 1. Суть

Портал принимает телеметрию ферментации от популярных сторонних устройств — цифровых
ареометров-поплавков (iSpindel, GravityMon, RAPT Pill, Tilt, Floaty) и термоконтроллеров
(BrewPiLess и совместимые) — и превращает её в живой график брожения на странице партии,
вердикт «похоже, добродило» и уведомления. Управлять чужим железом мы не пытаемся:
скоуп — **только приём данных** (read-only телеметрия). Управление остаётся привилегией BrewForge.

Ключевой рычаг: в нише сложились де-факто стандарты пуш-форматов («iSpindel generic HTTP»
и «Brewfather custom stream»). Один наш ingest-эндпоинт, понимающий оба, разом даёт
совместимость с десятком прошивок без партнёрств и SDK.

### Цели
1. Пользователь подключает свой поплавок за ≤5 минут без чтения документации.
2. Кривая брожения (плотность + температура) живёт на странице партии и обновляется сама.
3. Портал подсказывает: «брожение не началось», «затык», «похоже, добродило», «температура ушла».
4. Данные устройства **всегда** можно поправить: сдвинуть по ручному замеру, исключить шум,
   обрезать диапазон, удалить.
5. Всё то же самое доступно и без устройств — руками, без деградации UX.

### Не-цели (осознанно вне скоупа)
- Управление сторонними устройствами (уставки, команды) — только чтение.
- Bluetooth-шлюзы и мобильные приложения-мосты — пользователь использует штатные
  (приложение Tilt 2, TiltPi/TiltBridge, Wi-Fi самих устройств).
- Кег-мониторы, счётчики розлива, Plaato (снят с производства) — не в этой итерации.
- Grainfather / Inkbird / Speidel — закрытые экосистемы без официального API.
- Публичный API наружу (мы принимаем данные, а не раздаём).
- Telegram-уведомления — отдельное ТЗ (здесь только web-push по существующей инфраструктуре).
- Контракт `@nb/brewforge-protocol` **не трогается вообще** — сторонние устройства идут
  через отдельный generic-контракт (совместимость с прошивками в поле не затрагивается).

## 2. Термины

| Термин | Значение |
|---|---|
| Поплавок / гравиметр | Цифровой ареометр в ферментере: шлёт плотность+температуру раз в 15–60 мин |
| Стрим-устройство | Любое устройство, пушащее нам телеметрию по HTTP (в отличие от BrewForge с двусторонним протоколом) |
| Сеанс (session) | Период привязки устройства к конкретной партии: «этот поплавок сейчас в этом пиве» |
| Ingest | Публичный HTTP-эндпоинт приёма телеметрии |
| Ручной замер | Запись в `brew_measurements` (ареометр/рефрактометр руками) — **источник истины** для OG/FG |

⚠ Терминология UI («поплавок» vs «гравиметр» vs «ареометр») — на решение владельца,
см. открытые вопросы §14. В тексте ТЗ дальше — «поплавок».

## 3. Продуктовые принципы

Эти принципы — критерии приёмки для каждого экрана фичи.

**П1. Device-optional.** Ни один экран не деградирует без устройства. График брожения
строится и по одним ручным замерам; вердикт «добродило» работает по ручным замерам
(грубее, но работает); кнопка «Добавить замер» всегда первична, поплавок — усилитель.
Никаких пустых блоков-заглушек «подключите устройство, чтобы увидеть график» — если данных
нет вообще, блок компактный и не кричит.

**П2. Ручные данные главнее автоматики.** Поплавки — трендовые приборы (±0.002–0.005 SG,
дрейф от крауйзена и CO₂ на корпусе, углы калибровки). Поэтому:
- OG и FG партии определяются ручными замерами; кривая устройства их **никогда не перезаписывает**;
- всё, что автоматика «предлагает» (OG с кривой, FG-кандидат), становится записью только
  после явного подтверждения пользователем;
- при расхождении кривой и ручного замера прав ручной — и мы предлагаем выровнять кривую (П3).

**П3. Коррекция всегда доступна.** Пользователь может: сдвинуть кривую сеанса по своему
замеру (offset-калибровка), исключить точки/диапазоны (шум, крауйзен, доставали поплавок),
обрезать начало/конец сеанса, отвязать/перепривязать сеанс к другой партии, удалить данные.
Все коррекции обратимы (кроме удаления — оно через `ConfirmActionDialog`).

**П4. Прозрачность качества данных.** Всегда видно: когда устройство выходило на связь
в последний раз, батарея, сигнал, есть ли пропуски в данных. Ветхие данные (нет связи
дольше 3× интервала) помечаются явно, а не выглядят свежими.

**П5. Безопасный розлив.** Вердикт «похоже, добродило» — информационный. Рядом всегда
подпись «Перед розливом подтвердите плотность ареометром»: недоброд в бутылке под пробкой —
это бомбы. Никогда не формулируем как «можно разливать».

## 4. Поддерживаемые устройства и волны

### Волна 1 — generic HTTP ingest (закрывает большинство устройств разом)

| Устройство | Формат пуша | Примечания |
|---|---|---|
| iSpindel (сток-прошивка) | iSpindel native JSON | Самый массовый DIY-поплавок в RU |
| GravityMon (альт. прошивка iSpindel) | iSpindel native / Brewfather stream | Умеет HTTPS, шлёт `gravity-unit` |
| Tilt (через приложение Tilt 2 / TiltPi / TiltBridge) | Tilt cloud logging | BT-only, пушит штатный шлюз; °F и Excel-дата |
| Floaty | Brewfather stream | Дешёвый BLE, пушит его приложение |
| BrewPiLess | Brewfather stream | Термоконтроллер: температуры без плотности |
| MyBrewbot, PressureMon, прочий DIY | Brewfather stream | Поля pressure/ph принимаем в raw |

### Волна 2 — RAPT Cloud (KegLand)

| Устройство | Канал | Примечания |
|---|---|---|
| RAPT Pill | Вебхук RAPT-портала → наш ingest | Известный гэп из ресёрча болей («пилюли») |
| RAPT Temperature Controller / Fermentation Chamber | тот же вебхук | Температуры, уставка |
| BrewZilla Gen 4 | тот же вебхук | Телеметрия варки — храним, UI позже |

Вебхуки — основной канал (пуш от их облака на наш URL). Поллинг `api.rapt.io` по
API-секрету — опциональное дополнение для бэкфилла истории (§9.4).

### Волна 3 — не в этой итерации
Кег-мониторы (KegMon, Kegtron), pH-метры, Telegram-бот-приём. Заготовки не делаем.

## 5. User flows

### F1. Подключение устройства

Точка входа: `/app/devices` → кнопка «Подключить устройство» (заменяет текущую, заточенную
только под BrewForge). Шаг 1 — выбор типа:

```
Что подключаем?
● BrewForge — контроллер варки            [существующий флоу claim-кода, без изменений]
● Поплавок или датчик — iSpindel, Tilt, Floaty, BrewPiLess…   [новый флоу, ниже]
● RAPT Cloud — Pill, камера ферментации, BrewZilla            [флоу §F1-RAPT]
```

**Флоу «Поплавок/датчик» (generic stream):**
1. Имя устройства (обязательное, дефолт «iSpindel», «Tilt» по выбранному виду) + вид
   устройства (iSpindel / GravityMon / Tilt / Floaty / BrewPiLess / другое). Вид влияет
   только на иконку и текст инструкции — формат пакета детектится автоматически (§8.2).
2. Создали запись → экран подключения:
   - **URL для вставки в устройство** (крупно, кнопка «Скопировать»):
     `https://<host>/api/ingest/<token>`
   - инструкция по выбранному виду (сворачиваемая): для iSpindel — куда в конфигураторе
     вставить (Server Address / URL / Token), для GravityMon — раздел HTTP Push,
     для Tilt — «Настройки → Use Custom Cloud URL» (и рекомендация TiltPi/TiltBridge,
     т.к. телефон должен быть рядом с ферментером), для BrewPiLess — Remote logging.
   - **Живая зона «Ждём первый пакет…»** (поллинг раз в 5 сек): как только пакет пришёл —
     `✅ Данные пошли: 1.048 · 19.3 °C · батарея 4.1 В` и кнопка «Готово».
     Это ключевой момент доверия: пользователь уходит с экрана, только увидев данные.
3. URL можно посмотреть повторно со страницы устройства («Показать URL») — токен храним
   обратимо зашифрованным по образцу BrewForge (`tokenEncrypted`, AES-256-GCM,
   `lib/device-token-crypto.ts`). Там же — «Перевыпустить URL» (ротация токена, старый
   умирает сразу; подтверждение через `ConfirmActionDialog`).

**F1-RAPT:**
1. Создаём «Подключение RAPT» (одно на пользователя): экран показывает
   - URL вебхука: `https://<host>/api/ingest/rapt/<token>`;
   - готовый шаблон payload с @-переменными RAPT для копирования (§8.4);
   - пошагово: RAPT-портал → Integrations → Web Hooks → New, метод POST, вставить URL и шаблон.
2. Устройства **обнаруживаются автоматически** по первому пакету (`@device_id`):
   появляется плитка «RAPT Pill — обнаружен» с предложением переименовать.
   Отдельно «добавлять Pill руками» не нужно.
3. Живая зона ожидания первого пакета — та же, что в generic-флоу.

**Демо-режим:** рядом с существующим демо BrewForge — «Попробовать с виртуальным
поплавком»: создаёт стрим-устройство, которому dev-скрипт (§12, `sim:ispindel`) шлёт
реалистичную кривую. Доступно и в проде (кормится изнутри), позволяет пощупать фичу без железа.

### F2. Привязка к партии (сеансы)

Модель: сеанс = (устройство, партия, начало, конец|null, offset-калибровка). Одно
устройство — максимум один активный сеанс; у партии может быть несколько сеансов,
в т.ч. параллельных (Pill + iSpindel для сверки — легитимный сценарий).

Точки входа (все три обязательны):
1. **Перевод партии в «Брожение»** (status → `fermenting`): если у пользователя есть
   свободные стрим-устройства — необязательный шаг «Поплавок уже в сусле?» со списком.
   Пропускается одним тапом, ничего не блокирует (П1).
2. **Страница партии**, блок «Брожение»: компактная строка «Подключить поплавок» рядом с
   «Добавить замер» (не кричащий блок).
3. **Карточка устройства**: «Привязать к партии» → селектор партий в статусе
   `fermenting`/`brewing` (свежие сверху).

**Ретро-привязка данных.** Частый реальный случай: поплавок кинули в сусло в день варки,
партию в «Брожение» перевели через день. При создании сеанса, если у устройства есть
непривязанные показания за последние 7 дней, предлагаем: «Забрать данные с …
(за N часов, M точек)?» — старт сеанса ставится назад, точки доприсваиваются сеансу.

**Завершение сеанса:** вручную с карточки/партии; мягкий промпт при переводе партии в
`completed` («Завершить сеанс поплавка?»); автозавершение после 7 дней молчания устройства
(с пометкой «завершён автоматически»). Конец сеанса освобождает устройство для следующей партии.

### F3. Наблюдение

**Страница партии, блок «Брожение»** (главный экран фичи):
- График: ось Y1 — плотность в единицах пользователя (SG/Plato/Brix — существующая система
  `features/system/gravity-units`), ось Y2 — температура. Серии:
  - кривая устройства (при отрисовке сглаживается скользящей медианой по 5 точкам — хранение
    сырое, сглаживание только на чтении);
  - **ручные замеры — точками поверх кривой** (это визуальное воплощение П2);
  - температура — тонкой линией; давление (если устройство шлёт) — третья серия, скрытая по умолчанию;
  - исключённые точки — полупрозрачные (тумблер «показать исключённые»);
  - разрывы данных >3× интервала — разрыв линии, не интерполяция (П4).
- Диапазоны: 24 ч / 7 д / всё.
- Сводка над графиком: текущая плотность, видимая степень сбраживания, оценка ABV
  (от подтверждённого OG), температура, статус-вердикт (§F5).
- Несколько сеансов → несколько кривых с легендой по имени устройства.
- **Без устройства блок выглядит так же**: график по ручным замерам, та же сводка (П1).
  Сейчас замеры отображаются списком — график по ручным замерам делаем в этой же фиче.

**Дашборд `/app`, виджет устройств:** плитки стрим-устройств встают рядом с BrewForge:
имя, вид-иконка, последние SG/°C, батарея, ссылка на партию, «N мин назад». Ветхость — серым
с явным «нет связи 4 ч» (П4). Расширяется `listDeviceTiles` (`features/devices/tiles.ts`).

**Карточка устройства** `/app/devices/[id]` (для стрим-устройств — свой лэйаут, без пульта):
график всех данных с разбивкой по сеансам, статус связи/батарея/RSSI, история сеансов
(партия → период → итог), настройки (§F8).

### F4. Коррекция данных (сердце ТЗ — П3)

1. **«Выровнять по моему замеру»** (offset-калибровка сеанса). Кнопка в блоке «Брожение»
   рядом с ручным замером: берём ручной замер, находим показание устройства на тот же момент
   (интерполяция соседних точек), `offset = ручное − устройство`, сохраняем на сеансе.
   Применяется на чтении ко всей кривой сеанса; на графике бейдж «Кривая скорректирована
   на +0.003» с отменой. Хранится одна актуальная величина (не история офсетов) — простая
   ментальная модель: «кривая выровнена по последнему замеру».
2. **Исключение точек**: выделение диапазона на графике (brush) → «Исключить точки»
   (`excluded=true`). Исключённые не участвуют в вердикте, сводке и сглаживании. Обратимо.
   Типовые случаи: первые часы (пена, поплавок «ловит место»), доставали для дегустации,
   крауйзен налип.
3. **Границы сеанса**: изменить начало/конец задним числом (обрезать шум до задачи дрожжей).
4. **Подтверждение OG/FG с кривой**: когда кривая стабильна в начале (первые часы) или в
   конце — предлагаем «Записать OG 1.052 с поплавка?» → по подтверждению создаётся обычная
   запись в `brew_measurements` с пометкой «с устройства». Автоматически — никогда (П2).
5. **Удаление**: точек диапазона / всех данных сеанса / устройства целиком (каскад).
   Всё через `ConfirmActionDialog` с числом удаляемых точек.

Все правки числовых значений — через `NumericInput`.

### F5. Вердикт состояния брожения

Показывается в сводке блока «Брожение» (и в плитке устройства кратко). Считается по
сглаженной кривой сеанса без исключённых точек; при отсутствии устройства — по ручным
замерам (грубее: нужно ≥2 замеров). Правила (эвристики, чистое ядро `verdict-core.ts`):

| Вердикт | Условие (по умолчанию) |
|---|---|
| «Ждём начала брожения» | <36 ч от старта, падение <0.003 SG |
| «Брожение не началось?» ⚠ | ≥36 ч от старта и падение <0.003 SG → совет проверить дрожжи |
| «Бродит активно» | падение ≥0.002 SG/сутки |
| «Дображивает» | падение <0.002/сутки, но >0.0005/сутки |
| «Возможен затык» ⚠ | стабильность 48 ч на уровне >0.010 SG выше расчётного FG (если FG известен из снапшота рецепта) |
| «Похоже, добродило» | изменение ≤0.0015 SG за 48 ч и (если FG известен) в пределах 0.005 от расчётного |

К вердикту «похоже, добродило» всегда прилагается: «Стабильно N дней. Перед розливом
подтвердите плотность ареометром» (П5) + ссылка «Перейти к розливу» → существующий
калькулятор карбонизации/праймера с предзаполненными FG и температурой.
Пороги — константы ядра; в UI не настраиваются (MVP).

### F6. Уведомления (web-push, существующая инфраструктура `push_subscriptions`)

| Триггер | Условие | Где считается |
|---|---|---|
| Брожение не началось | вердикт «не началось?» впервые за сеанс | на ingest |
| Возможен затык | вердикт «затык» впервые за сеанс | на ingest |
| Похоже, добродило | вердикт «добродило» впервые за сеанс | на ingest |
| Температура вне коридора | выход за коридор сеанса на >30 мин | на ingest |
| Батарея садится | <3.4 В (li-ion) или <20 % | на ingest |
| Поплавок молчит | нет пакетов >2 ч (при известном интервале — >6× интервала) | периодический скан в bridge |

Температурный коридор сеанса: берётся из ferment-профиля снапшота рецепта партии, если
есть; иначе задаётся на сеансе руками (два `NumericInput`); иначе алерт выключен.
Дедуп: не чаще одного пуша данного типа на сеанс за 12 ч; «молчит» — один раз до
восстановления связи. Скан «молчит» — в `apps/bridge` (он always-on и уже умеет
ferment-watchdog/cloud-deadman для BrewForge; тот же паттерн).

### F7. Паритет «без устройства»

Проверочный список (обязателен при приёмке каждого милстоуна):
- график брожения строится по одним ручным замерам;
- вердикт считается по ручным замерам при ≥2 точках;
- «Перейти к розливу» с предзаполнением работает от ручного FG;
- ни одной кнопки/блока, которые без устройства выглядят обрубком или рекламой железа.

### F8. Управление устройством

Страница устройства → настройки: переименовать; сменить вид (иконка/инструкция);
показать URL; перевыпустить URL (ротация токена); удалить устройство (каскад данных,
`ConfirmActionDialog` с числом точек и сеансов). Для RAPT-подключения дополнительно:
показать/перевыпустить URL вебхука, удалить подключение целиком.

## 8. Ingest API

### 8.1 Эндпоинты

```
POST /api/ingest/[token]          -- generic: iSpindel native | Brewfather stream | Tilt logging
POST /api/ingest/rapt/[token]     -- вебхук RAPT (наш шаблон payload)
GET  /api/ingest/[token]          -- 200 {"ok":true} без записи: проверка URL из браузера
```

Токен в path — вынужденно: iSpindel/Tilt не умеют заголовки. Next.js route handlers в
`apps/web` (не в bridge: HTTP-приём — это веб-слой; bridge остаётся про MQTT/WS BrewForge).

### 8.2 Автодетект формата (по полям тела)

| Признак | Формат |
|---|---|
| есть `angle` и `temperature` | iSpindel native |
| есть `name` и (`temp` или `gravity`), поля `temp_unit`/`gravity_unit` | Brewfather stream |
| есть `SG` и `Temp` (+`Timepoint`/`Color`) | Tilt cloud logging |
| иначе | 400 `{ok:false, error:"unknown_format"}` |

Парсеры — чистое ядро `features/device-streams/parse-core.ts` (колокированные тесты без БД,
конвенция `*-core.ts` как `fermenter-binding-core.ts`). Эталонные пакеты:

```jsonc
// iSpindel native (сток и GravityMon)
{"name":"iSpindel000","ID":4974097,"angle":83.49,"temperature":21.44,"temp_units":"C",
 "battery":4.03,"gravity":30.29,"interval":900,"RSSI":-76}
// gravity: SG ИЛИ Plato — см. §8.3; GravityMon может добавить "gravity-unit":"G"|"P"

// Brewfather custom stream
{"name":"Floaty01","temp":19.2,"temp_unit":"C","gravity":1.048,"gravity_unit":"G",
 "pressure":0,"pressure_unit":"PSI","ph":0,"battery":3.9}

// Tilt cloud logging (шлёт приложение Tilt 2 / TiltPi; ⚠ сверить живым прогоном при реализации)
{"Timepoint":45123.52,"Temp":68.5,"SG":1.048,"Beer":"Untitled","Color":"BLACK","Comment":""}
// Temp — °F, Timepoint — Excel-серийная дата
```

### 8.3 Нормализация единиц (`normalize-core.ts`)

- Плотность → SG: если есть явный unit (`gravity_unit` / `gravity-unit`: G|P) — по нему;
  иначе эвристика: значение >1.2 → Plato (SG физически ≤~1.2), ≤1.2 → SG. Brix не шлёт
  никто из перечисленных — не поддерживаем на входе.
- Температура → °C: `temp_units`/`temp_unit` C|F; Tilt — всегда °F.
- Давление → кПа (PSI×6.8948).
- Батарея: value ≤6 → вольты (`battery_v`), >6 → проценты (`battery_pct`).
- Плаузибилити-клампы: SG вне [0.980, 1.200] или temp вне [−10, 50] °C → точка сохраняется
  в payload, но нормализованные поля NULL (мусор с датчика не должен ломать график и вердикт).

### 8.4 RAPT-вебхук

Мы даём пользователю готовый шаблон payload (копируется с экрана подключения):

```json
{"device_id":"@device_id","device_type":"@device_type","device_name":"@device_name",
 "temperature":"@temperature","gravity":"@gravity","battery":"@battery",
 "rssi":"@rssi","ts":"@created_date"}
```

Приём: по `device_id` находим/создаём `brew_devices` (providerId `rapt-cloud`,
hardwareId `rapt-<id>`, hardware_kind по `device_type`, name из `device_name`).
Новое устройство → плитка «обнаружен» (F1-RAPT). Значения приходят строками — парсим числа
терпимо. `gravity` RAPT — SG, `temperature` — °C.

### 8.5 Защита и дисциплина приёма

- **Auth:** токен из path → sha256 → поиск по `token_hash` (существующий паттерн
  `findDeviceByToken`). Нет — 404 (не 401: не раскрываем существование токенов).
- **Rate limit:** существующий механизм квот/рейт-лимитов (abuse-hardening): на токен —
  burst 6 / 12 в минуту; на IP — общий потолок. Превышение → **200 `{ok:true,stored:false}`**,
  не 429: прошивки на 4xx/5xx уходят в агрессивные ретраи и жрут батарею поплавка.
- **Персист-гейт:** пишем не чаще 1 точки/5 мин на устройство (сравнение с `max(ts)`
  последней записи в БД — без in-memory-состояния, безопасно при мультиинстансе).
  Пакет чаще — валидируем, отвечаем ok, обновляем `lastSeenAt`, но не пишем строку.
- **Лимиты:** тело ≤4 КБ; ≤10 стрим-устройств на пользователя (квота через существующую
  систему); авто-создание RAPT-устройств — тот же лимит.
- **Идемпотентность:** RAPT может ретраить вебхук — дедуп по (device_id, ts источника)
  `onConflictDoNothing` при точном совпадении ts.
- **Ответы:** успех `200 {"ok":true}`; неизвестный формат — 400; чужой/мёртвый токен — 404.
  Никаких редиректов (устройства их не умеют).

## 9. Сервис-слой

Новая фича `apps/web/features/device-streams/`:

```
contracts.ts        -- zod-схемы DTO: SessionDto, ReadingDto, VerdictDto, ConnectStreamInput…
parse-core.ts       -- детект+парс трёх форматов (чистое ядро + тест)
normalize-core.ts   -- единицы/клампы (чистое ядро + тест)
verdict-core.ts     -- вердикты F5 по массиву точек (чистое ядро + тест)
service.ts          -- ingest-запись, CRUD устройств/сеансов, коррекции F4, чтение серий для графика
alerts.ts           -- триггеры F6 на ingest + дедуп
actions.ts          -- server actions для UI
components/         -- визард подключения, блок «Брожение», графики, коррекции
```

Правила:
- чтение серий отдаёт точки уже с применённым `calibration_offset_sg` и без excluded
  (флагом можно запросить всё — для экрана коррекции);
- вердикт и сводка считаются на сервере (`verdict-core`), клиент получает готовый DTO;
- ручные замеры остаются в `features/brew-batches` — device-streams их **читает** для
  наложения на график и офсета, но не владеет ими;
- график: переиспользовать/обобщить `ferment-history-chart.tsx` из brew-controller
  (решение «обобщить vs скопировать» — на реализации, см. открытые вопросы).

## 13. Безопасность

- Токены: 32 байта случайности, hex; в БД — sha256 (`tokenHash`) + AES-256-GCM
  (`tokenEncrypted`) по существующим паттернам; показ URL — только владельцу.
- Ingest не принимает ничего, влияющего на управление: только числа телеметрии (никаких
  команд, никакого SSRF — мы никуда не ходим по данным из пакета).
- Компрометация токена = возможность спамить телеметрией одной кривой → ротация в один клик
  (F8), rate limit ограничивает ущерб.
- `payload` jsonb рендерится только как форматированный текст (не HTML).
- Квоты создания устройств — через существующий атомарный барьер abuse-hardening.
