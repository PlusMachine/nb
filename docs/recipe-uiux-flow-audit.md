# Recipe UI/UX Flow Audit

Дата: 2026-03-14
Среда проверки: локальный dev на `http://localhost:3100`
Пользователь: `qa.admin@localhost`

## Что это за интерфейс сейчас

Текущие страницы `recipe/new` и `recipe/[id]/edit` не являются пошаговым мастером.
Фактически это один большой single-page designer:

- сверху sticky summary bar с основными полями и кнопкой сохранения
- ниже live preview расчётов
- ниже описание и заметки
- ниже секции ингредиентов по категориям
- ниже process profile
- добавление и редактирование ингредиентов происходит не inline, а в отдельной модалке/overlay

Это важно для дизайнера: пользователь не проходит линейный сценарий "шаг 1 -> шаг 2 -> шаг 3", а работает в длинном редакторе со множеством зон внимания.

## Карта экранов

- `/app/recipes` — список рецептов
- `/app/recipes/new` — создание
- `/app/recipes/[id]` — просмотр detail
- `/app/recipes/[id]/edit` — редактирование
- `/recipes/[slug]` — публичная страница

## 1. Список рецептов: `/app/recipes`

### Что пользователь видит

- Заголовок `Мои рецепты`
- Справа primary CTA `Создать рецепт`
- Подзаголовок про статус и ключевые показатели
- Ниже список карточек рецептов

Каждая карточка рецепта содержит:

- badge статуса: `Черновик`, `Личный`, `Публичный`
- дату/время обновления
- название рецепта
- краткую строку: объём партии + время кипячения
- блок `Ключевые показатели` с 5 карточками:
  - `OG`
  - `FG`
  - `ABV`
  - `IBU`
  - `Color`
- строку действий:
  - `Открыть рецепт`
  - `Редактировать`
  - `Клонировать`
  - `Публичная страница` если рецепт опубликован
  - `Удалить`

### Что делает пользователь

- может перейти к detail view
- может сразу перейти в edit
- может клонировать рецепт и попасть в edit нового клона
- может удалить рецепт через confirm dialog
- может открыть публичную страницу опубликованного рецепта

### UX-наблюдение

Список сам по себе информативный, но перегружен для mobile:

- у каждой карточки есть крупный stats block
- затем ещё и строка из 4-5 действий
- при длинном списке это превращается в тяжёлую ленту

## 2. Создание рецепта: `/app/recipes/new`

### Начальное состояние экрана

Пользователь видит:

- заголовок `Recipe Designer`
- описание: `Компактный summary-first designer с живым пересчётом draft и редакторами по требованию.`

Сразу под ним sticky верхняя панель с полями:

- `Название рецепта`
- `Стиль BJCP`
- `Объём партии`
  - число
  - единица измерения (`ml`, `l`, `gal`)
- `Эффект., %`
- `Кипяч., мин`
- `Состояние`
  - `Черновик`
  - `Личный`
  - `Публичный`
- кнопка `Сохранить`
- кнопка `К списку`

### Значения по умолчанию

- title: пусто
- style: не выбран
- batch size: `20 l`
- efficiency: `75`
- boil time: `60`
- publication state: `Черновик`
- description: пусто
- author notes: пусто
- mash profile:
  - 1 шаг
  - `Основной настой`
  - `67 °C`
  - `60 мин`
- fermentation profile:
  - primary temp `20`
  - primary duration `10`
  - cold crash disabled, но поля уже видны с `2 °C / 2 дня`
  - conditioning disabled, но поля уже видны с `12 °C / 14 дней`

### Что пользователь видит сразу после открытия

1. В статусной строке сверху отображается зелёный badge `Все изменения сохранены`.
2. Ниже live preview `Стиль и расчёт`.
3. На пустом рецепте preview сообщает:
   - `Добавьте хотя бы одно сбраживаемое; для IBU понадобится ещё и хмель.`
   - все метрики `—`
4. Затем два больших textarea:
   - `Описание рецепта`
   - `Личные заметки`
5. Затем секции ингредиентов:
   - `Сбраживаемое`
   - `Хмель`
   - `Дрожжи`
   - `Водоподготовка`
   - `Прочее`
6. Затем process blocks:
   - `Mash Profile`
   - `Fermentation Profile`

### Как пользователь начинает создавать рецепт

Текущий интерфейс не подсказывает жёсткий порядок, но фактически у пользователя есть два естественных старта:

- путь A: сначала заполнить верхнюю панель
- путь B: сразу идти в ингредиенты и нажимать `Добавить`

На практике сейчас designer толкает в path B только косвенно, через пустые секции ингредиентов и пустой preview.

### Как работает сохранение при создании

- Сохранение всегда ручное
- autosave нет
- live recalculation есть, но это только preview, не save
- при изменении данных включается badge `Есть несохранённые изменения`
- при попытке закрыть вкладку появляется browser confirm
- при нажатии `К списку` при dirty-state появляется confirm

### Что происходит после сохранения

- если рецепт сохранён как `Черновик`, пользователь остаётся не на detail page, а переводится на `/app/recipes/[id]/edit`
- если рецепт сохранён как `Личный` или `Публичный`, пользователь переводится на `/app/recipes/[id]`

То есть create flow меняет маршрут в зависимости от publication state.

Это важный UX-нюанс: у пользователя нет одного стабильного пост-save destination.

## 3. Как пользователь добавляет ингредиенты

### Общий принцип

Категория ингредиента выбирается не внутри модалки, а раньше:

- пользователь нажимает `Добавить` в нужной секции
- из этого секционного контекста уже определяется тип будущего ингредиента

Примеры:

- `Сбраживаемое -> Добавить`
- `Дрожжи -> Добавить`
- `Водоподготовка -> Добавить`
- `Прочее -> Добавить`

Для хмеля flow другой:

- секция `Хмель` разбита на подпотоки
  - `Кипячение`
  - `Whirlpool / Hopstand`
  - `Dry Hop`
  - `Dip Hop`
  - `Другое`
- у каждого подпотока своя кнопка `Добавить`
- этим действием заранее задаётся use type хмеля

### Как выглядит editor ингредиента

После нажатия `Добавить` открывается overlay/modal.

На desktop:

- модалка по центру
- `max-width: 3xl`
- overlay затемняет весь экран

На mobile:

- тот же editor превращается в нижнюю sheet-like панель
- выезжает снизу
- занимает всю ширину
- max-height около `92vh`

### Базовые поля ингредиента

Во всех категориях пользователь видит:

- заголовок:
  - `Новая позиция` или `Редактор позиции`
- подпись категории
- поле `Ингредиент`
  - это search input с автоподсказками
- поле `Количество`
- поле `Ед. изм.`

Под полем `Ингредиент` есть пояснение:

- если ингредиент выбран: показывается summary/family/subtitle
- если не выбран: текст `Сначала выберите ингредиент из каталога или создайте свой.`

### Как работает поиск ингредиента

- поиск начинается только когда пользователь вводит текст
- debounce около `180ms`
- максимум `8` результатов
- результаты приходят из `/api/ingredients/search`
- input поддерживает keyboard navigation:
  - `ArrowDown`
  - `ArrowUp`
  - `Enter`
  - `Escape`

### Если ингредиент не найден

Внутри модалки появляется empty-state с двумя CTA:

- `Создать свой ингредиент`
- `Предложить ингредиент в каталог`

Это хороший функциональный ход, но он спрятан в empty state, то есть discoverability низкая.

### Специфические поля по категориям

#### Сбраживаемое

Дополнительные поля:

- `Использование`
  - `Затор`
  - `Настой`
  - `Кипячение`
- если выбран `Кипячение`:
  - `Минут от конца`

#### Хмель

Дополнительные поля:

- `Тип добавления`
  - `Кипячение`
  - `Whirlpool / Hopstand`
  - `Dry Hop`
  - `Dip Hop`
  - `Другое`

Дальше поля меняются динамически:

- для `boil`, `whirlpool`, `dip_hop`
  - `Минут`
- для `dry_hop`
  - `Длительность, дн`
- для `other`
  - `Stage label`
- для `whirlpool` и `dip_hop` дополнительно
  - `Температура, °C`

#### Дрожжи

Дополнительные поля:

- `Основная температура брожения, °C`
- справа информационный блок с summary дрожжей или fallback-текстом

#### Водоподготовка и Прочее

Дополнительные поля:

- `Стадия`
  - `Затор`
  - `Кипячение`
  - `Whirlpool`
  - `Ферментация`
  - `Розлив`
  - `Другое`
- `Время, если нужно`

### Кнопки в модалке ингредиента

- `Удалить` если это редактирование существующей позиции
- `Отмена`
- `Добавить позицию` или `Сохранить позицию`

И отдельно есть предупреждение:

- `На странице одновременно открыт только один редактор ингредиента.`

### После добавления ингредиента

Пользователь возвращается в длинную форму и видит строку/карточку позиции в секции.

Карточка в списке содержит:

- название ингредиента
- краткий summary
- количество
- `Редактировать`
- `Удалить`

Для хмеля позиции сгруппированы по use type, а не одной общей лентой.

## 4. Что пользователь видит при редактировании: `/app/recipes/[id]/edit`

### Общая структура

Экран редактирования визуально почти идентичен экрану создания.
Главное отличие:

- заголовок `Редактирование рецепта`
- все поля уже заполнены значениями рецепта
- секции ингредиентов уже содержат позиции

### Что видно на примере существующего рецепта

У рецепта `вкусненко` видны:

- title `вкусненко`
- style: пусто
- batch size `19.8 l`
- efficiency `75`
- boil time `60`
- publication state `Публичный`
- description `опис`
- author notes `замет`
- один fermentable `Pale Ale Malt`
- хмель отсутствует
- дрожжи отсутствуют

### Как пользователь редактирует

Есть три уровня редактирования:

1. Верхняя sticky-панель
   - title
   - style
   - batch
   - efficiency
   - boil time
   - publication state

2. Контент секции ниже
   - description
   - author notes

3. Секционные ingredient editors
   - кнопка `Редактировать` на конкретной позиции
   - открывается та же модалка

### Важное поведение

- live preview пересчитывается автоматически через debounce
- при сохранении опубликованного/личного рецепта пользователь уходит на detail page
- при редактировании черновика остаётся на edit page
- если открыт editor ингредиента и в нём есть unsaved changes, при попытке открыть другой editor показывается confirm
- при закрытии overlay с dirty state тоже показывается confirm

## 5. Что пользователь видит в detail view: `/app/recipes/[id]`

Detail page заметно проще и чище, чем edit/new.

Пользователь видит:

- status badge
- updated timestamp
- title
- краткую строку с объёмом партии и временем кипячения
- CTA row:
  - `Редактировать рецепт`
  - `Клонировать`
  - `Открыть публичную страницу` если рецепт published
- далее:
  - `Ключевые показатели`
  - `Ингредиенты`
  - `Описание рецепта`
  - `Личные заметки`

Важное наблюдение:

detail page намного ближе к хорошему consumption view, чем edit/new к хорошему authoring flow.

## 6. Реальные ограничения и валидация

### Бизнес-правила

Для `Черновик` публикационная валидация почти не применяется.

Для `Личный` обязательны:

- title
- boil time > 0
- минимум одно `Сбраживаемое`
- минимум одни `Дрожжи`

Для `Публичный` дополнительно обязательны:

- минимум один `Хмель`
- выбранный `Стиль BJCP`
- заполненное публичное `Описание рецепта`

### Важный UX-эффект

На create page:

- save button активна сразу
- badge говорит `Все изменения сохранены`
- но пустой title всё равно невалиден уже на уровне payload schema

То есть визуально экран сообщает "всё хорошо", хотя recipe ещё не существует и часть полей уже невалидна для реального save.

## 7. Что сейчас выглядит слабо с точки зрения UX

### 1. Это не wizard, хотя воспринимается как wizard-задача

Создание рецепта — когнитивно сложный flow, но интерфейс не помогает пройти его по шагам.
Пользователь видит сразу всё:

- метаданные
- стиль
- расчёты
- описания
- 5 ingredient sections
- 2 process profiles

Это усиливает перегрузку, особенно на mobile.

### 2. Верхняя sticky-панель перегружена

В ней одновременно:

- 6 полей
- 2 CTA
- dirty-state
- save feedback

На mobile это просто переносится по строкам, а не превращается в mobile-first control bar.

### 3. Badge `Все изменения сохранены` на пустом create screen вводит в заблуждение

Для нового рецепта это неверное mental model:

- рецепт ещё не создан
- пользователь ещё ничего не сохранил
- но интерфейс сообщает, что всё сохранено

### 4. Валидация видна не там, где пользователь её ждёт

Сейчас:

- общий error block показывается сверху
- section-level errors видны только у ingredient categories
- но ошибки `title`, `style`, `description`, `boilTimeMinutes` не имеют ясной inline-привязки в видимой форме

Это особенно плохо на длинной странице.

### 5. Ingredient add flow слишком модальный

Чтобы добавить позицию, пользователь:

- идёт в нужную секцию
- открывает overlay
- ищет ингредиент
- выбирает
- настраивает специфичные поля
- сохраняет
- возвращается назад в длинную форму

Flow рабочий, но тяжёлый.
Особенно для recipes с многими хмелями и несколькими ферментируемыми позициями.

### 6. Для хмеля слишком много входных точек

В секции хмеля пять подгрупп, у каждой своя кнопка `Добавить`.
Плюс внутри модалки снова есть `Тип добавления`.

Это дублирует выбор контекста:

- пользователь уже выбрал подгруппу кнопкой
- потом ещё раз видит use type в форме

### 7. Нет явного progress model

Сейчас нет ответов на вопросы:

- что уже достаточно заполнено
- что ещё нужно для `private`
- что ещё нужно для `published`
- почему рецепт ещё не ready

Preview считает метрики, но не помогает пройти authoring checklist.

### 8. Языковая неоднородность

В одном и том же экране смешаны:

- русский
- английский
- полуанглийские техмины

Примеры:

- `Recipe Designer`
- `Mash Profile`
- `Fermentation Profile`
- `Primary temp, °C`
- `Stage label`
- `Custom ingredient`

Для production UX это выглядит сыро.

### 9. Process profile визуально вторичен, но структурно тяжёлый

Он спрятан в `details`, что снижает визуальный шум, но:

- labels partly English
- cold crash / conditioning выглядят как отдельные mini-forms
- это добавляет complexity в самый низ длинного экрана

### 10. Mobile-first реализован только частично

Что уже есть:

- карточки стекуются
- ingredient editor превращается в bottom sheet-like overlay

Чего нет:

- явной мобильной информационной архитектуры
- приоритизации шага
- sticky mobile CTA bar
- упрощённого flow добавления ингредиентов
- мобильного progress/checklist сценария

## 8. Что стоит дать UI/UX специалисту как задачи на redesign

### Цель

Сделать authoring flow рецепта:

- менее длинным
- более направленным
- более mobile-first
- с понятным status model
- с более дешёвым добавлением ингредиентов

### Практичные направления redesign

1. Перейти от single huge page к staged authoring flow.

2. Разделить creation на блоки:

- `Основное`
- `Ингредиенты`
- `Процесс`
- `Проверка и публикация`

3. Добавить readiness/checklist:

- что нужно для draft
- что нужно для private
- что нужно для published

4. Свести ingredient add/edit к faster flow:

- inline add rows
- drawer вместо full modal на desktop
- однотипные быстрые сценарии для most-common additions

5. Для хмеля убрать двойной выбор use type.

6. Сделать единый язык интерфейса.

7. Упростить sticky header:

- меньше полей наверху
- save/status отдельно
- на mobile отдельная нижняя CTA bar

8. Сделать detail view референсом для читаемости и cleanliness, а edit view перестроить вокруг authoring tasks.

## 9. Технические замечания, важные для handoff

### Magic link bug

В логах генерируется ссылка на `/api/auth/magic/consume`, но реальный GET-роут находится на `/api/auth/magic`.
Это не часть recipe UX напрямую, но мешает локальному QA flow.

### Активный дизайнер

На страницах `new` и `edit` реально используется `RecipeDesigner`.
В репозитории есть и другие более старые recipe editor компоненты, но current flow pages идут именно через него.
