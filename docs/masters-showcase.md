# ТЗ: Витрина мастеров

Статус: утверждено владельцем (2026-07-07), реализация не начата.
Раздел: публичная витрина людей, которые делают пивоварное оборудование своими руками (ЦКТ, баки, автоматика, чиллеры, мельницы и т.п.).

## 1. Продуктовая рамка

**Что это.** Бесплатная витрина мастера: страница-каталог «кто что делает» + персональная страница мастера с контактами, галереей работ и карточками изделий. Сделка целиком вне платформы — покупатель связывается с мастером напрямую (Telegram/телефон).

**Что это НЕ.** Не маркетплейс: никаких платежей, корзин, заказов, чатов, споров и комиссий. Платформа не участвует в сделках и не сертифицирует изделия — это проговаривается явным дисклеймером.

**Масштаб MVP.** Единицы — пара десятков мастеров. Поэтому:
- никаких рейтингов, отзывов, фильтров, поиска, сортировок — витрина обозрима целиком;
- специализации мастера показываются как теги на карточке (чтобы с одного взгляда: «этот — автоматика, этот — железо, этот — чиллеры»), но НЕ являются фильтром;
- ставка на качество подачи: современно, чисто, в существующем визуальном языке витрины (/recipes).

**Решения владельца (2026-07-07):**
1. Контакты мастера видны всем, включая анонимов (SEO и польза важнее анти-парсинга).
2. Модерируется и первичная заявка, и **каждая последующая публикация правок** профиля/изделий.

## 2. Роли и жизненный цикл

Подать заявку может только залогиненный пользователь. Ролей БД не добавляем: «мастер» — это не роль, а наличие у пользователя профиля мастера (1 пользователь = максимум 1 профиль).

### Модель «черновик + опубликованный снапшот»

Из решения «модерируем каждую правку» следует: публичная страница всегда показывает **последнюю одобренную версию**, пока правки ждут модерации. Паттерн уже есть в проекте (снапшот партии = источник истины):

- Мастер в кабинете всегда редактирует **черновик** (живые строки в БД).
- Кнопка «Отправить на модерацию» переводит профиль в `pending`.
- Модератор смотрит превью черновика и жмёт «Опубликовать» → черновик целиком (профиль + изделия + ссылки на фото) копируется в `publishedJson` — денормализованный jsonb-снапшот.
- Публичные страницы (/masters и /masters/[slug]) рендерятся **только из `publishedJson`**, черновые таблицы не читают.
- «Отклонить» → статус `rejected` + обязательная заметка модератора; мастер правит и отправляет снова.

### Состояния профиля

| reviewStatus | publishedJson | Что видит публика | Что видит мастер в кабинете |
|---|---|---|---|
| `draft` | null | ничего | редактор + «Отправить на модерацию» |
| `pending` | null | ничего | read-only + бейдж «На модерации» + «Отозвать» |
| `rejected` | null | ничего | заметка модератора + редактор |
| `draft` | есть | опубликованную версию | редактор + «Опубликовать изменения» (есть неопубликованные правки) |
| `pending` | есть | **старую** опубликованную версию | read-only + «Отозвать» |
| `rejected` | есть | старую опубликованную версию | заметка + редактор |

Плюс независимый флаг `isListed` (default true):
- модератор может снять профиль с витрины в любой момент (нарушение, жалоба);
- мастер может сам скрыть свою витрину («уехал в отпуск») и вернуть без модерации — контент при этом не менялся.
`isListed=false` → профиль и страница скрыты (404 для публики), снапшот сохраняется.

«Отозвать» из pending возвращает в `draft` без участия модератора.

## 3. Данные (packages/db/src/schema.ts)

Следующая миграция после `0057`. Именование и паттерны — как у существующих таблиц (uuid pk defaultRandom, timestamps withTimezone, snake_case).

### `master_profiles`
- `id` uuid pk
- `userId` → users, **unique**, onDelete cascade (удалил аккаунт — витрина исчезла; корректно и по ПДн)
- `slug` varchar(220) unique — генерится из displayName при аппруве первой публикации (транслит, как у рецептов), далее стабилен
- `displayName` varchar(120) — имя мастера или мастерской
- `city` varchar(120)
- `specializations` text[] — значения из константы в contracts (см. §4), 1..4 шт.
- `summary` varchar(200) — одно предложение для карточки на витрине
- `about` text — «суть объявы»: что делает, из чего, сроки, география доставки
- Контакты (все опциональны, минимум один обязателен на уровне zod): `contactTelegram`, `contactPhone`, `contactEmail`, `contactWebsite` — varchar
- `craftSince` smallint nullable — год, с которого делает («работает с 2019»)
- `reviewStatus` pgEnum `master_review_status` = `["draft","pending","rejected"]`, default `draft`
- `isListed` boolean default true
- `publishedJson` jsonb nullable `$type<MasterPublishedSnapshot>` — снапшот: поля профиля + массив изделий + упорядоченные id фото галереи
- `publishedAt`, `submittedAt` timestamp nullable
- `moderatorId` → users (set null), `moderationNote` text nullable
- `createdAt`, `updatedAt`
- Индексы: unique(userId), unique(slug), (reviewStatus, submittedAt) для очереди

### `master_items` — изделия (черновик)
- `id`, `profileId` → master_profiles cascade
- `title` varchar(160) — «ЦКТ 60 л», «Контроллер затирания»
- `description` text — характеристики, материалы, комплектация
- `priceNote` varchar(80) nullable — свободный текст: «от 25 000 ₽», «по запросу». Никаких числовых цен/валют в MVP.
- `coverImageId` → master_images (set null)
- `sortOrder` integer, `createdAt`/`updatedAt`

Лимит: ≤ 12 изделий на профиль (проверка в сервисе).

### `master_images`
По образцу `recipe_images` (schema.ts:558): те же варианты original/large/medium/thumb + `blurDataUrl`, статусы uploading/ready/failed, soft-delete `deletedAt`.
- `profileId` → master_profiles cascade
- `itemId` → master_items nullable (null = общая галерея работ, иначе фото изделия)
- `sortOrder`
- Storage-ключи: `masters/${profileId}/images/${imageId}/${variant}.${ext}`
- Лимиты: ≤ 24 фото на профиль суммарно, ≤ 6 на изделие, 10MB/файл (константы — копия подхода recipe-images/contracts.ts)

Отдельная таблица заявок не нужна: очередь модерации = `master_profiles where reviewStatus='pending' order by submittedAt`. Истории ревизий в MVP нет.

## 5. Роуты и IA

### Публичная зона `(public)`
- **`/masters`** — витрина. В `lib/navigation.ts`: пункт «Мастера» в `publicLinks` (после «Каталог») **и префикс в `publicPathPrefixes`** (иначе ширина/лого поведут себя как app-зона — известная ловушка).
- **`/masters/[slug]`** — страница мастера. `notFound()` если нет снапшота или `isListed=false`.
- Sitemap: добавить `/masters` и опубликованные `/masters/[slug]` в `app/sitemap.ts`.

### App-зона `(app)`
- **`/app/master`** — единая точка, машина состояний:
  - профиля нет → короткий лендинг «Станьте мастером» (2–3 предложения ценности: бесплатно, ваша страница, покупатели из комьюнити) + анкета;
  - профиль есть → кабинет по таблице состояний из §2.
- Пункт в сайдбаре app-зоны (группа с профилем/настройками): «Моя витрина» — рабочее название, владелец пересмотрит формулировку вживую. Никаких пояснительных подписей под пунктом.

### Admin-зона `(admin)`
- **`/admin/masters`** — очередь: табы «На модерации | Опубликованные | Отклонённые» (querystring `?status=`, по образцу `/admin/feedback`). Гейт `requireRole("moderator")`.
- **`/admin/masters/[id]`** — превью заявки: рендер черновика **тем же компонентом, что публичная страница мастера** (моderator видит ровно то, что появится на витрине), сверху панель: «Опубликовать» / «Отклонить» + textarea заметки, для опубликованных — «Снять с витрины»/«Вернуть».
- Ссылка в индекс `/admin` (app/(admin)/admin/page.tsx).

## 6. UI

Общий принцип: никакого нового визуального языка — карточный стиль `/recipes` (`rounded-2xl border border-border bg-card shadow-sm`), токены тёмной темы, переиспользуемые части из `recipe-card-parts.tsx` (`AuthorAvatar`).

### /masters — витрина
- Заголовок «Мастера» + одна строка-лид (это тот случай, когда подзаголовок несёт смысл: «Оборудование для пивоварения ручной работы — от людей из комьюнити»). Формулировку утвердить у владельца.
- Сетка карточек: 3 колонки desktop / 2 tablet / 1 mobile. Карточки одной высоты.
- **Карточка мастера** (вся — stretched-link на страницу мастера):
  - обложка: первое фото галереи (variant `medium`, с blur-placeholder); нет фото — заливка-плейсхолдер в стиле SRM-фолбэка рецептов;
  - имя мастера крупно, город строкой ниже (иконка map-pin);
  - чипы специализаций (стиль `StyleChip`), максимум 3 + «+N»;
  - `summary` в 2 строки с line-clamp.
  - Контактов на карточке НЕТ — они на странице мастера.
- Внизу витрины — CTA-блок «Делаете оборудование своими руками? Откройте свою витрину» → `/app/master` (аноним уйдёт через `/login?next=`). Один блок, без лишних подписей.
- Пустое состояние (пока нет ни одного мастера): тот же CTA-блок как главный элемент страницы.

### /masters/[slug] — страница мастера
Рендер только из `publishedJson`. Структура сверху вниз:
1. **Шапка**: имя крупно, город, чипы специализаций, «Делает с 2019» (если задан `craftSince`); блок контактов — кнопки-действия: «Написать в Telegram» (primary), «Позвонить» (`tel:`), «Сайт», e-mail. Кнопки, не текст-простыня.
2. **О мастере** — `about`, обычный текст с переносами абзацев.
3. **Изделия** — сетка карточек 2 колонки: фото-обложка, название, `priceNote` бейджем, описание (line-clamp + разворот или переход в лайтбокс фото изделия). Если изделий нет — секция не рендерится.
4. **Галерея работ** — grid миниатюр + лайтбокс. Переиспользовать/адаптировать `recipe-image-grid.tsx` и `recipe-image-lightbox.tsx`.
5. **Дисклеймер** (мелкий, muted): «Платформа не участвует в сделках и не проверяет изделия. Договаривайтесь с мастером напрямую и уточняйте характеристики — особенно для ёмкостей под давлением.» Точную формулировку утвердить у владельца.

### /app/master — анкета и кабинет
- **Анкета** (первичная заявка): displayName, город, специализации (чипы-переключатели), summary, about, контакты (≥1), craftSince. Отправка = создание профиля в `draft` — фото и изделия добавляются уже в кабинете, потом «Отправить на модерацию». Так анкета остаётся короткой, а мастер не теряет работу при обрыве.
- **Кабинет**: секции Профиль / Изделия / Галерея. Числовые поля — `NumericInput`; деструктив (удаление изделия/фото) — `ConfirmActionDialog`; тосты — `useToast`.
- Статусная панель сверху: текущее состояние + главное действие («Отправить на модерацию» / «Опубликовать изменения» / «Отозвать»), заметка модератора при `rejected`. В состоянии с публикацией — ссылка «Открыть мою страницу» и тумблер «Скрыть с витрины».
- Загрузка фото — по образцу `recipe-image-uploader.tsx` (drag&drop, статусы, ретрай).

## 7. Сервисный слой

`apps/web/features/masters/`:
- `contracts.ts` — zod-схемы (профиль, изделие), константы специализаций и лимитов, метки статусов, тип `MasterPublishedSnapshot`.
- `service.ts` — CRUD черновика (все мутации проверяют владельца), `submitForReview`, `withdrawSubmission`, `approveProfile` (сборка снапшота: профиль + items по sortOrder + ready-фото; slug-генерация при первой публикации), `rejectProfile`, `setListed`, `listPublishedMasters`, `getPublishedMasterBySlug`, `listModerationQueue`, `countPendingMasters`.
- `permissions.ts` — `canModerate` = moderator+ (по образцу feedback).
- `images.ts` — тонкая обёртка над пайплайном по образцу `features/recipe-images` (sharp-деривативы, слоты, лимиты).
- `seo.ts` — metadata + JSON-LD.

API фото:
- `POST /api/master-images/upload` — по образцу recipe-images upload: `requireUser`, владелец профиля, `assertRateLimit(user.id, "master_image_upload", 30, 3600)`, sharp, откат при ошибке.
- `GET /api/master-images/[imageId]/[variant]` — публично отдаёт, только если id фигурирует в `publishedJson` профиля с `isListed=true` (immutable-кэш); иначе — только владельцу и модератору (private-кэш). Логика доступа — как у `getRecipeImageAsset`.

Server actions: мутации кабинета — `app/(app)/app/master/actions.ts`; модерация — `app/(admin)/admin/masters/actions.ts` (по образцу admin/feedback/actions.ts: requireRole, revalidatePath, `{ok}`-результат).

Rate limit на сабмит модерации: `assertRateLimit(user.id, "master_submit", 10, 3600)` — от пинг-понга с модератором.

## 8. SEO

- `/masters`: title «Мастера пивоварного оборудования», description про ручную работу/ЦКТ/автоматику; `revalidate = 300`.
- `/masters/[slug]`: title «{displayName} — {специализации через запятую}, {город}», description из summary; OG-image — первое фото галереи (large).
- JSON-LD на странице мастера: `LocalBusiness` (name, address.addressLocality, telephone, url, image) + `BreadcrumbList`; через существующий `jsonLdScriptProps`.
- Slug: транслит displayName + защита от коллизий суффиксом, как у рецептов.

## 9. Не делаем в MVP (осознанно)

- Рейтинги, отзывы, «проверенный мастер» — позже, когда мастеров станет десятки.
- Фильтры/поиск/сортировки на витрине.
- Сообщения/чат на платформе, кнопка «оставить заявку мастеру».
- Цены числом, валюты, наличие/склад.
- Платное продвижение и выделение.
- История ревизий модерации и diff «что изменилось» (модератор смотрит превью целиком — при паре десятков мастеров этого достаточно).
- Уведомления мастеру о решении модератора (в MVP статус виден в кабинете; пуши/письма — потом).

## 10. Этапы

- **M1 — данные и сервис**: миграция (3 таблицы + enum), `features/masters` (contracts, service, permissions), vitest на переходы состояний (submit/approve/reject/withdraw/setListed, лимиты, сборку снапшота, права владельца/модератора).
- **M2 — кабинет мастера**: `/app/master` (анкета + кабинет + статусная панель), пайплайн фото (upload/GET-роуты), пункт в сайдбаре.
- **M3 — модерация**: `/admin/masters` (очередь + превью публичным компонентом + действия), счётчик pending на индексе /admin.
- **M4 — публичная витрина**: `/masters`, `/masters/[slug]`, навигация (`publicLinks` + `publicPathPrefixes`), SEO/JSON-LD/sitemap, дисклеймер, CTA.
- **M5 — полировка и живой прогон**: тёмная тема, мобильная вёрстка, пустые состояния, смоук полного цикла: анкета → фото → сабмит → аппрув → витрина → правка → повторный аппрув (старая версия видна во время pending) → скрытие.

Критерий приёмки MVP: полный цикл из M5 проходит вживую; публичная страница во время модерации правок показывает прежнюю версию; `npm run typecheck` и suite зелёные.
