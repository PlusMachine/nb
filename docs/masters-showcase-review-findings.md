## P0 — ломает инвариант/данные

1. **`deleteMasterImage` уничтожает фото из опубликованного снапшота** (`features/masters/images.ts:398`) — подтверждено 5 измерениями.
   Профиль опубликован (`publishedJson` ссылается на imageId), reviewStatus=draft. Владелец удаляет это фото в кабинете: `deletedAt` + физическое удаление всех 4 storage-объектов. Публичная страница по снапшоту всё ещё рендерит imageId, но `getMasterImageAsset` отдаёт 404 для deletedAt → битые картинки на живой витрине **до** approve (нарушение инварианта «публика видит одобренную версию») + невосстановимая потеря данных.
   **Фикс:** soft-delete скрывает фото из черновика/кабинета, но (а) `getMasterImageAsset` отдаёт снапшотное фото публике несмотря на deletedAt; (б) storage-объекты физически не удаляются, пока imageId есть в текущем `publishedJson`; (в) GC осиротевших фото (deletedAt + не в новом снапшоте) — в `approveMasterProfile`. Миграция не нужна. ✅

## P1 — реальный баг / нарушение конвенции или спеки

2. **Правка галереи во время модерации** (`images.ts:298,350` + `service.ts:471`). `completeMasterImageUpload`/`markMasterImageUploadFailed` не зовут `assertProfileImagesEditable`, а `submitForReview` не смотрит на `uploading`-слоты. Аплоад стартовал в draft → сабмит → complete доводит фото до ready при pending → approve публикует фото, которого модератор не видел. **Фикс:** submitForReview отклоняет при наличии uploading-слотов; complete/markFailed перечитывают статус под локом. ✅
3. **TOCTOU в approve/reject** (`service.ts:600,648`). Чтение→проверка pending→UPDATE только по id, без транзакции и без `reviewStatus='pending'` в WHERE. Гонка с withdraw+правкой публикует немодерированную версию / перетирает отзыв. **Фикс:** транзакция + `for update` + предикат reviewStatus в WHERE, 0 строк = конфликт. ✅
4. **`reorderMasterItems` без транзакции** (`service.ts:458`). Цикл отдельных UPDATE (в отличие от `reorderMasterImages`, где транзакция+лок) → частичный порядок с дублями попадает в снапшот. **Фикс:** обернуть в транзакцию с локом. ✅
5. **`setOwnMasterListedAction` не ревалидирует публичные страницы** (`app/(app)/app/master/actions.ts:128`). «Скрыть с витрины» у владельца обновляет только кабинет; админский аналог ревалидирует `/masters` и `/masters/[slug]`. **Фикс:** тот же `revalidatePublicMasterPages(profile.slug)`. ✅
6. **Удаление фото без `ConfirmActionDialog`** (`master-image-manager.tsx:375,426`) — нарушение CLAUDE.md и спеки §6. Один клик по корзине (рядом с «обложка»/стрелки) необратимо стирает файл; нет busy-состояния. **Фикс:** ConfirmActionDialog для серверного фото (для локальных слотов — не нужно) + дизейбл кнопок на время запроса. ✅
7. **Публичная карточка изделия: видна только обложка, описание обрезано без разворота** (`master-page-view.tsx:136`) — спека §6.3 требует «line-clamp + разворот или лайтбокс». `item.images` (до 6 фото) в снапшоте есть, но публика видит одно. **Фикс:** клик по карточке/обложке → лайтбокс по `item.images` (переиспользовать `MasterGalleryLightbox`) + разворот описания. ✅
8. **Голые цвета ломают тёмную тему** (`master-image.tsx:19` — светлый `FALLBACK_GRADIENT`; `master-gallery.tsx:27` — `ring-black/5`). Карточка без фото = светлое пятно в dark, иконка почти невидима. **Фикс:** токены (`bg-muted`/градиент через `hsl(var(--...))`), `ring-black/5`→`ring-border`. ✅
9. **Владелец мгновенно отменяет модераторское «Снять с витрины»** (`service.ts:530`). `setOwnListed` не отличает самоскрытие от санкции модератора → кейс «нарушение/жалоба» из §2 обходится одним тумблером. **Требует поля в БД (миграция) + продуктового решения** (что видит мастер? апелляция?). 🔵 вопрос владельцу.
