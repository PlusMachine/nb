## Короткий вывод

- На верхнем уровне каталог покрыт полностью: все `1109` seed-ингредиентов попадают в один из текущих entry chips.
- На уровне внутренних chips покрытие уже не полное: они работают как shortcuts и refinements, а не как исчерпывающая карта каталога.
- Самая явная логическая проблема сейчас в `water_treatment`: group-refinement для этой категории рендерится с заголовком про расходники.
- Иерархия в целом рабочая, но она смешивает разные уровни taxonomy: где-то пользователь выбирает категорию, где-то broad group, где-то subtype, где-то quick-start family.

## 2. Что покрывают вложенные chips

### 2.1. Fermentables

После выбора `Сбраживаемые` UI уходит во второй уровень:

- `Солод`
- `Концентраты`
- `Сахара и сиропы`
- `Фрукты и соки`
- `Неосоложенка`

Фактическое покрытие non-malt fermentables:

- `extracts_and_concentrates`: `37`
- `sugars_and_syrups`: `47`
- `fruits_and_vegetables`: `51`
- `adjunct_grains`: `38`

Вывод:

- Для non-malt fermentables group-chips покрывают каталог полностью.
- Для malts отдельные quick-start chips `По типу` не являются полной taxonomy. Это 8 preset families, а не исчерпывающий классификатор.
- В статическом seed/alias-аудите хотя бы в одну из 8 malt-family chips попадают примерно `329` из `442` солодов. Около `113` солодов остаются вне этих family shortcuts.

Следствие:

- Ответ на вопрос "весь ли каталог покрывается chips" для malt quick-start: нет, не весь. Эти chips служат быстрым входом, а не полной картой каталога.

### 2.3. Water Treatment

Фактические water-groups по runtime-логике picker:

- `salt`: `8`
- `acid`: `7`
- `base`: `4`
- `dechlorination`: `3`
- `water_source`: `5`
- `acid`: включает и `acidulated-malt`

Почему это важно:

- На raw seed-уровне `acidulated-malt` выглядит неоднозначно, потому что у него `category = pH_fermentable`.
- Но в живом picker water-group определяется не только по raw category, а и по `technicalData`.
- У `acidulated-malt` в `technicalData` есть признаки кислотной группы, например `recommendedFor = German-style acidification` и `waterCalcRole = lower_mash_pH`.

Вывод:

- В текущем add-flow `acidulated-malt` действительно попадает в chip `Кислоты`.
- Значит, проблема покрытия water-group chips в этом месте отсутствует.

## 3. Иерархия и последовательность

## 3.1. Что хорошо

- Порядок верхних chips нормальный для склада: сначала основное сырье, потом вспомогательные категории.
- `Расходники` и `Другие добавки` стоят рядом, это логично.
- После выбора ингредиента summary уже показывает более конкретный контекст, например `Солод` или `Сбраживаемое сырье`, поэтому selection state понятнее, чем search state.

## 3.2. Что выглядит спорно

- Верхний ряд смешивает уровни taxonomy:
  - `Сбраживаемые`, `Хмель`, `Дрожжи`, `Водоподготовка` — это категории.
  - `Расходники` и `Другие добавки` — это не категории, а broad groups внутри `consumable`.
- Второй уровень у fermentables тоже смешанный:
  - `Солод` — subtype.
  - остальные chips — group внутри non-malt fermentables.

Следствие:

- Ментальная модель получается не чисто иерархической, а task-oriented.
- Для inventory UI это допустимо, но требует аккуратных подписей и отсутствия ложных ожиданий, что все chips находятся на одном semantic level.

## 3.3. Последовательность

Текущая последовательность chips в целом удачная:

1. `Сбраживаемые`
2. `Хмель`
3. `Дрожжи`
4. `Водоподготовка`
5. `Расходники`
6. `Другие добавки`

Менять порядок не требуется.

Если и улучшать последовательность, то не перестановкой, а прояснением hierarchy:

- либо визуально объединить `Расходники` + `Другие добавки` под общий consumable heading,
- либо честно назвать верхний уровень "категории и группы склада",
- либо вернуть более симметричную схему, где split делается одинаково для всех сложных веток.

## 4. Найденные проблемы

### P1. Неверный заголовок refinement для `water_treatment`

В `ingredient-picker.tsx` заголовок refinement-panel сейчас строится так:

- для `fermentable` — `Уточнить группу сбраживаемых`
- для всех остальных `consumable_group` — `Уточнить группу расходников`

Но `water_treatment` тоже использует refinement типа `consumable_group`.

Следствие:

- Для water treatment пользователь увидит некорректный заголовок `Уточнить группу расходников`.

Это явная UI-ошибка, не вопрос вкуса.

### P2. Пустой chip `other` в additive switch

Верхний split `consumable_additive` корректен, но во втором уровне есть chip `other` при нулевом текущем покрытии.

Следствие:

- пользователь получает пустой фильтр без явной пользы,
- а сама структура chips расходится с quick-start group logic, где `other` не показывается.

### P2. Семантическая иерархия chips неравномерна

UI смешивает:

- category
- broad group
- subtype
- quick-start family

Это не ломает поиск, но усложняет предсказуемость интерфейса.

Практически это проявляется так:

- пользователь не всегда понимает, почему `Сбраживаемые` — это один верхний chip, а `Расходники` уже split на два peer chips,
- `Солод` в одном месте выглядит как категория, а в другом как subtype/context label.

### P3. Документация в `docs` частично отстала от текущего UI

Несколько существующих документов все еще описывают старую схему верхнего ряда, где `Солод` и `Сбраживаемое сырье` были отдельными верхнеуровневыми chips.

Для текущего кода это уже не source-of-truth описание.

## 5. Ответ на основной вопрос

Если считать только верхнюю сетку категорий:

- да, каталог покрыт полностью.

Если считать все filter chips внутри picker как полную карту каталога:

- нет, не покрыт.

Точнее:

- `consumable` и non-malt `fermentable` покрыты chips хорошо;
- `water_treatment` по текущей runtime-логике покрыт корректнее, чем это выглядело по raw seed-аудиту;
- malt quick-start chips по своей природе не исчерпывающие и не должны считаться полным покрытием каталога.

## 6. Что я бы рекомендовал дальше

1. Исправить заголовок refinement для `water_treatment` на отдельный copy, например `Уточнить группу водоподготовки`.
2. Скрывать chip `other`, пока в нем нет реального покрытия.
3. Упростить hierarchy-слой в UI: либо визуально группировать broad groups, либо делать split-логику более симметричной.
4. Обновить старые документы в `docs`, которые все еще описывают прежнюю схему chips.
