# Веб-пульт BrewForge: режимы прибора и «веб как экран» — спека

> Продолжение `brewery-command-center-l2-redesign.md` (пульт = зеркало платы) на уровень выше:
> прибор с несколькими режимами (варка / дистилляция / ферментация) + веб-панели как
> основной большой экран устройства. Статус: спека на обсуждение/реализацию, 2026-07-03.

## 0. Рамки и мотивация

**Два факта, из которых всё следует:**

1. **Прошивка поддерживает один дисплей 3.5"** — осознанное решение владельца. Больших/разных
   дисплеев в прошивке не будет. Расширение экрана — целиком на стороне веба: телефон, планшет,
   ПК, ноутбук становятся «большим экраном» устройства. Веб-пульт — это HMI (панель
   оператора) прибора, а не просто «удалённый мониторинг».
2. **Прибор мультирежимный**: варка (реализована на портале), дистилляция и ферментация
   (стадии 17–21 в прошивке есть, на портале — только зеркало протокола, UI нет).
   Смена применения — это не пункт меню, а **физическая пересборка железа** (другие датчики,
   клапан отбора, охлаждение камеры и т.п.).

**Что покрывает спека:** модель режимов, user flow, состав пультов по режимам, киоск-режим
(«веб как экран»), матрица удалённого управления, требования к дизайну, контракту прошивки и
данным. **Что не трогаем:** safety-слой (control-lease, command-gate, интерлоки, транспорты) —
он режимо-независим и работает как есть.

## 1. Решения владельца (2026-07-03) — фиксируем

1. **Портал подключается к прибору в том режиме, в котором прибор стоит.** Режим задаётся на
   устройстве (там же, где пересобирают железо); портал его зеркалит и не переключает.
2. **Один дисплей в прошивке, богатые панели — в вебе.** Телефон/планшет/ПК как экран
   устройства: «удобно, наглядно», любой размер.
3. **Сценарии не смешиваются.** Флоу по режимам должны быть разведены так, чтобы ничего не
   путалось: просто и понятно, при этом конфигурируемо.
4. **Открытый вопрос владельца:** будут ли пользователи пересобирать один блок под разные
   применения — неизвестно. Модель должна это *допускать*, не навязывая (см. §2).

## 2. Ключевая модель: режим — состояние прибора, а не его тип

Это главный ответ на вопрос «один блок и для дистилляции, и для ферментации — как?»:

- **Портал не хранит и не спрашивает «тип прибора».** У устройства нет поля «я пивоварня» —
  есть только *текущий режим* из телеметрии (`appMode`, требование к прошивке §13). Один блок
  может прожить десять жизней — порталу всё равно: он рисует пульт под то, что прибор
  сообщает о себе сейчас.
- **Переключение режима — только на устройстве.** Смена применения = пересборка железа, человек
  физически у прибора — там и переключает (локальные команды `SET_APP_MODE`/`START_DISTILL`/
  `START_FERMENT` остаются локальными). Портал показывает режим read-only с подсказкой
  «режим переключается на устройстве». Это же снимает целый класс аварийных сценариев
  («удалённо переключил ферментер с пивом в режим дистилляции»).
- **Пересборка железа = профили конфига (уже есть).** `device_profiles` — сохранённые снимки
  конфига. Пользователь, перебирающий блок между ролями, сохраняет профиль на каждую роль
  («Пивоварня 30 л», «Ферментер в камере») и восстанавливает при возврате. Новая сущность
  «роль железа» не нужна — хватит существующей, максимум подсказать в UI сохранение профиля
  перед сменой режима (v2).
- **Capabilities решают «какое железо подключено».** Прибор уже сообщает `capabilities[]` и
  шлёт опциональные поля телеметрии только при наличии железа (`pump2On`, `valveOn`, `coolOn`,
  `hxTempC` — паттерн «undefined = скрыть строку» уже реализован в `StatusStrip`). Панели
  строятся по этому же принципу: **рисуем только то, что физически есть.**

## 3. Принципы

| Принцип | Основание |
|---|---|
| **Пульт зеркалит плату** — теперь включая режим прибора | продолжение решения L2 §1.2; решение владельца §1.1 |
| **Один маршрут — три лица.** Пульт `/app/devices/[id]` один; тело меняется по режиму. Пользователь не выбирает «какой дашборд открыть» — прибор диктует | «сценарии не смешиваются» §1.3 |
| **Невозможное — отсутствует, а не disabled.** «Сварить рецепт…» не существует на дистилляторе; «журнал отбора» не существует на пивоварне | чистый самоочевидный UI (память ui-no-slop-subtitles) |
| **Co-located first.** Главный пользователь режимного пульта стоит *рядом* с прибором, но смотрит в телефон/планшет, потому что 3.5" мал. Удалёнка — вторична и гейтится жёстче | решение владельца §1.2; следствие «веб как экран» |
| **Glanceable с 2–3 метров** в киоске: температура и стадия читаются от плиты | HMI-назначение |
| **Конфигурируемость = адаптация, не конструктор.** Панели адаптируются под режим и железо сами; ручной конструктор виджетов не строим (§11) | простота §1.3 |
| **Термины сообщества** — и для дистилляции («куб», «колонна», «головы/тело/хвосты», «отбор», «флегма»), и для брожения («главное брожение», «диацетильная пауза», «холодная выдержка») | L2 §1.6 |

## 4. Информационная архитектура и user flow

```
L1  /app/devices — грид приборов
    плитка: имя · статус связи · [бейдж режима: Варка|Дистилляция|Ферментация|Свободен]
            · режимная сводка (варка: стадия+t°; ферментация: день N, t°/уставка;
              дистилляция: фракция+t° куба) · sparkline
      │ «Пульт»
      ▼
L2  /app/devices/[id] — ЕДИНЫЙ пульт, тело по режиму (§5–8)
      ├── общий каркас: хедер (имя · режим · связь · аренда) · аварии · E-STOP ·
      │   ручной режим · датчики · график
      ├── прибор в ВАРКЕ      → варочный пульт (готов, L2-редизайн W1–W5)
      ├── прибор в ДИСТИЛЛЯЦИИ → пульт дистилляции (§7)
      ├── прибор в ФЕРМЕНТАЦИИ → пульт брожения (§8)
      ├── прибор СВОБОДЕН      → «Пивоварня свободна» + «Сварить рецепт…» (только если
      │                          режим прибора — варка) / «Ручной режим»
      │ [⛶ на весь экран]
      ▼
    КИОСК — тот же пульт без хрома сайта, крупно (§9)

    ⚙ /app/devices/[id]/settings — конфиг, профили, журнал (как есть)

Зона A (партии пива):
    /app/brew-batches/[id] — жизненный цикл партии; при варке уже подключает пульт.
    НОВОЕ: акт «Брожение» партии ↔ прибор в режиме ферментации (§8.4).
    Дистилляция в зону A не заходит вообще — это не пивной флоу.
```

**Как «не смешиваются» сценарии — три механизма:**
1. Режим определяет прибор, не пользователь → нельзя открыть «не тот» экран.
2. Бейдж режима сквозной: на плитке L1, в хедере L2, в киоске. Всегда видно, чем прибор занят.
3. Пивной мир (рецепты, партии, зона A) соединяется только с режимом варки/ферментации;
   дистилляция живёт исключительно на пульте устройства.

### 4.1 Сквозные сценарии (user journeys)

**J1 — варка с киоском (co-located, два экрана).** Планшет ставится у пивоварни: пульт → ⛶ →
киоск, экран не гаснет. Телефон в кармане ловит пуши промптов. Команды можно давать с любого
экрана: аренда управления переходит перехватом (§9.1), E-STOP работает с обоих всегда.

**J2 — дистилляция (co-located).** Пересобрал железо → на приборе включил режим дистилляции →
плитка L1 сама сменила бейдж на «Дистилляция» → открыл пульт на планшете рядом с аппаратом →
старт на приборе → следит за кубом/колонной на большом экране → головы отобраны — «К следующей
фракции» с планшета (подтверждение) → отошёл — пуш «смените приёмную ёмкость» → вернулся,
ответил с телефона → готово. (v2: перегон лёг в журнал.)

**J3 — ферментация (remote).** Партия сварена (зона A) → перелив в ферментер → на приборе
включил ферментацию → в партии, акт «Брожение»: «бродит в приборе …» → профиль подтянулся из
плана брожения рецепта (или задан на пульте) → уехал → день 3: пуш «отклонение +1.5°» → открыл
с работы, посмотрел график, поправил уставку → день 7: пуш «шаг завершён» → «Перейти к
диацетильной паузе» удалённо → конец профиля → отвязал партию, прибор свободен.

**J4 — смена жизни блока.** Пивоварня → ферментер: сохранил профиль конфига «Пивоварня 30 л» →
пересобрал железо → на приборе сменил режим → портал перерисовал пульт сам (без reload, §5),
плитка сменила бейдж → восстановил/создал профиль «Ферментер». Обратно — зеркально.

### 4.2 Плитка L1 — режимная сводка

```
┌───────────────────────┐ ┌───────────────────────┐ ┌───────────────────────┐
│ Пивоварня      ● live │ │ Куб            ● live │ │ Ферментер     ◐ 12 мин│
│ [Варка]               │ │ [Дистилляция]         │ │ [Ферментация]         │
│ 66.4° → 67.0°         │ │ куб 84.2° кол. 78.1°  │ │ 18.2° → 18.0°         │
│ Затор · пауза 2/3     │ │ Тело · отбор идёт     │ │ Главное брожение 4/7 д│
│ ∿∿∿∿∿∿                │ │ ∿∿∿∿∿∿                │ │ ∿∿∿∿∿∿                │
└───────────────────────┘ └───────────────────────┘ └───────────────────────┘
```

Свободный прибор: бейдж «Свободен» + last-known температура. Пороги свежести плитки — режимные
(ферментация шлёт кадры редко, §13.5).

## 5. Пульт: общий каркас (все режимы)

Не меняется относительно L2-редизайна: sticky-хедер (назад · имя · статус связи · канал ·
аренда · ⚙), баннер аварий (ISA-18.2), E-STOP hold-to-confirm всегда доступен, ручной режим,
сетка датчиков, живой график по SSE. Freshness-гейт и control-lease работают одинаково во всех
режимах.

**Дополнения каркаса:**

- **Бейдж режима в хедере** — рядом с именем: «Варка» / «Дистилляция» / «Ферментация»
  (+ «Ручной», «Авария» как сейчас через `deriveDeviceMode`).
- **`device-mode.ts` расширяется** до пары `{appMode, activity}`: `appMode` из телеметрии
  (brew / distill / ferment), `activity` — прежнее offline/idle/auto/manual/fault.
  Стадии 17–20 ⇒ distill running, 21 ⇒ ferment running; в IDLE режим различим только по
  `appMode` из прошивки (§13).
- **Словарь стадий — человекочитаемый для ВСЕХ 22 стадий.** Сейчас `MonitorHero` рендерит
  сырое машинное имя (`MASH_STEP`, а при дистилляции показал бы `DISTILL_HEARTS`). Нужен
  единый словарь `Stage → русская подпись` в `features/brew-controller`, герой и плитки
  используют только его. Это P0 независимо от остального (§15).
- **Кнопка «на весь экран» (⛶)** в хедере → киоск (§9).
- **Смена режима — на лету.** Приход телеметрии с другим `appMode` перестраивает тело пульта
  без reload (SSE уже live) + тост «Прибор переключён в режим …». Никаких зависших экранов
  «не того» режима.

## 6. Режим «Варка»

Готов (L2-редизайн, W1–W5). Изменения по этой спеке: только каркасные (§5). Полоса стадий,
гид-промпты, «Сварить рецепт…», транспорт — без изменений.

## 7. Режим «Дистилляция» — пульт

**Характер процесса:** надзорный, часы, оператор рядом (запах/проба решают переходы фракций).
Ценность веб-пульта — **большой наглядный экран рядом с аппаратом** + подстраховка пушем, если
отошёл («смените тару», авария). Удалённое участие «из другого города» — не сценарий.

### Состав

- **Полоса фракций:** Разогрев → Головы → Тело → Хвосты → Готово (маппинг стадий 17–20 + DONE
  в `stage-timeline` — новая карта макро-стадий для режима distill).
- **Герой — ДВЕ температуры:** куб (primary) и колонна/дефлегматор — назначенный датчик из
  `sensors[]` (НЕ `hxTempC` — тот про HERMS, §13). Температура колонны — главный рабочий
  инструмент дистилляции, прятать её в «датчики» нельзя; если датчик не назначен — герой
  показывает только куб.
- **Клапан отбора (флегма):** статус `valveOn` в герое и контуре.
- **«Смените ёмкость»** (`actionReady`): промпт-баннер в стиле гида варки + web-push
  (переживает сворачивание/обрыв — тот же механизм Phase 6).
- **Переход фракции — «К следующей фракции»**: главная co-located команда (оператор у
  аппарата, экран — телефон). Двухшаговое подтверждение («Завершить отбор голов и начать
  тело?»), требует live + аренду. Какой командой прошивки это делается (SKIP_STAGE или
  отдельная) — уточнить (§13).
- **График:** куб + колонна, вертикальные аннотации смен фракций (расширение
  `telemetry-annotations`).
- **Журнал отбора (v2):** времена и длительности фракций из телеметрии автоматически +
  ручной ввод объёмов/крепости → история перегонов на устройстве. В v1 не делаем.

### Безопасность (§10)

Старт дистилляции — **только на устройстве** (как сейчас; надзорный огнеопасный процесс,
человек обязан быть рядом на старте). Удалённо: наблюдение, ответы на промпты, переход
фракции, СТОП/E-STOP всегда. Уставка/мощность — через существующий ручной режим с теми же
гейтами, что у варки (opt-in `remote_control_enabled`, rate-limit, dead-man).

## 8. Режим «Ферментация» — пульт

**Характер процесса:** недели, оператор далеко. Полная противоположность дистилляции:
**удалёнка — весь смысл режима.** Посмотреть с работы, поправить уставку, получить пуш о
скачке температуры.

```
│ │ Охлаждение ● вкл (защита компр. 0:42) │  coolOn + coolLockS         │
│ │ Нагрев ○ выкл   Разрешён ДА           │                              │
│ └──────────────────────────────────────┘                              │
└──────────────────────────────────────────────────────────────────────┘
```

### Состав

- **Герой:** температура + уставка + «шаг профиля · день N из M» + следующий шаг. Отсчёт в
  днях, не в минутах.
- **График план vs факт** в масштабе дней/недель (не 1-Гц лента варки): линия профиля +
  фактическая температура. Требует **always-on персиста телеметрии** (§14) — сейчас история
  пишется только пока кто-то подписан, для брожения это дыра.
- **Профиль брожения:** список шагов (имя, уставка, длительность), текущий подсвечен.
  Действия: «изменить уставку» (шаг сейчас), «перейти к следующему шагу». Профиль живёт в
  конфиге прибора (`ferment.steps[]`, до 6 ступеней; `hours=0` = держать до ручного
  перехода — §13) и пишется существующим `PUT /config`; источник на портале — план брожения
  рецепта (`fermentationPlan`) либо простой редактор ступеней на пульте.
- **Контур:** охлаждение (`coolOn`) с отсчётом анти-короткого-цикла компрессора
  (`coolLockS`), нагрев, разрешение.
- **Уведомления:** отклонение от уставки больше порога, конец шага профиля, аварии — web-push
  (механизм Phase 6). Для недельного процесса это обязательная часть, не опция.
- **Свежесть:** прошивка шлёт 1 Гц во всех режимах (§13) — пороги «В эфире/Устарело» общие;
  режимные пороги понадобятся, только если прошивка перейдёт на редкий кадр в FERMENT (v2).

### 8.4 Связка с партией (зона A)

Партия пива после варки идёт в ферментер — соединяем два мира:

- На пульте ферментации: «В ферментере: партия … » → ссылка на партию. Привязка задаётся с
  партии (акт «Брожение»: «бродит в приборе …» — выбор из приборов в режиме ферментации),
  не с пульта.
- Доска брожения партии (`fermentation-board`) получает живую температуру и график с прибора
  вместо ручных отметок (ручные остаются для партий без автоматики — паритет с
  «веб-помощником» варки).
- Привязка **опциональна**: брага/не-пивной ферментер работает без партии.
- **Граничный случай:** прибор переключили из ферментации при привязанной партии → партия
  показывает «прибор больше не в режиме ферментации», собранные данные остаются в истории
  партии; привязка снимается вручную (не молча).

## 9. Киоск — «веб как экран устройства»

Ответ на «хочу выводить управление на телефон/планшет/ПК». Не отдельный продукт, а режим
отображения того же пульта.

- **Вход:** ⛶ в хедере пульта; состояние в URL (`?kiosk=1`) — шарабельно, переживает reload,
  закладка на планшете открывает сразу киоск.
- **Состав:** герой + полоса стадий + контур + транспорт + аварии/промпты. Убирается весь
  хром сайта (навигация, футер, паддинги страницы). E-STOP остаётся всегда.
- **Типографика:** температура — главный элемент, порядка 15–20 vh, tabular-nums; стадия и
  таймер читаются с 2–3 м. Три брейкпоинта: телефон (одна колонка, транспорт в зоне пальца —
  уже есть), планшет-ландшафт (герой слева, статус/управление справа), десктоп/ТВ (то же,
  крупнее).
- **Не гаснуть:** Screen Wake Lock API (требует secure context — работает на HTTPS-облаке;
  на LAN по `http://192.168…` не сработает → честная подсказка «включите „не гасить экран“
  в настройках планшета»). PWA-манифест, чтобы «на главный экран» открывался как приложение.
- **Живучесть:** авто-reconnect SSE уже есть; при обрыве киоск показывает крупный статус
  «Офлайн / данные устарели» — экран у плиты не должен молча врать.
- **Выход:** Esc / кнопка. Тёмная тема киоска — опция v2 (проект пока light-only).
- Киоск ценен **уже для варки** — не ждёт дистилляции/ферментации (§15).

### 9.1 Несколько экранов и аренда управления

Сценарий «планшет-киоск у прибора + телефон в руке» — это **два сеанса одного пользователя**,
а control-lease — single-writer. Поведение:

- **Киоск сам аренду не захватывает** — он экран. Аренда берётся первым сеансом, отправившим
  команду (существующая модель: явный запрос/перехват).
- Команда с другого экрана → штатный **перехват в один тап** (takeover уже реализован);
  никакого «идите на планшет и отпустите».
- Киоск крупно показывает, кто управляет («управляет другой сеанс» — существующий
  `otherSessionHolds`), чтобы экран у прибора не выглядел «сломанным», когда командует телефон.
- **E-STOP не требует аренды ни на одном экране** (fail-safe, уже так).

## 11. Конфигурируемость — рамки

«Конфигурируемо» ≠ конструктор дашбордов. Три слоя, от дешёвого к дорогому:

1. **Адаптация (v1, само):** режим прибора выбирает пульт; capabilities/опциональные поля
   телеметрии скрывают несуществующее железо (паттерн уже есть). Покрывает 90% потребности.
2. **Видимость панелей (v2):** «скрыть датчики / показать журнал» — чекбоксы на пульте,
   хранится per-device в localStorage/профиле.
3. **Конструктор виджетов (не планируем):** осознанно нет — противоречит «просто и понятно»,
   дорого в поддержке. Вернуться только если появится реальный спрос.

## 12. Требования к дизайну

- **Единый язык с существующим пультом:** те же карточки (`rounded-2xl border-zinc-200`),
  `@nb/ui Button` (primary/outline/danger), пилюли статусов emerald/zinc, амбер для промптов,
  красный для аварий. Дистилляция и ферментация не заводят собственных стилей.
- **Семантика цвета едина по режимам:** emerald = активный выход/ОК, amber = требуется
  действие/внимание, red = авария/деструктив, zinc = выключено/нет данных.
- **Числа:** `tabular-nums` везде, температуры с одним знаком после точки, таймеры `м:сс`
  (варка/дистилляция) и «день N из M» (ферментация).
- **Тач:** min-h 44px, транспорт в зоне пальца на мобиле (уже принято L2 §5).
- **Никаких пояснительных подзаголовков** — самоочевидность через названия/иконки/порядок
  (глобальное правило владельца).
- **Термины:** куб · колонна · дефлегматор · головы/тело/хвосты · отбор · флегма · приёмная
  ёмкость; главное брожение · диацетильная пауза · холодная выдержка · уставка. Никаких
  калек («сердца», «хвостовые фракции» — только формы из речи сообщества).
- **Офлайн-честность:** любой экран (особенно киоск) явно отличает «данные устарели» от
  «всё выключено» — правило уже действует, распространить на новые панели.

### 12.2 Уведомления (web-push, механизм Phase 6)

| Режим | События |
|---|---|
| Варка | промпты (засыпь/йодная/промывка), внесение хмеля (W6), аварии — как есть |

### 12.3 Доступность

- Статус — никогда только цветом: пилюли с текстом ВКЛ/ВЫКЛ (уже так), полоса стадий — с
  подписями.
- Все контролы — настоящие `button` с фокус-состояниями; hold-to-confirm имеет клавиатурную
  альтернативу.
- Живые цифры героя — без `aria-live` (спам SR); статусные переходы (авария, промпт) —
  `role="alert"` (уже так в баннерах).
- `prefers-reduced-motion` — отключает анимации графика/полосы.

### 12.4 Онбординг и обнаружимость

- **Демо-приборы для всех режимов:** расширить симулятор (`packages/brewforge-sim`)
  сценариями дистилляции и ферментации — «Демо-пивоварня» на L1 превращается в выбор из трёх
  демо (или демо-прибор умеет переключать режимы). Пользователь щупает все пульты без железа.
- **Киоск:** кнопка ⛶ видима в хедере пульта (не зарыта в меню); при первом входе — одноразовая
  подсказка «экран не будет гаснуть» (или честная про wake lock на LAN, §9).
- Пустые состояния L1 — как есть; режимные пульты определяют свои (§12.1).

## 13. Контракт прошивка ↔ портал — факты и пакет работ

> Сверено с `../brewforge` (bf_types.h, bf_proto.c, bf_state.h) 2026-07-03. Обе стороны
> подвижны (решение владельца): прошивку можно править под портал и наоборот.

**Факты — прошивка дальше, чем предполагал портал:**

- **Профили обоих режимов УЖЕ в конфиге** и сериализуются в `GET/PUT /config`:
  `distill{headsPct, heartsPct, tailsPct, tHeadsC…tEndC, *Reflux, refluxWindowS}` и
  `ferment{hysteresisC, compMinOffS/OnS, heatEnabled, nSteps, steps[{tempC,hours}]}`
  (bf_proto.c:874–898), плюс `appMode` (：913, config v11). Портальный `DeviceConfigSchema`
  их пропускает через `.passthrough()`, но не типизирует и не рендерит. ⇒ **Отдельный
  контракт профиля брожения не нужен** — портал дописывает типизацию + UI поверх
  существующего пути конфига.
- **CMD_MAP прошивки шире портального протокола:** сетевые `MANUAL_PUMP2 / MANUAL_VALVE /
  MANUAL_COOL` (этап 6-A) и `FORCE_PUMP / FORCE_PUMP2 / FORCE_VALVE` (этап 6-D, любая стадия
  кроме FAULT) — в `@nb/brewforge-protocol` их нет. Клапан отбора и охлаждение уже управляемы
  удалённо на уровне прошивки.
- **START_DISTILL / START_FERMENT / SET_APP_MODE — намеренно локальные** («стартуются только
  с LVGL-экрана», «топология/режим правятся только локально»). Философия прошивки совпадает
  со спекой (§2, §10) — не меняем.
- **`hxTempC` — это HLT/труба HERMS/RIMS, НЕ колонна.** Дистилляция ведётся по primary
  (куб) + температурные пороги фракций из конфига. Датчик колонны/пара — при желании
  обычный датчик из `sensors[]`; отдельная роль не обязательна для v1 (герой: куб крупно +
  выбранный датчик, если назначен).
- **Телеметрия всегда 1 Гц** (`BF_TELEMETRY_PERIOD_MS`), включая FERMENT ⇒ пороги свежести
  общие, режимные не нужны; хранение решает портальный даунсэмпл (§14). Редкий кадр в
  FERMENT — необязательная оптимизация трафика (v2).

**Пакет работ по контракту:**

| # | Что | Где |
|---|---|---|
| 1 | `appMode` в телеметрию (сейчас только в конфиге; IDLE-дистиллятор неотличим от пивоварни без чтения конфига) | прошивка `bf_proto_telemetry_json` + Zod optional |
| 2 | Догнать CMD_MAP: `MANUAL_PUMP2/VALVE/COOL`, `FORCE_*` в `CommandTypeSchema` + билдеры | портал `@nb/brewforge-protocol` |
| 3 | Типизировать `distill{}`/`ferment{}`/`appMode` в `DeviceConfigSchema` + `CONFIG_FIELD_RANGES` (клампы из `bf_config_parse_json_clamped`) | портал |

## 14. Данные / бэкенд портала

- **Always-on персист телеметрии** для длинных режимов: сейчас история пишется даунсэмплом
  ~10 с только пока открыт пульт (см. `features/devices/contracts.ts`). Для ферментации мост
  должен писать всегда (редкий даунсэмпл, например раз в 5 мин в FERMENT; в DISTILL — как
  варка). Иначе график «план vs факт» будет дырявым.
- **Привязка партия ↔ прибор-ферментер:** поле/таблица связи (партия в акте «Брожение» знает
  deviceId) — по образцу существующей связки варка↔устройство.
- **Журнал перегонов (v2):** времена фракций из телеметрии + ручные объёмы/крепость.
- Плитки L1: `DeviceTileSnapshot` дополнить `appMode` (+ поля для режимной сводки).
- **Офлайн-watchdog ферментации (§12.2):** серверная периодическая проверка `lastSeenAt`
  приборов в режиме ферментации → пуш при молчании > порога. Клиентская проверка не годится
  (вкладка закрыта неделями).
- **Симулятор:** сценарии distill/ferment в `packages/brewforge-sim` — нужны для демо (§12.4)
  и для разработки пультов без железа/прошивки.
