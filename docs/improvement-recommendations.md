# Рекомендации по улучшению приложения NB

**Дата анализа:** 2026-06-23
**Объект:** монорепо `nb` — web-first платформа для домашних пивоваров (Next.js 15 App Router, React 18, TypeScript strict, Drizzle/PostgreSQL, npm workspaces).
**Метод:** статический анализ кода по пяти направлениям — архитектура, безопасность, данные/производительность, фронтенд/UX, тесты/инфраструктура. Все находки привязаны к файлам и строкам.

> Приоритеты: **P1** — критично (безопасность/корректность/блокирует развитие), **P2** — важно (качество/производительность/риски), **P3** — желательно (полировка, DX).

## 2. Безопасность

### P1 — Токены аутентификации пишутся в логи
`apps/web/lib/auth.ts:73, 87, 138` — `console.info` выводит весь объект верификации, включая `rawToken`, magic-link и ссылку сброса пароля.
```ts
console.info("[auth] OTP token", verification);            // :73
console.info("[auth] Magic link", { ...verification, link }); // :87
console.info("[auth] Password reset", { ...verification, link }); // :138
```
**Риск:** токены попадут в серверные логи / централизованный сбор логов и позволят захватить аккаунт.
**Рекомендация:** убрать или спрятать за dev-only флагом (`if (process.env.NODE_ENV !== "production")`), а в идеале — выводить только в почту (есть Mailpit в `docker-compose.yml`).

### P1 — Капча отключена (заглушка)
`apps/web/lib/anti-abuse.ts` — `verifyCaptchaHook` возвращает `true`, если `AUTH_CAPTCHA_SECRET` пуст (дефолт), пропускает `"dev-pass"`, а в остальных случаях всегда `false` — **реального обращения к сервису капчи нет**. Используется в `app/api/auth/{otp,magic,password}/route.ts`.
**Риск:** auth-эндпоинты без защиты от ботов/брутфорса (rate-limit есть, но капчи нет).
**Рекомендация:** реализовать реальную проверку (hCaptcha/reCAPTCHA/Turnstile), а в проде запретить пустой `AUTH_CAPTCHA_SECRET`.

### P1 — Magic-link токен в GET-параметрах
`apps/web/lib/auth.ts:86` + `app/api/auth/magic/route.ts` — ссылка вида `/api/auth/magic/consume?email=...&token=...`.
**Риск:** токен оседает в истории браузера, access-логах, Referer, у прокси/CDN.
**Рекомендация:** обмен токена через POST/одноразовую сессию, не передавать сырой токен в URL для логируемых переходов.

### P2 — Очистка просроченных верификаций не запускается
`packages/auth/src/service.ts:231` — `cleanupExpiredVerifications` экспортируется, но нигде не вызывается → таблица `verifications` растёт бесконечно.
**Рекомендация:** периодический job (cron/скрипт) на ежедневную очистку.

### P2 — Защита dev-байпаса `DEV_AUTH_EMAIL`
`apps/web/lib/auth.ts` — байпас корректно отключён при `NODE_ENV=production`, но если `.env` с заданным `DEV_AUTH_EMAIL` случайно уедет в прод при неверном `NODE_ENV`, все запросы без сессии станут одним пользователем.
**Рекомендация:** добавить «предохранитель» — бросать ошибку на старте, если `DEV_AUTH_EMAIL` задан при `NODE_ENV=production`; задокументировать в деплой-инструкции.

### P3 — Прочее (hardening)
- Возможная **энумерация аккаунтов** по таймингам rate-limit на сбросе пароля (`app/api/auth/password/route.ts`) — отвечать единообразно независимо от существования email.
- `refreshToken` OAuth хранится без шифрования (`apps/web/lib/oauth.ts`) — зависит от защиты БД; рассмотреть шифрование на уровне приложения.
- CSRF на API-роутах держится на `SameSite=Lax` — задокументировать допущение «только same-origin».

**Хорошо уже сейчас:** хеширование токенов (SHA-256), пароли (scrypt+salt), httpOnly+SameSite+secure(prod) cookie, проверки владения на мутациях рецептов/картинок, RBAC на админ-роутах, валидация входа через Zod на ряде эндпоинтов, проверка OAuth state.

## 3. Производительность и слой данных

### P1 — N+1 запросы в сервисе рецептов
`apps/web/features/recipes/service.ts`:
- **Гидратация ингредиентов** (`recomputeRecipeStats`, ~1247–1307 и `hydrateRecipeIngredientDto`, ~884–927): по запросу на каждый ингредиент (`ensureCatalogIngredientExists` / `ensureOwnedCustomIngredient`). Рецепт на 17 позиций → +17 запросов.
- **Подсчёт версий семейств** (`listRecipesForAuthor`, ~1644–1650): отдельный `COUNT` на каждое `recipeFamilyId` в цикле. 20 семейств → +20 запросов.
- **Синхронизация позиций** (`syncRecipeIngredients`, ~1059–1084): отдельный `update`/`insert` на каждую позицию.
- Аналогично в `features/recipes/inventory-service.ts:352–370`.

**Рекомендация:** батч-выборки через `inArray()` перед циклом; агрегаты через `GROUP BY`; пакетные вставки/обновления в транзакции.

### P2 — Отсутствуют индексы на внешних ключах
`packages/db/src/schema.ts`:
- `ingredient_catalog_items.created_by` / `updated_by` (~278–279) — без индексов.
- `proposed_ingredients.submitted_by_user_id` (~296), `moderator_id` (~303) — без индексов (есть только по `status+createdAt` и `normalizedName`).

**Рекомендация:** добавить индексы и миграцию; проверить остальные FK, по которым идут выборки/JOIN.

### P2 — «Загрузить всё → фильтровать в памяти»
`apps/web/features/ingredients/service.ts:~312–333, ~550–645` — `loadIngredients` тянет все ингредиенты со всеми связями (`aliases`, `sources`, `packageVariants`), затем ранжирование/фильтрация в памяти. На тысячах позиций это дорого и по памяти, и по времени.
**Рекомендация:** перенести фильтрацию в SQL (WHERE/полнотекст/триграммы), связи подгружать только для финального набора; рассмотреть индекс для поиска по имени.

### P3 — Кэширование
- Расчёты рецепта (`recomputeRecipeStats`, ~1242–1344) не кэшируются — пересчёт на каждый просмотр. Кэшировать результат в рецепте, пересчитывать только при изменении состава.
- Нет использования Next.js-кэша (`unstable_cache`/`revalidateTag`/`React.cache`) для списков рецептов/ингредиентов/инвентаря.

**Хорошо:** миграции безопасны (`IF NOT EXISTS`, аккуратные casts, без деструктивных операций).

## 4. Архитектура и организация кода

### P1 — Компоненты-«монстры» с бизнес-логикой
Топ крупнейших файлов (строки):

| Файл | Строк | Проблема |

| `components/recipes/recipe-designer.tsx` | ~6323 | ~20 экспортируемых утилит + ~16 inline-подкомпонентов + 39 `useState` |
| `components/ingredients/ingredient-picker.tsx` | ~3171 | ~40 экспортов логики поиска вперемешку с UI |

| `features/recipes/service.ts` | ~1783 | 48 импортов, 15 функций |
| `features/ingredients/catalog-service.ts` | ~1748 | — |

**Рекомендация:** вынести чистые утилиты в `features/*` (тестируемые модули), `recipe-designer.tsx` разнести на подкомпоненты (`ingredient-editor.tsx`, `style-picker.tsx`, `recipe-profiles.tsx` и т.д.) — цель свести головной файл к ~2–3 тыс. строк. Это разблокирует и тестируемость (см. раздел 6).

### P2 — Дублирование обработки ошибок
В `app/(app)/app/{recipes,ingredients,catalog}/actions.ts` повторяется маппинг Zod-ошибок и кодов в сообщения (напр. `recipes/actions.ts:80–107`). ~60+ try/catch с похожей логикой.
**Рекомендация:** общий `lib/error-handling.ts` с `translateZodError()` и универсальным маппером.

### P2 — Утечки слоёв
`features/ingredients/custom-catalog-form-values.ts:1` импортирует тип из `@/components/...` — фича зависит от компонента (риск циклов).
**Рекомендация:** типы контрактов держать в `features/*/contracts.ts`, компоненты импортируют из фич, не наоборот.

### P2 — Смешение server actions и API-роутов
Большинство логики — в server actions, но часть в API-роутах (`api/ingredients/search`, `api/inventory/suggestions`).
**Рекомендация:** задокументировать правило выбора (когда роут, когда action) и придерживаться его.

### P3 — Мелочи
- Мёртвый пакет `@nb/search` (`packages/search/src/index.ts` — только метаданные `status: "scaffold"`, нигде не импортируется) — удалить или задокументировать как план.
- Магические числа/константы в компонентах (напр. `ingredient-picker.tsx`) — вынести в контракты.
- Крупные contract-файлы (`ingredients/contracts.ts` ~688, `recipes/contracts.ts` ~555) — при желании разбить на типы/схемы/лейблы.

## 5. Фронтенд и UX

### P1 — Управление состоянием редактора рецепта
`recipe-designer.tsx` — 39 `useState` в `RecipeDesigner`, прокидывание пропсов через вложенные компоненты, 100+ обработчиков.
**Рекомендация:** консолидировать в `useReducer` + выделенные хуки (`useRecipeEditorState`, `useIngredientEditor`, `useIngredientSearch`); при необходимости — `RecipeEditorContext` для глубоко вложенных частей.

### P2 — Непоследовательная валидация форм
Каждая форма реализует свою валидацию: `custom-ingredient-form.tsx` (реалтайм), `catalog-ingredient-form.tsx` (`validateCatalogIngredientNumbers`), `inventory-item-details-editor.tsx` (`validateInventoryEditorNumbers`), редактор рецепта (`validateNumericInput` + field-level). Сообщения и поведение различаются.
**Рекомендация:** общий хук `useFormValidation()` и единый паттерн отображения ошибок у поля (как недавно сделано в редакторе ингредиента рецепта — взять за эталон). Маппинг сообщений вынести из компонентов.

### P2 — Обработка ошибок промисов
`recipe-designer.tsx:~3933–3942` — `Promise.all` по группам поиска воды без `.catch`: падение одного запроса рушит всю загрузку. Парсинг `response.json()` в пикере (~3594, ~3874) без явных error-состояний → тихие сбои.
**Рекомендация:** оборачивать `Promise.all` в try/catch с деградацией; показывать пользователю состояние ошибки поиска.

### P3 — Доступность (a11y)
- Нет focus-trap в модалках/дроверах (`ingredient-add-drawer.tsx`); Esc обрабатывается, но фокус может «убежать», нет восстановления фокуса после закрытия.
- Ошибки полей не связаны с инпутами через `aria-describedby` (множество форм).
- Иконочные кнопки местами без `aria-label`; неполные `inputMode`/типы.

### P3 — i18n
i18n-слоя нет, строки (193+ только в `recipe-designer.tsx`) захардкожены по-русски.
**Рекомендация:** если планируется мультиязычность — внедрить `next-intl` и вынести строки в словари. Если нет — зафиксировать решение «русский как единственный язык», чтобы это был осознанный выбор.

### P3 — Адаптивность
Точечные хардкод-размеры (`w-[72px]`, `h-7` и т.п. в `recipe-designer.tsx`); `useIsMobile()` объявлен, но в `ingredient-add-drawer.tsx` `isMobile` фактически не используется (`void isMobile`). Проверить на узких экранах (<320px).

## 6. Тесты, наблюдаемость, инфраструктура

### P1 — Пробелы покрытия
- **API-роуты:** из ~22 покрыты тестами ~3. Без тестов — все auth-роуты (`otp`, `magic`, `password`, `logout`, OAuth google/vk/yandex), админ-роуты ингредиентов, загрузка картинок.
- **Пакеты:** `@nb/auth`, `@nb/ui`, `@nb/shared`, `@nb/search` — **0 тестов**; `@nb/db` — почти нет.
- **Нет e2e/интеграционных тестов** с реальной БД (всё на моках).
- `recipe-designer.tsx` тестируется только через `renderToStaticMarkup` (статичный HTML) — интерактив/состояние не проверяются.
- `vitest.config.ts` включает только `tests/**/*.test.ts` и `environment: "node"` — DOM-тесты компонентов фактически вне покрытия; нет отчёта о coverage.

**Рекомендация:** покрыть auth/админ API-роуты интеграционными тестами; добавить тесты на `@nb/auth` и др. пакеты; ввести e2e (Playwright) на ключевые сценарии (регистрация→рецепт→публикация); тестировать редактор рецепта через React Testing Library; включить coverage с порогами.

### P2 — CI/CD
`.github/workflows/ci.yml` — один последовательный пайплайн (`install → lint → typecheck → test → build`).
**Пробелы:** нет проверки миграций (`db:generate` + «нет незакоммиченных изменений схемы»), используется `npm install` вместо `npm ci`, нет coverage-порогов, нет `npm audit`, не собирается Docker, шаги не распараллелены.
**Рекомендация:** добавить шаг проверки дрейфа миграций, перейти на `npm ci`, разнести job'ы, добавить аудит зависимостей.

### P2 — Типобезопасность
`strict: true` включён (`tsconfig.base.json`), но в неtestовом коде **~60** `@ts-ignore`/`@ts-expect-error` и **~83** вхождения `any`/`as any` (проверено grep'ом). Плюс ~21 non-null assertion (`!`) в парсинге/состоянии (`bjcp-*`, `lib/oauth.ts`, `recipe-designer.tsx`, `features/inventory/service.ts`).
**Рекомендация:** провести аудит подавлений — каждое либо починить, либо обосновать комментарием; заменить `!` на type-guards; рассмотреть ESLint-правила `no-explicit-any`, запрет ban-ts-comment без описания.

### P2 — Обработка ошибок / логирование
Sentry и PostHog **подключены** (`instrumentation.ts`, `sentry.*.config.ts`, `lib/analytics.ts`) — это хорошо. Но:
- Структурного логирования нет — точечные `console.*`.
- `features/recipe-images/service.ts` глушит ошибки удаления из стораджа `catch { console.error }` без проброса → возможны «осиротевшие» файлы/неконсистентность.

**Рекомендация:** ввести тонкий логгер-обёртку; решить политику для ошибок очистки стораджа (ретраи/отложенная очистка/метрика).

### P3 — DX и зависимости
- Нет Prettier, нет pre-commit хуков (husky/lint-staged) — формат и линт не гарантируются до коммита.
- ESLint минимален (`next/core-web-vitals` + `next/typescript`), нет правил сложности/циклов/`no-console`.
- Устаревшие зависимости: `@aws-sdk/client-s3` (сильно), `drizzle-orm` (0.36→0.45), `@sentry/nextjs`, Radix/Tiptap; есть лишняя `@emnapi/runtime`.
- `docker-compose.yml` хорош (Postgres 16 healthcheck, Mailpit), но без контейнера самого приложения.

## Приложение: что уже сделано хорошо

- Чёткая базовая структура: `app/` · `features/` · `components/` · `lib/` · `packages/`; устойчивый паттерн `features/*/contracts.ts`.
- TypeScript strict, изоляция модулей.
- Безопасные дефолты крипто/сессий (хеши токенов, scrypt, httpOnly/secure cookie, RBAC, проверки владения).
